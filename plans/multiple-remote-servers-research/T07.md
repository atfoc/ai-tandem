**completed**: R1, R2 and R4 were run on this Mac with scratch servers; R3's container runs are unknown because no Docker daemon was running, so only the Linux cross-compile is verified (static, no cgo, amd64 and arm64). A server-only install is the binary plus the client folder (37 files, about 20 MB), started with `launch -client <absolute path>`; under an SSH-like environment it prints the URL in about 0.15 s, survives the parent's exit and SIGHUP, and a repeated `launch` is idempotent. The main hazards found: `launch` identifies a running server by port and not by data folder, MCP port 6006 allows one server per machine, a missing client folder fails silently, and slow login files delay `launch` past its 5 s limit.

## R2. Started the way SSH would start it

Method:
- A Perl parent stood in for sshd. It calls `setsid`, starts the command with stdin from `/dev/null`, stdout and stderr on pipes, and the working folder set to the home.
- The command was:
  `/usr/bin/env -i HOME=<scratch>/fakehome USER=pedjat SHELL=/bin/zsh PATH=/usr/bin:/bin AIWB_MCP_PORT=52782 CURSOR_CONFIG_DIR=<tmp> /bin/zsh -c '<install>/ai-whiteboard launch -port 52781 -home <scratch>/h6 -client <install>/web -claude … -cursor … -pi … -cursor-cost …'`
- The fake home was empty (no login files) unless stated.

Findings:

- **Time until the URL line — verified.** Cold start 0.154 s and 0.155 s; server already running 0.027 s. Stdout EOF, stderr EOF and process exit all came at the same moment (0.156 s cold), with stderr empty and exit 0. So `ssh host launch…` returns as soon as the URL is printed; the server holds none of the pipes (its fd 0 is `/dev/null`, fd 1 and 2 are `server.log`).

- **Survives the parent's exit and SIGHUP — verified.**
  - Parent exits at the URL line: the process group was already empty (`kill -HUP -80325` → "No such process"), and the server kept answering.
  - Parent kept alive, then `kill -HUP -<pgid>`: the parent died ("Hangup: 1"); the server (`ppid 1`, `pgid` = its own pid, tty `??`) still answered `hello` with the same pid.

- **A foreground `serve` does not survive SIGHUP — verified.** `kill -HUP <serve pid>` ended it with status 129 and no shutdown path: `server.json` and `bridge.sock` were left behind. The next `launch` recovered (new pid, 0.197 s). Over SSH use `launch`, not `serve`.

- **`PATH` of the server — verified.** `ps eww` showed:
  ```
  PATH=/usr/local/bin:/System/Cryptexes/App/usr/bin:/usr/bin:/bin:/usr/sbin:/sbin:/var/run/com.apple.security.cryptexd/…:/Library/Apple/usr/bin
  all variables: HOME USER SHELL PATH AIWB_MCP_PORT CURSOR_CONFIG_DIR LOGNAME SHLVL OLDPWD _ PWD
  ```
  - The login-shell step ran and replaced `/usr/bin:/bin` with the system login path (`/etc/zprofile`), since the temp home has no user files.
  - With a `.zprofile` adding `$HOME/tools` and a `.zshrc` printing a banner on stdout: `PATH` began with `<fakehome2>/tools:` and `launch` still printed only the URL (0.206 s).
  - With a real home the user's own login files would run, which is how `claude`, `agent` and `pi` in user folders get found — inferred; I did not read the real home.
  - Only `PATH` is taken (`launch.go:222-237`). Other variables exported in login files do not reach the server or its agents, and the server has no `LANG`, `TERM` or `TMPDIR` — the variable list is verified, the consequence for agents is inferred.

- **The 5 s limit on the login-shell step does not bound `launch` — verified.** With `.zshrc` containing `sleep 12`: `launch` took 12.209 s, exit 0, and the server's `PATH` stayed `/usr/bin:/bin`. A slow login file therefore delays every cold start and loses the login `PATH`.

- **`$SHELL` variants — verified on macOS.**

  | `SHELL` | launch | seconds | server `PATH` |
  |---|---|---|---|
  | `/bin/zsh` | ok | 0.15 | login path |
  | `/bin/sh` | ok | 0.23 | login path |
  | `/bin/dash` | ok | 0.55 | login path |
  | `/bin/bash` | ok | 0.18 | login path |
  | `/nonexistent/zsh` | ok | 0.19 | `/usr/bin:/bin` (unchanged) |
  | unset | ok | 0.20 | login path (falls back to `/bin/zsh`, `launch.go:203-205`) |

- **Log — verified.** `<-home>/server.log`, mode 0600, appended, each start preceded by `--- <RFC3339 time> launch`. A second `launch` adds nothing to it. There is no rotation — inferred from `launch.go:99-106`.

- **Second identical `launch` — verified idempotent.**
  - Same URL, exit 0, 0.027 s, same server pid, log unchanged.
  - Five at once against a running server: five identical URLs, one server.
  - Five at once cold: five identical URLs, exactly one `serve` left; the losers wrote `AI Whiteboard is already running at …` into `server.log`.

- **Flags are ignored when a server is already running — verified.** `launch -port 52799 -home <same>` printed `http://127.0.0.1:52781/`, exit 0.

- **The running server is identified by port, not by home — verified.**
  - `launch -port 52781 -home <scratch>/h7` while h6's server held 52781 printed `http://127.0.0.1:52781/`, exit 0.
  - `h7` was never created, and `/api/state` at that URL reports `dataDir …/h6`.
  - `stop -home h7` then says `AI Whiteboard is not running` (exit 0) and the server keeps running.
  - On a machine where another user or another data folder already has a server on the port, `launch` hands back that server (`main.go:269-285`).

- **`stop` with the same `-home` — verified.**
  - `AI Whiteboard stopped`, exit 0; the pid is gone; `server.json` and `bridge.sock` are removed; `boards`, `chats`, `pi-extension`, `server.log`, `state.json` remain.
  - A second `stop`: `AI Whiteboard is not running`, exit 0.
  - After `kill -9`: `stop` says "not running" and the stale `server.json` stays; the next `launch` works (0.166 s).

- **Failure modes as an SSH caller would see them — verified.**

  | Situation | stdout | stderr | exit | seconds |
  |---|---|---|---|---|
  | MCP port already held | empty | `AI Whiteboard: the server stopped while starting` + log tail `cannot serve the MCP endpoint on port 52782: … address already in use …` | 1 | 0.08 |
  | HTTP port held by a program that is not AI Whiteboard | empty | `AI Whiteboard: the server did not answer within 30 seconds` / `See <home>/server.log` | 1 | 30.09 |
  | `-home` cannot be created | empty | `AI Whiteboard: cannot start the server` / `cannot create the data folder …` | 1 | — |
  | Binary not at the given path | empty | `zsh:1: no such file or directory: …` | 127 | — |
  | Bare `ai-whiteboard` with ssh's `PATH` | empty | `zsh:1: command not found: ai-whiteboard` | 127 | — |

  The desktop's own limit for `launch` is 40 s (`desktop/lib.js:6`).

## What a remote machine needs

Built only from verified findings.

- **Files:** the `ai-whiteboard` binary for that OS and architecture, and the built client folder next to it (37 files, about 20 MB together on macOS arm64), both stamped with the same version.
- **Start command:** `<abs>/ai-whiteboard launch -client <abs>/web`, by absolute path; a bare `ai-whiteboard` is not found under SSH's `PATH`. Or use the bundle-shaped layout, which needs no flag.
- **Health check after start:** `webVersion` must not be `"dev"`, or `GET /` must be 200. `launch` exits 0 and prints a URL even when the client folder is missing.
- **Reading the result:** stdout is exactly one line, `http://127.0.0.1:<port>/`, exit 0. On failure stdout is empty, the reason is on stderr, and exit is 1 (or 127 from the shell). Failure can take 30 s.
- **Use `launch`, not `serve`.** `launch` detaches and survives the session's end and SIGHUP; a foreground `serve` dies on SIGHUP and leaves `server.json` and `bridge.sock`.
- **`launch` on every connect is safe:** same URL, same server, about 30 ms, also when several run at once. Its flags have no effect once a server runs.
- **Free loopback ports:** the HTTP port (4747 unless `-port`) and the MCP port. A second server that cannot get the MCP port fails at once with the message quoted in R2.
- **One port, one server:** `launch` returns whatever AI Whiteboard server answers on the port, whatever its data folder. A connecting app should compare `/api/state` `dataDir` or `/api/hello` `pid` with what it expects.
- **Login shell:** `$SHELL` must work with `-ilc` and finish quickly. A slow login file delays every cold start by its full duration and loses the login `PATH`. A missing shell is tolerated, but then `PATH` is only what SSH gave.
- **Agent CLIs:** none is needed to start. A missing one shows only in `server.log` and as a `null` catalog for Cursor and pi.
- **Side effects in the user's home:**
  - the data folder (`-home`, default `~/.ai-whiteboard`) including `server.log`, which only grows;
  - an existing Cursor `cli-config.json` is rewritten with two deny rules that are never removed;
  - with a long data-folder path, an `aiwb-<hash>` folder in the temp dir that is never removed.
- **OS limits:** macOS runs as tested. Linux compiles without cgo to a static binary for amd64 and arm64. Windows does not compile. "Reveal in Finder" returns a 500 wherever `open` is absent.
- **Stopping:** `ai-whiteboard stop -home <same home>`. With the wrong home it reports "not running", exits 0 and leaves the server up.
