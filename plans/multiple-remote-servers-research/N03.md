# N03 — How a new chat starts today, what is chosen where, and how the sticky defaults work

Today the agent is the only thing chosen at "+": every menu that makes a chat lists the three agents, and `POST /api/chats {agent, group|board|run}` fixes the agent for the life of the chat. Folder, model and effort are resolved by the server at creation from the sticky defaults and stay changeable in the composer (`PATCH /api/chats/{id}`) until the first message, which sets `Locked`. No agent process, session or per-agent file exists before the first message; the only per-agent thing made at creation is a session id string for Claude and pi. There is no route that changes a chat's agent, but nothing started stands in the way of adding one for an unlocked chat. The defaults are one object in `state.json`: `last` (most recent choices anywhere) and `groups[<group id>]`, each holding a folder, a model+effort per agent, and a run record; "last" is read in four places (two fallbacks in `Resolve`, top-level group seeding, the run defaults) and nothing in the web client reads the defaults at all. A draft run is the working example of the pattern asked for: it is created with no choice, and its agent, folder and models are changed by `PATCH` until the start.

## S2. What depends on the agent being known at creation

Very little is allocated per agent before the first message: a session id string. The agent process starts at the first `Send`, never at creation. A chat's agent cannot be changed by any route today. What does assume the agent is known from the first moment is validation, the choice of catalog for the model and effort, and every place the client draws the chat.

**When the process starts.** `Create`'s own comment: "No agent starts: it starts on the first Send" (`internal/chats/manager.go:762`). `Open` (selecting the chat) "never starts an agent" (`internal/chats/manager.go:818-822`). `spawn` is called only from `Send` (`internal/chats/manager.go:853-856`) and picks the spawner by `c.meta.Agent` (`internal/chats/manager.go:870`); `spawnOptions` reads agent, session id, folder, model, effort and token at that moment (`internal/chats/manager.go:982-992`).

**Can the agent be changed after creation?** No. `PATCH /api/chats/{id}` accepts only `name`, `group`, `model`, `effort`, `cwd` (`internal/server/server.go:705-738`); `ConfigReq` has only `Model, Effort, Cwd` (`internal/chats/manager.go:200-202`). No other route writes `ChatMeta.Agent`.

## S3. The pickers in the chat today

The composer's toolbar shows three choices: folder, model, effort (plus the context meter, which is not a choice). There is no agent and no server picker. Each change is one `PATCH /api/chats/{id}?branch=…`. They lock when the first message is sent.

**Routes and storage.** `api.configure(id, branch, {model?, effort?, cwd?})` → `PATCH /api/chats/{id}` (`web/src/api.ts:131`) → `Chats.ConfigureOf` (`internal/server/server.go:729-735`). The server expands and checks the folder (`~`, relative paths, must be a directory: `internal/server/server.go:196-209`; the same in `chats.expandDir`, used at `internal/chats/manager.go:1370`), refuses the app's own data folder (`:1375-1378`), resolves model and effort with `choose` (`:1381`), writes `chat.json` (`:1396`), records the sticky default (`:1401-1403`) and emits the chat's view (`:1404`).

`choose` (`internal/chats/choice.go:37-70`): a model must be in the agent's catalog; a new model keeps the current effort if the model offers it, else takes the model's default effort, else none; an effort must be one the model has. When the agent's catalog is not known (`nil`), anything is accepted (`internal/chats/manager.go:1468-1473`).

**The lock, on the server.** `Send` sets `c.meta.Locked = true` (`internal/chats/manager.go:1247`). `ConfigureOf` then:

| State of the branch | Folder | Model / effort | `path:line` |
|---|---|---|---|
| not `Locked` | open | open | `internal/chats/manager.go:1363` |
| `Locked` | refused, `ErrLocked` ("folder, model and effort are fixed once the chat has started", 409) | refused | `internal/chats/manager.go:189,1363-1366`, `internal/server/server.go:127` |
| `Locked` and the folder is missing on disk, request names only `cwd` | open (the "folder fix"), and written to every branch with the missing folder | refused | `internal/chats/manager.go:1356,1385-1408` |
| `Fresh` (a fork whose prefix has a user message and which has had no message of its own) | refused | open, unless a turn is running (`ErrBusy`); the agent process is started again on the new choice | `internal/chats/manager.go:1357-1362`, `internal/chats/restart.go:25-44` |
| archived, or a legacy chat | refused | refused | `internal/chats/manager.go:1347-1354` |
| a run agent's chat | refused (`ErrRunAgent`) | refused | `internal/chats/manager.go:1338`, `internal/chats/owned.go:200-205` |

A fork at a point with no user message before it is not `Locked` and behaves like a new chat (`internal/chats/fork.go:276-280`). A new branch never uses `PATCH`: its model and effort are picked in the composer while the move is pending and travel in the message's `target` (`web/src/Composer.tsx:399-402`, `web/src/api.ts:124-130`).

**The lock, in the client.** `pickerMode(c, move)` (`web/src/logic/models.ts:67-70`): `"move"` with a pending move; `"patch"` when `!c.locked || (c.fresh && !isBusy(c.status))`; else `"fixed"`. The folder has its own condition: `folderOpen = !c.locked || !!c.folderMissing` (`web/src/Composer.tsx:404`).

**What a locked picker shows.** Folder: a lock icon and a static chip with the folder's name, the full path in the tooltip (`web/src/Composer.tsx:408,636`). Model and effort: one static chip "model · effort" with the tooltip "Model and effort are fixed once the chat has started" (`web/src/Composer.tsx:411-414`). Open pickers carry the hint "can be changed until you send the first message" (`web/src/Composer.tsx:458`).

**The folder listing.** `DirBrowser` calls `api.dirs(path)` = `GET /api/dirs?path=…` (`web/src/Composer.tsx:654`, `web/src/api.ts:145`). The server lists the sub-folders of that path **on its own machine**, hiding dot-folders, and answers `{path, parent, dirs, git}`; an empty path means the server's default folder (`internal/server/server.go:771-791`). The browser starts at the chat's folder, else the snapshot's `defaultCwd`, else `home` (`web/src/Composer.tsx:657-662`). `~` in the display is the server's home from the snapshot (`web/src/Composer.tsx:52`, `internal/app/app.go:43-44`). The "Recent" list is the browser's own: up to six paths in `localStorage` key `aiwb.dirs`, written after each pick (`web/src/Composer.tsx:50-51,644`).

**The catalogs.**

- Loaded at server start: three goroutines ask each CLI for its model list with a 20 s limit, store it in `state.json` (`State.Catalogs`) and broadcast a `catalog` event; on failure the stored catalog stays (`cmd/ai-whiteboard/main.go:196-198,374-414`). A running agent's own `EvCatalog` updates it the same way (`internal/chats/manager.go:1039-1046`).
- Reach the page in the snapshot (`internal/app/app.go:41,57-75`) and by the `catalog` event (`web/src/conn.ts:61`); kept in `store.catalogs` by agent (`web/src/store.ts:52,117-118`).
- Claude always has one: a built-in list stands in until the CLI has reported (`internal/chats/manager.go:715-730`, `internal/app/app.go:57-62`). Cursor and pi have `null` until the first report.
- While a catalog is not loaded, or the CLI is missing so it never loads: the client shows a static chip "Loading models…" instead of both pickers (`web/src/Composer.tsx:415-416`); the folder picker still works. On the server a `nil` catalog makes `Resolve` return an empty model unless a default was recorded (`internal/defaults/defaults.go:27-33`), and `choose` accepts any model. A chat with an empty model can still be sent to: the CLI then uses its own default (**inferred** from `spawnOptions` passing `Model` through, `internal/chats/manager.go:984-985`). A missing CLI shows only as a failed start at the first message; the catalog itself says nothing about whether the CLI is installed (**inferred**: no "installed" flag exists in `Snapshot`, `internal/app/app.go:34-45`).

## S4. Sticky defaults, exactly

**The data** (`internal/model/model.go:103-117`, `internal/model/run.go:180-190`; mirrored in `web/src/types.ts:47-61,650`):

```
Defaults      { last: GroupDefaults, groups: { <group id | "__ungrouped__">: GroupDefaults } }
GroupDefaults { cwd?, byAgent?: { claude|cursor|pi: { model, effort? } }, run?: RunDefaults }
RunDefaults   { agent, maxParallel, maxTurns, maxCost, setup?, setupCwd?, tiers? }
```

The folder is per group for all agents; model and effort are per group and per agent (`internal/defaults/defaults.go:1-2`). The ungrouped area is a group of its own under the key `__ungrouped__` (`internal/model/model.go:19-22`). Stored in `state.json` in the data folder, as `State.Defaults` (`internal/model/model.go:71`, `internal/store/store.go:56,77,86-88`). There is **no agent** in the chat defaults (only in `run.agent`) and nothing per server.

**Resolution order** (`defaults.Resolve`, `internal/defaults/defaults.go:18-50`):

- folder: the group's `cwd` → `last.cwd` → the server's default folder (`-cwd` flag, `cmd/ai-whiteboard/main.go:162`); if the result does not exist on disk, the server's default folder (lines 21-24);
- model and effort: the group's `byAgent[agent]` if it has a model → `last.byAgent[agent]` if it has a model → the catalog's default (lines 27-33); then, if the model is not in the catalog, the catalog's default, and if the effort is not one the model has, the model's default effort or none (lines 35-48).

## S5. "Last used" and what removing it touches

`Defaults.Last` is written in two places and read in four. Removing it changes: the fallback for a group that has no value of its own, what a new top-level group is seeded with, and where a group's first run takes its agent and settings from.

| # | Use of `last` | `path:line` | Behaviour today | Under "a new group gets its defaults from the ungrouped group" (fact about what the code would have to do, not a design) |
|---|---|---|---|---|
| 1 | write | `internal/defaults/defaults.go:62` | every recorded change also goes to `last` | the write goes away |
| 2 | write | `internal/runs/service.go:895` | a run's start sets `last.run` | the write goes away |
| 3 | read, folder fallback | `internal/defaults/defaults.go:21` | group has no folder → `last.cwd` → server default | the middle step has to become something else or nothing |
| 4 | read, model fallback | `internal/defaults/defaults.go:29-30` | group has no model for this agent → `last.byAgent[agent]` → catalog default | same |
| 5 | read, seeding | `internal/defaults/defaults.go:72` | new top-level group = copy of `last` | copy of `groups["__ungrouped__"]` |
| 6 | read, run defaults | `internal/runs/tiers.go:90-92` | group has no `run` → `last.run` | `SeedGroup` does not copy `run` today, so either it starts to, or this fallback reads the ungrouped group |
| 7 | copy for clients | `internal/app/app.go:102` | sent in the snapshot and `defaults` events | field disappears from the wire |
| 8 | TypeScript | `web/src/types.ts:59`, `web/src/store.ts:83,133` | typed and initialised, never read | type and initialiser change only |
| 9 | e2e | `web/e2e/app.e2e.mjs:2283,2302` | asserts `defaults.last.byAgent.claude` is Haiku after a pick | must assert the group's value instead |

Rows 3 and 4 matter more than they look: seeding is a one-time copy, so a group seeded when the source had no value for an agent (for example pi never used yet) gets that agent's model from `last` **later, at resolve time**. Without `last`, such a group falls straight to the catalog default unless another fallback is put in its place (**inferred** from `Resolve` and `SeedGroup`; `TestRecordChangeEmptyFieldsLeftAlone`, `internal/defaults/defaults_test.go:83-97`, pins today's behaviour). The same holds for groups that exist before an upgrade and have an empty or partial entry.

A seeded copy is not a link: a later change in the source does not reach the group (`TestSeedSubgroupFromParent`, `internal/defaults/defaults_test.go:124-127`). Under the new rule a top-level group would copy the ungrouped group's values as they are at that moment; a subgroup still copies its parent (`internal/defaults/defaults.go:73-75`).

**Existing stored state.** `state.json` holds `"defaults": {"last": {...}, "groups": {...}}` and `"version": 1`; the store has no migration step and no strict decoding (`internal/store/store.go:63-88`; a search for `DisallowUnknownFields` finds none). So if the `Last` field is removed from the Go struct, an old file loads, the `last` object is ignored, and it disappears at the next write (**inferred** from Go's `encoding/json` behaviour). The values in it are lost unless something copies them first, for example into the ungrouped group where that group has none.

**The default agent today.** There is no stored default agent for a chat: the user always names one, except at the empty-state button, which hard-codes `"claude"` (`web/src/App.tsx:182`). A new run starts as `model.Claude` unless the group's (else `last`'s) run record names another known agent (`internal/runs/service.go:491,499-504`). A subagent's default is its parent chat's agent. `defaults.AgentOrder` (Claude, Cursor, pi) has no user in Go outside its test (search of `internal` and `cmd`); the client has its own copy, `AGENT_ORDER` (`web/src/types.ts:13`), which orders the menus. So "agent as a sticky default" has no chat field to extend: `GroupDefaults` has `byAgent` (keyed by agent) and `run.agent`, and nothing that says which agent a new chat takes.

## S6. Runs, as the comparison case

A draft run is created with no choice at all and is then configured in its own composer until the start: this is the pattern the chat redesign asks for, already built once.

- **Create**: `POST /api/runs {group, name?}` (`internal/server/server.go:849`, `web/src/api.ts:86`); the "+" offers "New run" with no agent list (`web/src/Sidebar.tsx:257,501`, `web/src/App.tsx:184`). `Service.Create` picks the agent (Claude, or the last started run's kind), the settings, the folder via `defaults.Resolve`, and the three tiers' models (`internal/runs/service.go:480-526`).
- **Change until the start**: `PATCH /api/runs/{id} {agent?, tiers?, cwd?, settings?}` (`internal/server/server.go:863`, `web/src/api.ts:93-94`). A started run answers `ErrStarted` (409) (`internal/runs/service.go:685-686`).
- **Changing the agent re-resolves what depends on it**: `m.Agent = *p.Agent`, then `m.Tiers = s.svcNewTiers(m.Group, m.Agent, rd)`: the new agent's defaults in all three tiers (`internal/runs/service.go:691-698`). The folder is kept. The answer is the whole view, and the client shows what the server chose (`web/src/run/RunComposer.tsx:155-161`).
- **The form**: `RunToolbar` has an Agent `Picker` over `AGENT_ORDER` with glyphs, the same `DirPicker` as the chat, and the tier pickers, each with the hint "until start"; "Loading models…" while the agent's catalog is missing (`web/src/run/RunComposer.tsx:162-172`). `Picker`'s own comment says it is shared with the run composer "also for the agent" (`web/src/Composer.tsx:460-463`).
- **Lock**: the start sets `Started` (`internal/runs/service.go:876-879`); "a run has started exactly when it is set" (`internal/model/run.go:192-193`).
- **Recording**: only at the start, into the group and `last` (`internal/runs/service.go:883-898`); changes made to a draft are not recorded. A chat differs: each composer change is recorded at once (`internal/chats/manager.go:1401-1403`).
- **Default agent**: sticky per group through `GroupDefaults.run.agent` (`internal/runs/service.go:502-504`), which is the only sticky agent that exists today.

Same pattern as the chat redesign: an object that exists before its agent is final; an agent picker in the composer; server-side re-resolution of models on agent change; one `PATCH`; a single moment that locks everything. Different: a run records its defaults once at the start, has three models, not one, and its lock is `Started`, not `Locked`.

## S7. Where a "server" choice would sit next to these

Nothing in the defaults or in the composer is per server today: `Defaults`, `GroupDefaults`, `ChatMeta`, `ChatView` and `ConfigReq` have no server field (`internal/model/model.go:108-117,196-250,334-346`, `internal/chats/manager.go:200-202`), and the client has one store filled from one snapshot (`web/src/store.ts:117-133`).

## Implications (opinion)

- **Keep the agent always set; make it changeable until the first message.** Creating a chat with a default agent and adding `agent` to `PATCH /api/chats/{id}` for an unlocked chat is a small change that mirrors `runs.Service.Patch`: set the agent, re-resolve model and effort with `defaults.Resolve` for the new agent, set or clear the session id, emit the view. An agent-less chat would touch every reader of `c.agent` on both sides for no gain.
- **The sticky agent needs one new field**, for example `GroupDefaults.agent`, recorded where the folder is recorded (on change and on the first send). Until one is recorded the fallback has to be a constant; Claude is what the empty state and the run service already use.
- **Replace `last` with the ungrouped group in all four read sites, not only in `SeedGroup`.** If only the seeding changes, an empty or partial group entry falls to the catalog default where it used to fall to the last choice, which users would see as "the group forgot". The simplest rule that keeps today's feel: group value → ungrouped group's value → catalog/server default. `SeedGroup` should then also copy `run`, or `svcRunDefaults` should fall back to the ungrouped group.
- **Migrate once at load**: where the ungrouped group lacks a folder, a per-agent model or a run record, copy it from the stored `last`, then drop `last`. Without this, an upgrade silently loses the values that new groups have been taking.
- **The server choice is the outermost one.** Folder, catalogs, efforts, defaults and groups are all facts of one server, so the order in the composer is server → agent → folder/model/effort, and a server change in an unstarted chat is better treated as "ask the new server for a fresh unstarted chat" than as a patch of the old one. The stored defaults cannot be shared across servers as they are, because the folders in them are paths on one machine.
- **The client can stay thin.** It reads no defaults today; every default arrives inside the view the server answers with. Keeping it so means the new pickers need only the catalogs (already per agent) and, per server, a list of which agents are usable, which no server reports today.
- **Test cost is concentrated in two places**: the `Last` assertions in about a dozen Go tests (mechanical), and `newChatVia` in the e2e suite (one helper, thirteen call sites).
