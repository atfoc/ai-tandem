**completed**: I ran X1–X6 with the real built client in separate headless Chromes against a scratch server, and the hand-over is not safe for board or draft data. "Use here" brings a page back with its old cached scenes and drafts, so the next user edit, agent tool call, or in two cases no action at all, writes them over the other page's work; a page whose connection was cut even takes the role back by itself and does the same. Reloading the page is the only verified safe way back; thread content was not covered because sending messages was forbidden.

# T11: two pages on one server — what is lost or overwritten at take-over and take-back

## Result in short

- **A friendly take-over is safe.** The page being replaced writes its pending board saves before it releases, even for an edit younger than the 500 ms save delay. [V]
- **Taking back with "Use here" is not safe.** The page comes back with every scene it loaded earlier, never re-reads them, and writes them whole over the other page's work. [V]
- **Two overwrites need no user action on the returning page**: a save that was refused during the take-over, and a board the page had edited off screen for an agent. [V]
- **A page whose connection was cut takes the role back by itself** when the network returns, with its old scenes, and kicks the other page out. [V]
- **Reloading the page is the only way back that kept everything on disk** in the runs. [V]
- **Drafts behave like scenes**: the returning page shows its own old draft and writes it over the other page's at the next keystroke. [V]

Marks: **[V]** verified by a run, **[I]** inferred from code, **[U]** unknown.

## Set-up used

- Scratch directory `/tmp/aiwb-t11.p0pnNT` (removed at the end).
- Build: `npm ci && npm run build` in `web/`, then `go build -o <tmp>/ai-whiteboard ./cmd/ai-whiteboard`.
- Server, exactly in the brief's form: `CURSOR_CONFIG_DIR=<tmp>/cursor-config AIWB_MCP_PORT=42001 <tmp>/ai-whiteboard serve -port 42000 -home <tmp>/home -client <worktree>/web/dist -cwd <tmp>/cwd -claude /nonexistent/claude -cursor /nonexistent/agent -cursor-cost /nonexistent/cursor-cost -pi /nonexistent/pi`.
- Ports: 42000 (app), 42001 (MCP), 42010–42012 and 42019 (Chrome debugging), 42020 (a TCP forwarder of my own). Each was checked free with `lsof` first.
- Pages: Google Chrome 154 headless, each "machine" its own Chrome with its own `--user-data-dir`, all loading `http://127.0.0.1:42000/`. Where shared storage could matter I repeated the run with two tabs of one Chrome.
- Driver: `cdp.mjs` copied from `/tmp/aiwb-t04` and extended in my directory. Each page had an init script that logged every `EventSource` message and every non-GET request with its status.
- User-style edits: real pointer input through Chrome (key `r`, then a drag on the canvas).
- Agent-style edits: JSON-RPC `tools/call` (`apply`, `read_board`) to `http://127.0.0.1:42001/mcp` with the board chat's token from `chat.json`. No agent CLI ran and no message was sent.
- Truth: the file `<home>/boards/<id>/drawing.excalidraw` and `GET /api/boards/{id}/scene`. They agreed at every step.
- Canvas state: the live Excalidraw instance's element list, plus screenshots.
- A cut connection: page A reached the server through the forwarder (`--host-resolver-rules=MAP 127.0.0.1:42000 127.0.0.1:42020`), which I killed or froze.
- Each experiment started from a wiped scratch server with fresh boards, each seeded with elements `a` and `b`.

| 14 | Tool call `apply d` through A | X2 **`a b d`** (`c`, `e` gone) | `a b d` | – |

Conclusions:

- **"Use here" never re-reads a scene.** A shows and holds whatever it loaded before. Nothing on screen says the board is old. [V]
- **The next save writes the old scene whole.** This holds for a user edit and for an agent tool call, and for a board on screen or one only loaded earlier. [V]
- **An agent reads the old board too.** `read_board` through the returning page answered the stale content, so the agent plans on a board that no longer exists. [V]
- **A board the page never loaded is safe.** It is fetched fresh. [V]
- **New path: no edit needed.** A board the page changed off screen for an agent before the take-over is saved 0.5 s after it is merely opened. Seen twice (step 9d, and B's own copy of X2 at step 12). [V] The likely cause is that Excalidraw normalises tool-made elements when it mounts, which changes the scene version that `sceneChanged` compares (`web/src/board.ts:50-60`, `207-213`). [I]
- **Both pages end up stale.** After A's take-back, B's cache is old as well, so every further "Use here" in either direction can overwrite. [V]

Code that explains it:

- `web/src/board.ts:20`, `28-30`: the scene cache, and `loadScene` returning the cached scene.
- `web/src/board.ts:64-69`: `forgetBoard` is the only place an entry is removed; its only callers are `web/src/store.ts:121` and `133`. Nothing clears the cache on `superseded`, on "Use here" or on a snapshot (grep confirmed).
- `web/src/conn.ts:69`: `takeBack` is only `connect()`.
- `web/src/board.ts:88-108`: `runSave` sends the whole scene.
- `internal/boards/boards.go:194`: `Save` overwrites with no revision check.

## X3. Unsaved work at the moment of take-over

### (a) Friendly: B connects inside the 500 ms save delay — safe [V]

- B clicked "Use here" 2 ms after A's drawing ended.
- A's log: `release_request` → `PUT …/scene` 200 → `POST release` 200 → `superseded`. The whole hand-over took 13 ms.
- Disk: F1 `a b rA`. A afterwards: `hasPendingSaves` false, `window.aiwbFlush()` true.
- Code: `web/src/conn.ts:34`, `web/src/board.ts:111-119`.

### (b) Unfriendly: A cannot answer for more than 3 s — B's work is overwritten at take-back with no action [V]

Run twice: A's Chrome frozen with `SIGSTOP` for 5.1 s, and A's connection stalled for 5.0 s (forwarder frozen). The results were the same.

| # | Step | Disk | Page A | Page B |
|---|---|---|---|---|
| 1 | A draws `rA` on U1 and is frozen at once | `a b` | frozen, edit unsaved | clicks "Use here": `hello waiting` |
| 2 | 3.0 s later | `a b` | frozen | `hello active`, promoted by the timer |
| 3 | B opens U1, a tool call adds `c` | `a b c` | frozen | canvas `a b c` |
| 4 | A wakes | `a b c` | `PUT …/scene` → **409**; `release_request`, `superseded`; `POST release` → 409; take-over screen | unchanged |
| 5 | A while superseded | `a b c` | `hasPendingSaves` **true**; `aiwbFlush()` **false** (each call sends the PUT again, 409) | – |
| 6 | A clicks "Use here", nothing else | **`a b rA`** (`c` gone) | at `hello waiting` A sends `PUT …/scene`; 1 ms later it is active; the PUT gets **200**; canvas `a b rA` | released, take-over screen |

- **Why step 6 writes at once.** While the role is `waiting` the app shows only the waiting screen (`web/src/App.tsx:28`), so the canvas unmounts and its cleanup calls `flush(board)` (`web/src/Canvas.tsx:52`), which re-sends a failed save (`web/src/board.ts:116`). B releases within milliseconds, so the request is accepted.
- **Seen in 3 of 3 runs.** [V]
- **If B released slowly** the PUT would get 409 and stay "failed" until the next trigger: opening another board (`web/src/Sidebar.tsx:27`), the window being hidden (`web/src/main.tsx:12`), any edit, or the next `release_request`. [I]

### (c) A superseded with a refused save, then A reloads [V]

- The reload raised the browser's `beforeunload` prompt (`web/src/main.tsx:14`).
- After accepting it A showed `a b c`. A's own rectangle was lost; B's work was kept.

### What the desktop app would be told

- **Superseded, nothing pending:** `hasPendingSaves` false, `aiwbFlush()` true. [V]
- **Superseded with a refused save:** `hasPendingSaves` true, `aiwbFlush()` false within milliseconds. [V]
- **The dialog this leads to:** closing that window would show "Board changes are not saved. The server did not answer. Close anyway and lose them?" (`desktop/lib.js:328-380`). That text is wrong for this case: the server answered 409. [I] I did not run the desktop app.

## X4. Chats across a hand-over

| # | Step | Server | Page A |
|---|---|---|---|
| 1 | A has P1 open with a saved draft; P5 has a saved draft, not on screen | P1 "P1 draft typed in A", P5 "P5 draft typed in A" | composer shows its P1 draft |
| 2 | B takes over, opens P1 (sees A's draft), replaces the drafts of P1 and P5, makes a chat and a board, renames chat P2 and board K1, archives board K2 | all of B's changes | take-over screen |
| 3 | A clicks "Use here", types nothing | unchanged | sidebar shows **all of B's changes**; composer on P1 shows **A's old draft** |
| 4 | A types one character in P1 | P1 draft = A's old text plus the character; **B's draft gone** | – |
| 5 | A opens P5 | unchanged | composer shows **B's draft** |
| 6 | A types in Q1; B takes over 7 ms later | Q1 has no draft; A's `PUT …/draft` → 409 | text kept in `localStorage` `aiwb.draft.<chat>` |
| 7 | B opens Q1 (empty composer), writes its own draft | Q1 "Q1 written in B" | – |
| 8 | A clicks "Use here", types nothing | still "Q1 written in B" | composer shows A's unsaved text; the `localStorage` copy is **deleted** |

| 9 | Two tabs of one Chrome: tab1 types, tab2 takes over, tab2 opens the chat | the draft is saved by tab2 | tab2's composer shows tab1's unsaved text |

Conclusions:

- **Boards, chats, names, new and archived items** come from the snapshot and are shown correctly after "Use here". Nothing of A's overwrote them. [V]
- **The draft of the chat on screen at the take-over** stays A's old one after "Use here". The next keystroke saves it over B's. [V] The composer is rebuilt before the snapshot arrives, and later drafts from the server are deliberately not put in (`web/src/Composer.tsx:73`, `110`, `152-158`).
- **A chat not on screen** shows B's draft. [V]
- **A draft younger than 400 ms at take-over is not on the server.** `release_request` flushes boards only (`web/src/conn.ts:34`); the composer's own save runs after `superseded` and is refused. [V]
- **That unsaved text is then silently lost.** After "Use here" A shows it but drops its safety copy, because `saveDraft` put the text into the store before the request failed (`web/src/Composer.tsx:68`; `web/src/logic/drafts.ts:53-55`). A reload or a chat switch without typing loses it; typing overwrites B's draft. [V]
- **With shared `localStorage`** (two windows of one app) the unsaved draft crosses over to the other window and is saved there. [V]
- **Not covered:** thread content, a running turn, permission cards and branch moves across a hand-over, because sending a message was forbidden. I saw only that after every take-back the page asks for the open chat's items again (`GET …/items` 200, `web/src/conn.ts:52-55`). [V for the request, U for the rest]

## X5. Ping-pong

| Situation | What page A did | Mark |
|---|---|---|
| After `superseded`, 25 s, no click | stayed on the take-over screen; one `EventSource` made, `readyState` 2 (closed) | [V] |
| B reloaded its page | B became active at once (`hello active`, no wait); A unchanged | [V] |
| B's Chrome closed, 26 s | A unchanged; a board tool call failed at once with "The board isn't open: the AI Whiteboard window is closed…" | [V] |
| A clicks "Use here" with no other client | active at once (`hello active`); tool calls work again | [V] |
| **A's connection is cut while A is active** (forwarder killed; A never receives `superseded`) | see below | [V] |

- **A superseded page never reconnects by itself.** It closes its stream (`web/src/conn.ts:35`). After the other page closes, the server has no page until someone clicks "Use here" or reloads; agents' board calls fail meanwhile. [V]
- **A page that lost its connection without being told does reconnect by itself.** `EventSource` retries every 3 s with the same client id (`web/src/conn.ts:21`). If another page became active meanwhile, the server treats the returning stream as a new take-over (`internal/editorbridge/bridge.go:103-115`).

The cut-connection runs:

| # | Step | Disk | Page A | Page B |
|---|---|---|---|---|
| 1 | A active on H1; its connection is cut | `a b` | "Reconnecting…", canvas still shown | – |
| 2 | B opens the page, a tool call adds `c` | `a b c` | still retrying | active at once |
| 3 | A's network returns, nobody clicks | `a b c` | 3 s later: `hello waiting` → `hello active`; canvas `a b` | `release_request` → `superseded`; take-over screen |
| 4 | Tool call `apply d` | **`a b d`** (`c` gone) | applied it on its old scene | – |

Variant with an edit made while cut off (J1):

- A drew `rA` while "Reconnecting…"; its save failed with a network error.
- B opened the page and a tool call added `c`. Disk: `a b c`.
- A's network returned. With nobody touching A: `hello waiting` → `PUT …/scene` 200. Disk: **`a b rA`**. B was on the take-over screen.

So two desktop shells that each keep a page loaded for the same server already fight over it today whenever one of them loses and regains its connection. [V with a killed forwarder; I for a real laptop sleep or Wi-Fi change]

## X6. What the superseded page can still do [V]

Nothing. While superseded the app renders only the take-over screen (`web/src/App.tsx:27`). The DOM held 0 canvases, 0 editable elements and one button ("Use here"). A pointer drag, typed text and key presses changed nothing and sent no request. The scenes stay in the page's memory, which is what makes "Use here" unsafe. Reads still work if something makes them (`GET /api/state` and `GET …/scene` answered 200), but the page makes none by itself. Any write gets 409 `not_active` (`internal/server/guard.go:32-35`). Tool calls go to the active page only. A page that is merely disconnected is different: its canvas stays fully editable under "Reconnecting…", and those edits are held as a failed save (see X5).

## Data-loss paths found

| # | How to reach it | How likely with two machines | What the user sees |
|---|---|---|---|
| 1 | A has a board loaded; B takes over and changes it; A clicks "Use here" and edits that board | High. It is the ordinary flow: the board both machines work on is the one on screen on both | After "Use here" B's elements are simply missing on A, with no notice; after the first stroke they are gone from disk |
| 2 | As 1, but an agent's board tool call arrives instead of a user edit, for any board A loaded earlier, on screen or not | High when agents run: no user action on A beyond "Use here" | Nothing. The agent also reads the old board and reports on it |
| 3 | A applied an agent edit to a board off screen; B changed the board; A takes back and merely opens it | Medium | B's elements vanish 0.5 s after opening, with no edit |
| 4 | A holds an unsaved edit and cannot answer for 3 s (frozen page, stalled link); B is promoted and works; A clicks "Use here" | Medium on remote links: any stall over 3 s during a take-over | B's work on that board is replaced by A's older scene the moment A comes back |
| 5 | A's connection is cut while active; B takes over; A's network returns | High for laptops: sleep, Wi-Fi change, VPN or tunnel drop | B is thrown to the take-over screen mid-work; then paths 2 and 4 run with nobody at A |
| 6 | A has a chat open with a draft; B changes the draft; A clicks "Use here" and types | Medium | A sees its old draft, never B's; one keystroke replaces B's |
| 7 | A typed within 400 ms before the take-over; B wrote another draft; A clicks "Use here", then reloads or switches chat | Low | A's own text disappears without notice |
| 8 | After any take-back the other page is stale as well, so paths 1–3 repeat in the other direction | High once two machines alternate | As 1–3 |

What a fix has to prevent, without designing it:

- A page that becomes active again must not show, hand to an agent, or write a scene or draft it loaded before another client was active.
- A save refused as `not_active` must not be written later over newer content without the user deciding.
- A whole-scene write based on an older scene than the one stored must not be accepted silently.
- A page that lost its stream must not take the server away from another client by itself.
- An unsaved draft copy must not be dropped while the server holds a different draft.
- A superseded window with a refused save must not be told "the server did not answer".

## Ways of coming back that are safe (verified runs only)

- **Reload the page** (X2a, X3c, X4 8b). The scene cache and composers start empty and everything is read from the server. The cost: an edit or draft the page could not save is lost, after a `beforeunload` prompt for boards and with no prompt for drafts.
- **Do not come back** (X2b, X6). A superseded page is inert and tool calls go to the active page.
- **"Use here" is safe only for boards this page load never loaded** (Z1, Z2) and chats not on screen at the take-over (P5). The user cannot know which those are.

Not safe: "Use here" in general, and the automatic reconnect of a page whose connection dropped.

## Unknowns that remain

- **Thread content across a hand-over**: messages, a running turn, permission cards, branch moves, subagent drawers. Not run, because sending was forbidden.
- **The Electron app itself**: its windows, its close dialog and its reload path. `desktop/main.js` was not run; the dialog in X3 is inferred from `desktop/lib.js` plus the page's measured answers.
- **A real sleep/wake or network change.** The cut was a killed local forwarder. Whether a sleeping laptop's page receives `superseded` on waking (as with `SIGSTOP`) or reconnects as a new take-over (as with the cut) depends on whether the TCP connection survives.
- **Why opening an off-screen-edited board triggers a save** (path 3). Observed twice; the cause is inferred.
- **Slow release in path 4.** In all runs B released within milliseconds; the later triggers are read from code only.
- **Not run:** three or more pages (a waiting client replaced by another, `internal/editorbridge/bridge.go:104-107`); a board deleted or archived by B while A holds it (`web/src/store.ts:121`); scenes with image files.
- **Hidden pages save later.** In the two-tab run a save after a tool call left 0.7 s later instead of 50 ms, which suggests timer throttling. One observation, not investigated.
