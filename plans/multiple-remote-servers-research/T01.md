### What would have to change for another machine to reach it

- **Direct reach:** the bind address (`main.go:125`) and the Host allowlist (`guard.go:26`) both have to change. Either one alone blocks it. [V]
- **Loopback-to-loopback forward (e.g. SSH `-L`):** the bind can stay. The Host header then becomes the blocker unless the client's local port equals the server's port. Observed:

```
Host: 127.0.0.1:58604              -> 200
Host: localhost:58604              -> 200
Host: 127.0.0.1:9999               -> 403 {"error":"bad host"}   (forward on another local port)
Host: localhost                    -> 403                        (no port)
Host: myserver.lan:58604           -> 403
Host: 192.168.1.20:58604           -> 403
Host: box.tailnet.ts.net           -> 403                        (HTTPS reverse proxy that keeps Host)
Host: LOCALHOST:58604              -> 403                        (exact, case-sensitive match)
Host: [::1]:58604                  -> 403
```

- So today a forward works unmodified only when the local port number equals the remote server's `-port`. Two remotes on the default 4747 cannot both be forwarded; the local server also uses 4747. [V for the 403s; I for the conclusion]
- The server serves plain HTTP. [V]

## 2. Request guarding and identity

### `internal/server/guard.go`, exactly

- `guard(b, port, next)` wraps the whole mux (`server.go:708`), so it covers static files and `/api/events` too. [V]
- **Step 1 — Host** (`guard.go:26-31`): `r.Host` must equal `127.0.0.1:<port>` or `localhost:<port>`, where `<port>` is `Server.Port`, the actually bound port (`main.go:129`, `191`). Otherwise `403 {"error":"bad host"}`. [V]
- **Step 2 — active client** (`guard.go:32-35`, `needsActive` at `41-52`): a request needs `X-AIWB-Client` equal to the active client's id when all of these hold:
  - the path is `/api` or starts with `/api/`;
  - the method is not GET or HEAD;
  - the path does not start with `/api/client/` and is not `/api/rpc-reply`.
  
  Otherwise `409 {"error":"not_active"}`. [V]
- **Exempt from the header rule:**
  - every GET and HEAD, including `GET /api/events`, `/api/state`, `/api/dirs`, `/api/usage/*`, scene and chat reads;
  - everything outside `/api` (static client files);
  - `POST /api/client/release`, `POST /api/client/flushed`, `POST /api/rpc-reply`. These check for themselves that the id is active or pending; the id comes from the body's `client` or the header (`server.go:138-145`, `218-258`; `guard.go:55-57`). [V]
- **MCP listener:** `MCPHandler` uses the same `guard` with the MCP port (`server.go:183-187`). Only the Host check applies there, because `/mcp` is outside `/api`. [V]

### What exists and what does not on `/api`

| Mechanism | Present? | Evidence |
|---|---|---|
| Authentication (token, password, cookie, session) | No. `X-AIWB-Client` is a self-chosen id, not a secret | grep for `Authorization\|Cookie` in `internal/server`: no hits. [V] |
| CORS handling | None. No `Access-Control-*` header anywhere | grep. A preflight gets 409: `OPTIONS /api/boards` → `409 {"error":"not_active"}`. [V] |
| Origin / Referer / Sec-Fetch check | None | grep. `GET /api/state` with `Origin: http://evil.example` → 200, full body, no ACAO header. [V] |
| TLS | None; plain `http.Serve` | `main.go:200`, `219`. [V] |
| Rate limiting, IP allowlist | None | [V by absence] |

- **The only credentials in the system** are the per-chat MCP bearer tokens. They are stored in `chat.json` (`internal/model/model.go:207`), used only on the MCP listener (`internal/boardapi/mcp.go:198-204`), and not present in `ChatView` (`model.go:274-303`). Observed: the token appears 0 times in `GET /api/state` and `GET /api/chats/{id}`. [V]
- The MCP handshake is permissive: `initialize` and `tools/list` answer without a valid token. A `tools/call` with a bad token returns tool text "unknown board token", not HTTP 401 (`mcp.go:231-247`, `277-281`). [V]

### Threat model the guard covers today

Stated in `guard.go:14-18`: "requests that could come from a web page other than the client".

- **DNS rebinding:** covered by the Host allowlist.
- **Cross-site request forgery from a browser page:** a mutation needs a custom header, which forces a preflight the server never approves.
- **Two tabs writing at once:** covered by the active-client rule, which is a concurrency rule.

It relies entirely on the loopback bind plus browser same-origin rules. Any local process can already do anything. [V for code; the framing is my reading]

### What is uncovered once the listener is reachable

- **Everything, if the Host check is relaxed or satisfied.** An attacker who can send a request with an accepted Host can:
  1. read all state, boards, transcripts and the server's folder tree — every GET is open (observed: `GET /api/state`, `/api/chats/{id}/items`, `/api/boards/{id}/scene`, `/api/dirs?path=/` all 200 with no header and no client connected) [V];
  2. become the active client by opening `GET /api/events?client=<anything>`. Observed: a second client becomes active after 3 s without the first one's consent. [V]
  3. then create chats and send messages, which runs agents as the server's OS user in any folder on that machine. Claude runs with `--permission-mode auto` (`internal/claude/claude.go:95`). pi tool calls are auto-approved (README; `internal/pi/args.go:34`). The permission card itself is answered by the active client via `POST /api/chats/{id}/permission`. That is remote code execution. [V for the pieces; I for the chain end-to-end, since I did not run a real agent]
- **Through a tunnel that presents a different Host or port:** the guard fails closed, 403 on every request including static files. [V]
- **Through a tunnel that presents the right Host:** the guard gives no protection. Whoever can reach the tunnel's local end is fully trusted — on a multi-user client machine, any local user or process. [I]
- **Plain HTTP:** over a non-loopback path, traffic (board content, transcripts, prompts) is readable and modifiable in transit. [V it is plain HTTP]
- **A side effect that exists already [I]:** `/api/events` is a GET with no Origin check, so any web page in the user's browser can request `http://127.0.0.1:4747/api/events?client=x`. The server then registers a pending client and sends `release_request` to the active one (`bridge.go:103-114`). The page cannot read the stream, but the takeover is triggered. I did not test this in a browser, and Private Network Access rules may block it.

## 3. The active-client model (`internal/editorbridge/bridge.go`)

### How the one active client is decided

- **Connect:** `GET /api/events?client=<id>` (`bridge.go:78-83`). The id is chosen by the client; a missing id gets 400. [V]
- **No active client** → the newcomer becomes active and gets `hello{active:true}` plus a `snapshot` event carrying the whole `app.Snapshot` (`bridge.go:95-97`, `305-322`). [V]
- **Same id reconnects** → the old stream is closed, the new one is active, and it gets a fresh snapshot (`bridge.go:98-102`). [V]
- **A different id connects** → take-over (`bridge.go:103-115`):
  - the newcomer becomes `pending` and gets `hello{active:false, waiting:true}`;
  - the active client gets `release_request`;
  - a 3 s timer starts (`handoverDelay`, `bridge.go:24`);
  - an earlier pending client gets `superseded` and is closed. [V]
- **Promotion** (`bridge.go:286-302`) happens when the active client POSTs `/api/client/release` (`bridge.go:167-173`), when the timer fires, or when the active client's stream ends while one is pending (`bridge.go:121-126`). The old client gets `superseded`, its in-flight RPCs fail with `ErrNoClient`, and its stream is closed. The new one gets `hello{active:true}` plus a snapshot. [V]
- **`server_stopping`** (`bridge.go:247-266`): on SIGINT/SIGTERM the server sends it to the active client and waits up to 2 s (`main.go:209`) for `POST /api/client/flushed`. [V]
- **`Broadcast` sends to the active client only** (`bridge.go:190-200`). If its 4096-message buffer is full, the stream is closed so the client reconnects and gets a new snapshot (`bridge.go:334-343`). An idle stream gets a `: ping` comment every 20 s (`bridge.go:27`, `158-160`). [V]

Observed timeline (client A never releases, B connects at 0.52 s):

```
0.52s B <- hello{active:false, waiting:true}      A <- release_request
1.02s POST /api/boards as A -> 200                POST as B -> 409 not_active
3.52s A <- superseded, A's stream ends            B <- hello{active:true}, snapshot
4.23s POST as A -> 409 not_active                 POST as B -> 200
```

### The RPC that sends agents' board edits through the open window

- Path: an agent's MCP `tools/call` → `Relay.dispatch` → `Relay.Call` (`internal/boardapi/mcp.go:46-76`, `277-302`) → `Bridge.Call("tool", {chat, board, name, args}, 30s)` (`bridge.go:204-233`). The active client gets an SSE event `{type:"rpc", id, method:"tool", params}` and answers with `POST /api/rpc-reply {id, client, result|error}` (`server.go:243-258`). [V]
- Observed: with client B active, `list_boards` over MCP produced `rpc_1` on B's stream. A reply posted as A got 409; B's reply was returned verbatim to the MCP caller. [V]
- **All seven board tools go this way**, including the read-only `list_boards`, `read_board` and `get_view` — `Relay.Call` has no server-side branch (`mcp.go:58-65`). The spawn family (`spawn_subagent`, `stop_subagent`, `list_subagent_models`) is handled in the server and needs no client (`mcp.go:289-294`, `306-332`). [V]
- If the client does not answer within 30 s: "the board did not answer tool in 30s" (`bridge.go:230-231`; `mcp.go:27`). [V in code]

### When no client is connected

This is the state of a remote server whose window the user has switched away from, if switching closes the event stream.

- **Board tool calls fail at once** with `ErrNoClient`. Observed over MCP with a valid token and no client:
  > "The board isn't open: the AI Whiteboard window is closed. Board work needs the window open. Tell the user, and don't retry until they ask again." (`isError: true`; `mcp.go:30-31`, `66-68`). [V]
  
  The text tells the agent not to retry, so a turn that needed the board ends without doing the board work. [V text; I for agent behaviour]
- **Running chats keep running.** The chat manager only calls `Bridge.Broadcast`, which is a no-op without an active client (`internal/chats/manager.go:133-142`, `1305`; `bridge.go:197`). Agent processes are children of the server, not of a client. Items are kept in `items.jsonl` per chat (`internal/transcript/transcript.go:1-2`). [V for code paths; I that a real turn completes, since no real agent was run]
- **Events during that time are not queued.** A client that connects later gets the snapshot, then reads threads with `GET /api/chats/{id}/items`, which carries a `version` (`server.go:479-492`). [V]
- **Mutations are impossible.** `POST /api/chats/{id}/messages` with no client → `409 not_active` (observed). So are permission answers and interrupts. A permission card raised while no client is connected waits; I found no timeout for it in `internal/chats`. [V for 409; I/U for "waits forever" — I did not trace the per-agent permission timeouts]
- Plain (non-board) chats are unaffected apart from having nobody to answer permission cards. [I]

### When two clients connect

Example: a desktop app on a laptop and a browser tab on the server machine.

- The later one wins after at most 3 s. The earlier one gets `superseded`, its stream closes, and its in-flight board RPCs fail (`bridge.go:294-298`). [V]
- If the earlier client then reconnects with its own id, it is a "different id" again and takes over in turn. Two clients that both auto-reconnect would alternate every 3 s or so. Whether the web client reconnects after `superseded` is the web task's question. [I for the ping-pong; V for the server rule]
- There is no notion of a read-only observer. A non-active client can issue GETs but receives no events. [V]
- An agent's board edits are applied by whichever machine holds the active window. Unsaved board changes of the superseded client depend on it handling `release_request` within 3 s. [V for the server side]

### B. Work, but act on the server machine in a way a remote user must understand

- **`PATCH /api/chats/{id}` with `Cwd`** (`server.go:604-637`): the path is resolved and `os.Stat`-ed on the server machine; `~` is the server user's home (`internal/chats/manager.go:929-939`, `1020-1034`). Paths inside the data folder are refused (`manager.go:935`). Correct for a remote server, but the paths are the remote machine's. [V]
- **`GET /api/dirs?path=`** (`server.go:669-688`): lists the subfolders of any folder on the server machine; the default is the server's `DefaultCwd`. It is the folder picker and is needed for remote use. It is also an unauthenticated directory enumerator (observed: `?path=/` lists the root with no header). [V]
- **`GET /api/usage/{agent}`** (`server.go:691-703`): runs `claude -p /usage` (`internal/claude/usage.go:30-41`) or the `cursor-cost` binary (`internal/cursor/cost.go:56-61`) on the server machine. It reports that machine's logins and plans, cached for 1 minute (`main.go:192-193`). pi gets 404. Meaningful per server, since each remote has its own logins. A GET, so open, and it spawns a process. [V]
- **`POST /api/chats/{id}/messages`** and the other chat routes: agents run with the server user's credentials, PATH and files. [V]

### C. Meaningless or misleading from a remote client

- **`POST /api/boards/{id}/reveal`** (`server.go:441-447`): runs `open -R <board file>` on the server machine (`internal/boards/boards.go:286-291`). It opens Finder there, not for the remote user. `open -R` is a macOS command; on a Linux server it would fail and return 500. [V for code; I for the Linux outcome]
- **`POST /api/restart`** (`server.go:200-216`): starts `<server binary> relaunch <the original serve args>` detached on the server machine (`launch.go:154-168`; `main.go:196`). It works remotely as "restart that server from the binary on its disk" [I; verified locally by `TestRestartEndpoint`]. Caveats:
  - the client's connection drops and must come back through the same transport;
  - it restarts the server binary on the remote, not the desktop app, so a "version mismatch → restart" prompt means something different for a remote;
  - it returns 409 `binary_missing` if the binary was moved.
- **`GET /api/mcp/status`** (`server.go:264-277`): reports `{"port":6006,"url":"http://localhost:6006/mcp","up":…}` plus the last MCP contact per chat. The URL is the server machine's loopback; shown to a remote user it reads as if it were their own machine. No secrets (pinned by `TestMCPStatusRoute`). [V]
- **`GET /api/state` fields `home`, `defaultCwd`, `dataDir`** (`app.go:38-40`, `57-59`): absolute paths on the server machine. Observed: `"home":"/Users/pedjat","defaultCwd":"/Users/pedjat","dataDir":"/tmp/aiwb-t01-home…"`. Each chat's `cwd` and the per-group default `cwd` are server paths too. Any client feature that hands these to the local OS (open in Finder, open the log, shorten the home prefix) would use the wrong machine's paths. [V for the data; the client's use of it is the siblings' question]
- **Server log:** no route serves it. It is a file on the server machine (section 5). [V]

### D. Dangerous if reachable without authentication

- `GET /api/events` — take-over of the session by anyone; the precondition for every write.
- `POST /api/chats` + `POST /api/chats/{id}/messages` + `POST /api/chats/{id}/permission` + `PATCH /api/chats/{id}` (cwd) — command execution as the server user.
- `POST /api/restart` — restart on demand, ending running agents.
- `DELETE /api/boards/{id}`, `/chats/{id}`, `/groups/{id}?contents=delete` — data loss.
- `PUT /api/boards/{id}/scene` — overwrite boards.
- All GETs — disclosure of boards, transcripts, folder structure, plan usage, and running agent subprocesses for `/usage`.
- `POST /api/boards/{id}/reveal` — spawns a process on the server.
- The MCP listener, if it were ever exposed: the handshake is permissive, and `tools/call` is gated only by a chat token that never leaves the server machine.

## 5. Lifecycle

### Commands

Dispatch is in `main.go:60-84`; no command means `serve`.

**`serve`** (`main.go:116-220`), in the foreground:
1. If `findRunning` finds a server, print "AI Whiteboard is already running at <url>" and exit 0 (`main.go:120-123`; observed).
2. Bind the HTTP port, then the MCP port.
3. Open the store; load boards and chats.
4. Write the pi extension to `<home>/pi-extension` and start the UDS bridge.
5. Start the model-catalog probes for the three agents in the background (`main.go:182-184`).
6. Write `server.json`.
7. Serve.

On SIGINT/SIGTERM: flush the client (2 s) → `cm.Shutdown()` → `agent.EndAll(2s)` → close the pi bridge → remove `server.json` → exit 0 (`main.go:208-215`). [V]

**`launch`** (`launch.go:48-89`):
1. `findRunning` → print the URL and return.
2. Otherwise set PATH from the login shell: `$SHELL -ilc …`, 5 s timeout (`launch.go:55`, `201-237`).
3. Start `<own exe> serve <same args>` detached (`launch.go:95-117`): `Setsid: true`, working folder the user's home, stdout and stderr appended to `<home>/server.log` (mode 0600) after a `--- <RFC3339> launch` line.
4. Poll `findRunning` every 100 ms for up to 30 s.
5. Print **exactly one line on stdout: the URL `http://127.0.0.1:<port>/`**.

Errors go to stderr as `AI Whiteboard: <title>\n<detail>` with exit 1 (`launch.go:253-256`). [V]

Observed:

```
$ ai-whiteboard launch -home $H -port 58604 …
http://127.0.0.1:58604/
ps: PID 74977  PPID 1   ai-whiteboard serve -home … -port 58604 …   (cwd /Users/pedjat)
```

**`relaunch`** (`launch.go:122-127`): if a server is found, `stopServer` sends SIGTERM to the pid from `/api/hello` and waits up to 10 s; then it does `launch`. It prints only the URL. [V]

## 9. Must stay unchanged

1. **The exact MCP URL `http://localhost:6006/mcp`** for every agent: no query, no extra path, no trailing slash, no `127.0.0.1`. The fixed port is not user-configurable (`endpoint.go:5-11`; README; `TestMCPURLEndpoint` and the per-spawner pins). The MCP listener stays loopback-only with its own Host check.
2. **DNS-rebinding and CSRF protection for local use:** the Host allowlist for `127.0.0.1:<port>` and `localhost:<port>`, the custom-header rule on mutations, and no CORS approval for foreign origins (`TestBadHostIsForbidden`, `TestMutationsNeedTheActiveClient`).
3. **One instance per machine and per data folder:** `serve` and `launch` find the running server instead of starting a second one; a 6006 conflict fails fast, writes no `server.json`, and leaves the running instance alone (`TestLaunchRace`, `TestMCPPortConflictFailsFast`).
4. **`launch` prints exactly one line, the URL, on stdout.** The Electron app and scripts parse it (`launch.go:44-47`; `TestLaunchPrintsRunningServerURL`). `relaunch` does the same.
5. **Quitting the app does not stop the server or its chats.** The server is detached and ends only on SIGTERM/SIGINT, flushing boards, writing history and ending agents (`main.go:208-215`; README).
6. **`launch` never replaces a running server of another version.** The page offers the restart (`TestLaunchKeepsServerOfAnotherVersion`; `/api/restart` + `relaunch`).
7. **One active client per server,** with take-over, the `release_request` → `release` handover, `superseded`, `server_stopping` → `flushed`, and board edits going through the active window (all of `bridge_test.go`).
8. **Chat tokens never leave the server machine through `/api`.** `ChatView` has no token; `/api/mcp/status` exposes none (`TestMCPStatusRoute`).
9. **The local default experience:** `./bin/ai-whiteboard`, then open `http://127.0.0.1:4747`, with no setup, no password, data in `~/.ai-whiteboard` (README "Getting started").
10. **The hello contract `app == "ai-whiteboard"`, `version`, `webVersion`, `pid`.** It is used by `findRunning`, `relaunch` and the page's version banner. Fields may be added; these may not change.
11. **Agents cannot touch the data folder** (`TouchesAppDir`, the Claude disallowed rules, the Cursor deny rules). A chat's cwd cannot be inside it (`manager.go:935`).

## (a) Unknowns that would change the plan

1. **Does the web client reconnect after `superseded`, and what does it do on `release_request`?** If it auto-reconnects, two clients on one server alternate every 3 s or so. If it does not, a remote server's window that was superseded stays dead until reloaded. This decides whether "switching servers" can keep background connections open. (Web task.)
2. **Does switching servers in the desktop app close the event stream of the one switched away from?** If it does, every board tool call on that server fails at once with "the window is closed" while its chats keep running. If it does not, the app holds N active-client sessions, one per server. That is allowed by the server (each server has its own bridge), but each remote then has a hidden window acting as its board engine. (Desktop and web tasks.)
3. **Where the web client comes from for a remote server.**
   - Served by the remote: it needs `web/dist` on the remote and `-client`; the client version equals the remote's.
   - Served by the desktop app: needs CORS or a proxy, and client/server versions can differ. The server has no CORS and no API versioning today.
4. **Permission-ask timeouts with no client connected.** I did not trace whether Claude, Cursor or pi time out a pending permission request on their own. If they do, a turn on an unattended remote fails; if not, it waits indefinitely.
5. **Whether a real agent turn completes cleanly with no client connected.** Inferred from code; not run, because it would need a real agent.
6. **Target OS of remote machines.** A Linux build compiles, but `reveal` (`open -R`), the `.app` bundle lookup and `scripts/` are macOS-only. No Linux packaging or service unit exists. Windows does not compile.
7. **How the server gets started and kept running on the remote** (by hand over SSH, by the desktop app over SSH, a service). Nothing exists; it is entirely a design choice.
8. **SSE through the chosen transport:** whether it buffers or idles out a stream that only sees a `: ping` every 20 s. (Transport task.)
9. **Large scene `PUT`/`GET` bodies over a slow link.** No size limit or compression in the server; not measured.

## (b) Implications — my opinion, not facts

- **The Host allowlist is the first thing every transport hits.** With a loopback forward, the server needs no bind change, but either each remote must be reached on a local port equal to its own `-port` (which collides between remotes and with the local server on 4747), or the guard must learn additional allowed hosts. I would treat "which Host values a server accepts" as an explicit, per-server setting and keep the loopback pair as the default.
- **The active-client rule must not be mistaken for access control.** Anything that makes a server reachable beyond its own loopback needs real authentication on `/api`, including GETs and `/api/events`, or a transport that authenticates and terminates on the server's loopback (SSH-style). With the latter, the server could stay almost unchanged. Whoever can reach the listener can run commands as the server's user.
- **Keep remote forwards away from the ports `findRunning` probes** (4747 and the `server.json` port), or give hello an instance identity that `findRunning` and `relaunch` check. Otherwise the local launcher can adopt a remote server as "the local one", and `relaunch` can signal a wrong local pid.
- **The server has no identity.** A multi-server client needs one to label servers, detect "this address now answers as a different server", and avoid registering the same server twice. A stable id and a display name stored in the data folder and returned by `/api/hello` would be a small, additive change. Hostname and OS in hello would help the UI explain whose paths it is showing.
- **"Board edits need the open window" becomes the central product question for remotes.** A remote server the user is not looking at cannot do board work. Either the app keeps a live client per registered server, with the 3 s take-over fight if the user also opens that server elsewhere, or the UI makes clear that agents on a server in the background can chat but not draw.
- **Several routes need a remote-aware answer rather than removal:** `reveal`, the log (no route exists), `restart` (meaningful but different), `mcp/status` (label it as the server's own loopback), and the `home`/`dataDir`/`cwd` paths (label them as the server's). The folder picker (`/api/dirs`) already does the right thing for a remote.
- **Deployment is the largest gap on the server side:** no embedded web client, no service unit, no non-macOS packaging, one instance per machine because of 6006, and a boot-time write into the user's Cursor config. The plan should say who installs and starts the remote server and how its version is kept compatible with the desktop app. Today only page-versus-server on the same machine is compared.
- **Tests to extend rather than replace:** `TestBadHostIsForbidden`, `TestMutationsNeedTheActiveClient`, `TestFindRunning*`, `TestLaunch*`, `TestHello`. The MCP URL pins and `bridge_test.go` should stay green untouched.
