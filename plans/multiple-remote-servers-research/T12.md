**completed**: I ran the one-window skeleton (shell strip plus three partitioned server views) on Electron 44.4.5 against scratch servers and have a run-based answer for every item S1–S7, including a 25.5-minute background run in which all 18 agent edits were saved and no SSE stream dropped. The model works, but three things need app code: keyboard focus can land on a hidden view (after a switch and whenever the window regains key status), the default menu's Reload/DevTools/Zoom act on whichever view has focus (including the shell strip or a hidden view), and views are never asked on close/quit. One finding outside the brief: `will-prevent-unload` is not emitted for a reload when the page has had no user gesture, so an agent-only page lost an acknowledged edit on reload.

# T12 report: skeleton run of "one window, one kept-alive view per server"

## Read this first

1. **Focus can end up in a hidden view.** With `setVisible(false)` hiding, keyboard focus moved to a hidden server view in 2 of 4 switches without a focus call (2 of 6 counting the two repeated in S2c), and in 4 of 5 cases where the window regained key status. Calling `shownView.webContents.focus()` on every switch and on the window's `focus` event fixed it in every run (S2).
2. **`will-prevent-unload` is not emitted for a reload when the page has had no user gesture since it loaded.** An agent-only page was reloaded with a pending save and the acknowledged edit was lost (S4, "extra finding"). The repository's `attachCloseFlush` relies on that event.
3. **One acknowledged edit was lost in a way I could not reproduce.** It was sent 30 ms after the first `show_board` on a freshly loaded hidden page; `aiwbFlush()` returned `true` and the file was written without the element (S4, "extra finding").
4. **Harness mistakes that cost screen time, nothing else.** One S5 run hung for 200 s and one for 60 s on harness bugs, each leaving a small inactive window on screen. The first S3 pass dispatched menu commands on the wrong object and was repeated.
5. **The machine was not idle the whole time.** System idle time dropped to 0 at about 23:11. The real app's own server wrote to `~/.ai-whiteboard` at 23:18–23:19 (`state.json`, `server.log`, `chats/`). None of my processes use that folder or ports 4747/6006.

To see where the operating system routes a keyboard action without sending a key press, I called `Menu.sendActionToFirstResponder('selectAll:')` and checked which page's text field became selected. In every run this agreed with `isFocused()`.

- **After `win.show(); win.focus()` and nothing else, no view has the focus.** **verified** — `getFocusedWebContents=null`, every `isFocused=false`, every `document.hasFocus()=false`.
- **`viewA.webContents.focus()` gives A the focus.** **verified** — `A: isFocused=true hasFocus active=INPUT#t12in`; the native select-all selected A's field.

  | A | hide A, nothing shown yet | **B (hidden)**; stays there when B is shown 250 ms later |

  ```
  hide B first, then show A | focusedWC=C | A(shown) isFocused=false ... | C(hidden) isFocused=true hasFocus=true nativeSelectAllHit=true
  ```
  All six fit "focus moves to the next view in child order, visible or not" (pattern **inferred**).
- **`viewB.webContents.focus()` works when called in the same tick as `setVisible(true)`.** **verified** in both call orders; the state was correct immediately and 300 ms later.

- **What `attachCloseFlush` requires of its `win`** (by reading `desktop/lib.js:355-391`):
  - `win.on('close')` (line 359). A view has `.on` but never emits `close`, so the close path never runs.
  - `win.webContents.on('will-prevent-unload')` and `win.webContents.executeJavaScript` (lines 362, 333). Both work with a view.
  - `win.close()` (line 388). A view has no `close` (`typeof view.close = undefined`); never reached for a view.
  - `dialog.showMessageBox(win, …)` (line 373). In the run, the fake dialog's first argument was a `WebContentsView`. Electron's source (printed from the running binary, read) treats a first argument that is not a `BaseWindow` as the options object:
    `function showMessageBox(e,t){const r=!e||e instanceof n.BaseWindow?e:null,o=!e||e instanceof n.BaseWindow?t:e;…}`.
    The real dialog would therefore get the view as its options and lose the message and buttons. Not run, because no real dialog may be shown.
  - `app.quit()` when the shared `quitting` flag is set (line 387). Views are never asked on quit, so the flag is not cleared by a view; a later reload with pending saves could call `app.quit()` instead of reloading. **inferred** by reading.

### Extra finding: `will-prevent-unload` depends on a user gesture

`executeJavaScript(code, true)` counts as a user gesture; my first runs used it, which hid this. **verified** (one run per row):

| Page state | Action | Result |
|---|---|---|
| no user gesture since load, save slowed 1.5 s | `reload()` | page's `beforeunload` called `preventDefault`, **no `will-prevent-unload`**, page replaced, **edit not on disk** |
| no user gesture, save not slowed | `reload()` 10 ms after the edit | page replaced; edit was saved |
| after `executeJavaScript('1', true)` | `reload()` | `will-prevent-unload` emitted, reload cancelled |
| no user gesture | `close({ waitForBeforeUnload: true })` | `will-prevent-unload` emitted, page stays |

```
1. no user gesture since load: view A, userActivation {"hasBeenActive":false,...}, save slowed by 1500 ms, disk 31; now reload()
   [A page] beforeunload defaultPrevented=true ; [A page] pagehide
   -> page was replaced (new client id) | disk 31->31 (EDIT NOT ON DISK)
```
- The same happened twice in an earlier S4 run, with the menu's Reload and with `reload()`.
- A page that only agents have touched since it loaded is not protected against a reload by `will-prevent-unload`. This covers Cmd+R, the reconnector's `load`, and any `loadURL` on that view.
- Whether today's single `BrowserWindow` behaves the same was not run (**unknown**; I expect it does).

### Extra finding: one acknowledged edit missing after a successful flush

- In the first S4 close run the edits were sent 30 ms after the first `show_board` on freshly loaded pages. B's flush answered `true` and its file was written at that moment, but with 3 elements instead of 4. A and C were fine. **verified** (seen once).
- 32 later tries, editing 0–2000 ms after a reload, with and without `show_board`, shown and hidden, lost nothing.
- Likely cause, by reading `web/src/Canvas.tsx:69-80` and `web/src/board.ts:49-59`: the edit arrived while the canvas was mounting, and Excalidraw's first `onChange` with the initial elements replaced the stored scene. **inferred**
- This is a web-client matter, not a window-model one. All my other runs waited 3 s after `show_board`.

## What the desktop app has to do in this window model

- **Give focus to the shown view explicitly** (S2): at start-up, on every switch (same tick as showing it), after a click on the shell strip, and on the window's `focus` event. Or detach hidden views instead of `setVisible(false)`, which keeps focus off hidden pages; the explicit `focus()` is still needed.
- **Set its own application menu** (S3): Reload, Force Reload, DevTools and Zoom otherwise act on whichever view has focus, including the shell strip and hidden views. The app has to decide which view they target.
- **Flush before any reload or navigation of a view, from the main process** (S4 extra finding, S5): `will-prevent-unload` is not emitted for a page with no user gesture. This covers the menu's Reload and the reconnector's `load`.
- **Flush every view on window close and on quit** (S4): prevent the event, call `aiwbFlush()` on each view with a timeout, then go on. The close and quit handlers need a shared "already flushed" state so the second pass is not prevented again.
- **Name the server in the unsaved-changes dialog** (S4): the per-view flush result gives the server and the time. The dialog's parent has to be the window, not a view.
- **Close each view's `webContents` when the window closes, or keep the views on purpose** (S4): otherwise they stay active clients until garbage collection (17.8 s in one run).
- **A view-aware replacement for `attachCloseFlush`** (S4): the existing one handles only a view's reload, passes a view to the dialog, and shares a quit flag that views never clear.
- **Show a placeholder for an unreachable server and load the server later** (S5): the failed view is an empty page. Treat `did-fail-load` or the `loadURL` rejection as the signal, not `did-finish-load`.
- **One reconnector per server view, with a `launch` that fits a remote server** (S5): today's instance reloads a page that has already reconnected by itself.
- **Set the window title itself** from the shown view's `page-title-updated` or `getTitle()` (S7).
- **Lay out every view on the window's `resize`** (S7).
- **Refuse or route the preload call by sender** (S1; T05's E5): `aiwbDesktop` is present in every server view and even on the error page.

## Anything that argues against this window model

Nothing found that the model cannot do. Three things make it more work than T05's report suggests:

- **Focus on hidden views** (S2): with `setVisible(false)`, the user can type into, select in, paste into, or reload a page they cannot see, unless the app hands focus over on every switch and on every window `focus`. Evidence: the two tables in S2 and the "hidden server view C" row in S3.
- **The default menu is wrong for this model** (S3): Cmd+R and Cmd+Option+I hit the shell strip when it has focus.
- **Reload protection is weaker than assumed** (S4 extra finding): this applies to any model that relies on `will-prevent-unload`.
