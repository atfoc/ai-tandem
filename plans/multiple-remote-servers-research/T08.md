# T08 — Real `ssh -L` runs against a private loopback sshd

All statements are marked **verified** (I ran it and quote the output), **inferred** (not run) or **unknown**. All timings are on loopback, so they are lower bounds: a real network adds its round trips.

## Things to know first

1. **The key line from the brief does not make a forward-only key.** With `restrict,port-forwarding,permitopen="…"`, `ssh host echo hi` printed `hi` and exited 0 (**verified**). `restrict` removes the pty, agent and X11 forwarding; it does not stop command execution. I added `command="/usr/bin/false"` to the line; after that a command and a shell both exit 1 with no output. If the plan suggests a restricted key to users, it needs the forced command.
2. **A stalled link makes ssh exit after about 60 s, not 45 s** (two runs: 59.2 s and 57.3 s after the stall began).
3. **A plain `ssh` child outlives its parent** when the parent is killed, terminated or exits normally. The app has to end tunnels itself.
4. **sshd's default per-source penalties punish retry loops.** After four failed logins one second apart, sshd dropped every connection from that address for about 17 s, including one with a good key.
5. **Rejected key and passphrase-protected key are indistinguishable** from exit code and stderr at the default log level.

Details per case:

- **Port busy without `ExitOnForwardFailure`.** ssh stayed up for the 3 s I watched; `lsof` showed the port still owned by the other process. The app would see a running tunnel that forwards nothing.
- **Far server not listening.**
  - curl through the forward: `curl: (56) Recv failure: Connection reset by peer`.
  - Chrome: `fetch` fails with `ERR_CONNECTION_RESET`; the `EventSource` gets `ERR_CONNECTION_RESET`, stays in `CONNECTING` and retries every 3 s; ssh logs one `open failed` line per attempt.
  - After the server started again the stream reopened 3.0 s later (`hello active=true`, snapshot), no reload. Same result for a clean stop (the page first receives `server_stopping`) and for SIGKILL.
- **Forward not permitted.** curl exit 56, as above. sshd log: `Received request from 127.0.0.1 port 62964 to connect to host 127.0.0.1 port 4899, but the request was denied.` A key with `restrict` and no `port-forwarding` gives the same client text.
- **Never answers, without `ConnectTimeout`.** My loopback trick (a listener with a full backlog) timed out after 7.8 s, which is an artefact of the trick. The real default is **unknown**; `sysctl net.inet.tcp.keepinit` is 75000 ms on this machine.
- **`accept-new`.** It wrote `[127.0.0.1]:22811 ssh-ed25519 AAAA…` to the temp `known_hosts` and the tunnel came up. The warning line is on stderr of a successful run, so non-empty stderr does not mean failure.
- **Changed host key.** `accept-new` does not override it (same output, 255). With `BatchMode` off and `SSH_ASKPASS` forced, the askpass program was not called. `known_hosts` stayed unchanged.
- **Rejected key vs. passphrase key.** Identical at default log level. With `-v` the passphrase case shows `debug1: Server accepts key: …` and then, without `BatchMode`, `debug1: read_passphrase: can't open /dev/tty: Device not configured`. I did not run `-v` with the rejected key.
- **Per-connection sshd killed.**
  - Killing the traffic-carrying child ends the client in 25 ms.
  - Killing only the `[priv]` parent did not end anything: the tunnel still answered 200 four minutes later.
  - Restarting the sshd listener (new host key) left an established tunnel working.
- **Stall.** `page.mjs stall`:

```

--- 10/20/30/40 s into the stall: fetch /api/hello: TimeoutError (3 s)   page text unchanged, no ES error
    [ssh stderr t=63428ms] Timeout, server 127.0.0.1 not responding.

    63413ms ES error (CONNECTING: will retry)                           page: "Reconnecting…"
```

  - Second run without a page: exit 57.3 s after SIGSTOP. That is about 60 s after the last data from the server, i.e. interval × (count + 1). The reason is **inferred**; the timing is **verified**.
  - During the stall: `-O check` answered `Master running` every time, `curl -m 3` exited 28, the local listener was still there.
  - After `SIGCONT` the server processes exited by themselves.
- **`ssh -G` with a made-up alias — verified.** Exit 0 in 13 ms. It prints the resolved options (`hostname made-up-alias-t08`, `user pedjat`, `port 22`, `localforward [127.0.0.1]:4823 [127.0.0.1]:4812`, `identityfile …`). It does not say whether the alias exists or the host is reachable. ### What a parent process can tell apart from exit code and stderr alone

| Message for the user | Recognised by | Distinguishable? |
|---|---|---|
| Port in use | exit 255 + `Address already in use` (needs `ExitOnForwardFailure=yes`) | yes |
| Cannot reach host | exit 255 + `ssh: connect to host … : Connection refused` / `Operation timed out` / `timed out during banner exchange` | yes, as a group |
| Host key not trusted | exit 255 + `Host key verification failed.` and no `HAS CHANGED` | yes |
| Host key changed | exit 255 + `REMOTE HOST IDENTIFICATION HAS CHANGED` | yes |
| Login refused | exit 255 + `Permission denied (publickey)` | yes; wrong key vs. locked key: **no** |
| Server is not running on that machine | ssh keeps running; `/api/hello` through the forward is reset; stderr `open failed: connect failed: Connection refused` | yes, but only by probing, never from the exit code |
| Forwarding not allowed | ssh keeps running; stderr `open failed: administratively prohibited` | yes, only after a request |
| Connection lost | exit 255 + `closed by remote host` or `Timeout, server … not responding` | yes |
| Blocked by sshd penalties (see below) | exit 255 + `Connection closed by … port …` or `kex_exchange_identification: read: Connection reset by peer` | looks like a network fault; not separable |
| Name does not resolve | not run (would send a DNS query off this machine) | **unknown** |

## S4. Two servers at once (`s4.zsh`)

- **(i) Two separate `ssh` processes — verified.** Both answer 200. Server B stopped: A 200, B curl exit 56, both ssh processes stay up. ssh B killed: A 200, B curl exit 7. Fully independent.
- **(ii) One connection with two `-L` — verified.** Both answer 200; one process owns both listeners. Server B stopped: A unaffected, ssh stays up. When the process ends, both go. With one local port busy at start and `ExitOnForwardFailure=yes`, the whole process exits 255 and neither forward exists; without the option, the free one works and the failure is only on stderr.
- **(iii) One `ControlMaster` — verified.** It works; other forwards are unaffected by each operation below, except `-O stop`.

| Command | Result |
|---|---|
| `-O forward -L …` | exit 0, silent, forward works |
| `-O forward` of one that exists | exit 0, silent |
| `-O cancel -L …` | exit 0, that port refuses |
| `-O cancel` of one that is not there | **exit 0**, stderr `forwarding request failed: port not forwarded` |
| `-O forward` to a busy local port | exit 255, `mux_client_forward: forwarding request failed: Port forwarding failed`; master stays up |
| `-O forward` to a port the key may not open | exit 0; fails only on the first request |
| `-O stop` | `Stop listening request sent.`; the `-N` master then **exited and all forwards were gone** |
| `-O exit` | `Exit request sent.`; master exits with code **255**, empty stderr |
| Master killed with SIGKILL | socket file stays; `-O check` → 255 `Connection refused`; a new master prints `ControlSocket … already exists, disabling multiplexing` and runs as an uncontrollable plain ssh |

- **Simplest to supervise (opinion):** one `ssh` process per server. State is "process alive + hello answers", failures are isolated, and there is no socket file to go stale. The master saves one connection per host but adds a second control channel with its own exit-code oddities, and one dead link takes all servers of that host down together.

## What the app's tunnel supervisor has to do (verified findings only)

1. **Start** one process per server: `ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -o ConnectTimeout=<n> -L 127.0.0.1:<Q>:127.0.0.1:<P> <dest>`, stdin ignored, stdout and stderr piped. Without `ConnectTimeout` an unanswering host has no bound I could measure.
2. **Prompts**: either `-o BatchMode=yes` (never asks, fails in under 0.4 s), or no `BatchMode` plus `SSH_ASKPASS=<app program>` and `SSH_ASKPASS_REQUIRE=force` to show host-key and passphrase questions itself. Without a terminal and without askpass, ssh fails; it never hangs.
3. **Readiness**: poll `GET /api/hello` through `127.0.0.1:<Q>` until 200. ssh prints nothing when ready. A TCP connect to Q succeeding means only that SSH is authenticated.
4. **Classify a start failure** by stderr text (table in S3); the exit code is always 255. Trim `\r`. Do not treat non-empty stderr as failure: `Warning: Permanently added …` appears on a good run.
5. **"Server not running there"** is detected while ssh runs: the probe is reset and stderr gets `open failed: connect failed: Connection refused`. `open failed: administratively prohibited` means forwarding is not allowed for that login. `403 bad host` means the Host guard.
6. **Losing the link**: ssh exits 255 with `closed by remote host` (within 25 ms of a dead peer) or `Timeout, server … not responding` (about 60 s after a silent stall). Restart the tunnel; the page reconnects by itself within 3 s of the forward being back, without a reload.
7. **Do not retry in a loop** after `Permission denied` or a host-key failure: four failures in four seconds got the address blocked for 17 s, and a good key then failed with a text that looks like a network fault. Retry with back-off only for connection-lost and cannot-reach cases.
8. **Stop**: SIGTERM, exit code 0 within milliseconds. Treat exit 0 as "we stopped it".
9. **Tunnels do not die with the app.** Kill each child on quit, and cover a crash: the stdin-EOF wrapper tested in S5 works. Otherwise a leftover ssh keeps the port; the next start then failing with `Address already in use` is **inferred** from the two verified facts, not run as a sequence.
10. **If a `ControlMaster` is used anyway**: delete a stale socket before starting, never use `-O stop`, and do not trust the exit code of `-O cancel`.

## Unknowns that remain

- **Sleep and wake of a real laptop**, Wi-Fi change, NAT idle timeouts, latency and packet loss. Everything here is loopback.
- **Connect time on a real network**, and the timeout without `ConnectTimeout`.
- **Name resolution failure** text: not run.
- **The user's own `~/.ssh/config`**: aliases, `ProxyJump`, an agent, 1Password or Keychain-stored passphrases (`UseKeychain`), a user-level `ControlMaster`. I used an isolated config with `IdentityAgent none` by rule.
- **Password, keyboard-interactive or two-factor logins**: only public key was enabled.
- **Electron itself**: the runs used Node `spawn`. Which quit paths run handlers, and an askpass program inside the app bundle, are not tested.
