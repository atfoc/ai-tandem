**completed**: I settled all six questions by reading the server code, running the existing fake-agent tests, adding temporary tests (since removed), and probing a scratch server over real HTTP. A turn with no page runs to its end and everything a page needs is recoverable from the snapshot plus the GET routes; the exceptions are board tool calls, which fail or time out, and permission requests (Claude and Cursor only), which wait with no server-side timeout and block the chat until a page answers. Three things the plan should not miss: a stalled stream keeps its client "active", so board calls burn the full 30 s; a late page reply is dropped with HTTP 200; and the agent gets three different failure texts depending on when the page went away.

## 1. Permission requests with no client

### When a request can reach the user at all

- **Claude [V]**: the process runs with `--permission-mode auto --permission-prompt-tool stdio` (`internal/claude/claude.go:95`).
  - Board and spawn MCP tools are pre-allowed with `--allowedTools` (`claude.go:111-113`, `125-138`).
  - The app folder, `Task` and `Agent` are disallowed (`claude.go:108`).
  - Any `can_use_tool` control request the CLI still sends becomes a card, unless its input touches the app folder, which is denied silently (`claude.go:314-332`).
- **Claude [U]**: when the CLI's auto mode decides to send `can_use_tool` is CLI behaviour. The repo only shows that such requests exist (fixtures in `internal/claude/proc_test.go:247-248`, `309`, `400-401`).
- **Cursor [V]**: every ACP `session/request_permission` is handled in `internal/cursor/cursor.go:796-862`.
  - Board and spawn MCP calls are answered "allow" at once (`cursor.go:840-846`).
  - Requests touching the app folder are answered "reject" at once (`cursor.go:848-851`).
  - Everything else becomes a card (`cursor.go:852-861`).
- **Cursor [U]**: which tool calls Cursor asks about depends on Cursor's own permission configuration. The server only adds deny rules for its data folder (`internal/cursor/config.go:28`).
- **pi [V]**: never. The bridge's ask is answered at once: allow, or deny for the app folder (`internal/pi/perm.go:15-20`). pi's `Decide` always returns an error (`perm.go:24-26`). Only Claude and Cursor emit `EvPermRequest` (`claude.go:330`, `cursor.go:861`).
- **App-spawned subagents [V]**: a Claude or Cursor child's request lands as a card in the parent chat's thread with the child's sid (`internal/chats/spawn.go:418-428`). It is answered through the child's process (`permAgent`, `manager.go:1197-1202`). It puts the parent chat into `approval` (test `TestSubagentPermissionWhileIdle`, PASS).

### Where an open request is held

- **[V]** In two places, both in memory only:
  - the adapter's map: `proc.perms` in `claude.go:63`, `327` and `cursor.go:94`, `853`;
  - the thread: a `perm` item with `decided:""` plus `Transcript.perms` (`internal/transcript/transcript.go:28`, `291-304`).
- **[V]** The open card is not on disk while the server runs: an undecided `perm` is not "settled" (`transcript.go:489-499`). Temp test: with the request open, `items.jsonl` held only the user line.

### Timeouts

- **Server side [V]**: none. No timer exists on the path request → card → `Decide` (`manager.go:1165-1192`; the timer grep over `internal/chats` shows only `fork.go:27` and `claim.go:13`, both unrelated). Temp test: status was still `approval` after 1.5 s idle, and nothing in the code would change that later.
- **Agent side [U]**: the repo documents no timeout for Claude's `can_use_tool` or Cursor's `session/request_permission`, and I could not test real CLIs. Treat "the agent waits indefinitely" as an assumption.

### While the request is open

- **[V]** The chat is busy: status `approval` counts as busy (`manager.go:289-299`), so a new message gets `ErrBusy` → HTTP 409 (`manager.go:818-821`). Temp test: `Send` returned `ErrBusy`.
- **[V]** The app does not start its own turn to deliver subagent results (`deliverable` needs `!busy`, `internal/chats/delivery.go:116-119`).
- **[V]** With no client nobody can answer or interrupt: both are POSTs that need the active client (`internal/server/guard.go:32-52`). The turn stays blocked for as long as the agent waits.

### When a page connects later

- **[V]** The snapshot shows the chat with `status:"approval"`. `GET /api/chats/{id}/items` returns the `perm` item with `decided` empty. `POST /api/chats/{id}/permission` then works and the agent process receives the answer.
  - Temp test `TestT06PermissionWithNoClient`: card read as `RequestID:p1 Decided:""`; late `Decide` returned nil; the agent got `{p1 allow:true}`; status went `approval` → `tool`; `"decided":"allow"` was on disk.
  - Existing test over HTTP: `TestChatPermission` (PASS).
- **[V]** A stale answer gets `ErrNoRequest` ("this permission request is no longer open; reload the page if it still looks open", `manager.go:106`, `1177-1179`) → HTTP 400 (`server.go:654-656`).

### When the server restarts

- **[V]** `Shutdown` writes every open item, including the undecided card (`Flush(true)`, `manager.go:1373`).
- **[V]** On the next load every open card is closed as `deny` and written (`transcript.go:107-111`, `manager.go:267-270`). It cannot be answered: `Decide` → `ErrNoRequest`.
  - Tests: `TestLoadClosesOpenPermissions`, `TestLoadClosesSameIDPermissions`, `TestLoadClosesOpenPerms` (all PASS). Temp test confirms the same.
- **[V]** After a crash without `Shutdown`, the card is simply absent from disk (see "Where held").

### When the turn is interrupted

- **[V]** `Interrupt` sends only the interrupt signal; it does not answer the open request (`manager.go:1127-1160`; `claude.go:376-379`; `cursor.go:343-353`).
- **[V]** The agent's aborted turn end then closes the chat's own cards as `deny` in the thread (`transcript.go:306-318`).
  - Temp test: items after interrupt were `user, perm(decided=deny), note "Stopped.", end`; the agent received no decision; a later `Decide` → `ErrNoRequest`.
  - Tests: `TestTurnEndClosesOwnPermission`, `TestAbortedTurnClosesSubagentPermissions` (PASS).
- **[V]** A subagent's card survives a normal parent turn end (`TestTurnEndKeepsChildPermissionOpen`, PASS). It is closed when the subagent ends or is stopped.
- **[V]** Archive, delete and Stop answer "no" to the process and close the cards (`stopOne`, `internal/chats/branches.go:442-497`; `TestStopDeniesPendingPermission`, `TestStopDeniesEachAskersPermission`, PASS).
- **[V]** A process exit closes all cards (`transcript.go:320-333`; `TestIdleExitClosesLatePermission`, PASS).

## 2. A turn that runs with no client

- **Runs to its end [V]**: the pump goroutine reads the agent's events and never consults the bridge except to broadcast, which is a no-op with no client (`manager.go:673-787`, `133-144`; `bridge.go:190-200`). Agent event channels are drained whether or not a client exists (`claude.go:207`, `cursor.go:136`, `pi.go:42`).
- **Two things stop or degrade such a turn [V]**: an open permission request (section 1) and board tool calls (section 4).
- **Written to disk [V]**:
  - the user message at Send (`manager.go:869-873`);
  - settled items at each tool result, tool denial, session event, turn end and exit (`manager.go:767-773`);
  - the end mark with the fork point (`manager.go:747-750`).
  - Temp test `TestT06TurnWithNoClient`: after the turn, `items.jsonl` held `user, text(done), tool(with result), text(done), end(point)`.
- **Not on disk mid-turn [V]**: streaming text, a tool call without its result, and an open permission card live only in memory until the next flush point or `Shutdown`. Temp test mid-turn: the file held only the user line, while `GET items` returned the partial text item from memory (`version=4`, `Text:"partial text"`, `Done:false`).
- **State settles [V]**: status `ready`, `turnActive=false`, `usage.turns=1`, context token numbers saved in `chat.json` (`manager.go:718-742`, `772`).
  - Temp test: `status="ready" usage={CtxIn:1234 CtxOut:56 CtxWindow:200000 Turns:1}`, identical in `chat.json`.
  - Test `TestUsageTurns` (PASS).
- **Name from the namer [V]**: the namer goroutine starts at the first Send, independent of any client, and `Rename` saves `chat.json` (`manager.go:886-896`, `1039-1056`). Temp test: `name="Named title"` on disk with no client.
- **The app's own turns still happen [V]**: owed subagent results are handed to the parent agent in a turn the server starts by itself (`delivery.go:233-265`, `297-320`; `TestPendingResultGoesOutAtTurnEnd`, PASS, no client). A turn Claude starts itself is tracked too (`manager.go:762-766`; `TestUnrequestedTurnSetsTurnActive`, PASS).
- **Unread markers [V]**: the server has none. `ChatView` has no such field (`internal/model/model.go:270-303`) and a grep for unread/unseen/notification over `web/src` and `desktop` found nothing. The only "new" marker is `Board.New` for a board an agent created, persisted in `board.json` (`model.go:57`; `internal/boards/boards.go:261-264`). Nothing records that a chat finished while nobody watched.

## 3. A page that reconnects after a gap

### What brings it up to date

- **[V]** Opening the stream is enough for app state: the newly active client gets `hello` and a full `snapshot` (`bridge.go:95-102`, `305-322`). `GET /api/state` returns the same snapshot without a stream and needs no active client (`server.go:259-261`).
- **[V]** Threads are fetched per chat: `GET /api/chats/{id}/items` (`server.go:479-492`), `GET …/subagents/{sid}/items`, `GET …/tree`. Scenes come from `GET /api/boards/{id}/scene`. All GETs work for any client or none (`guard.go:45-47`).
- **[V]** Nothing is queued across the gap. Temp test `TestT06NothingQueuedForNextClient`: events broadcast with no client were not delivered to the next client, for a new id and for the same id.

### Same client id (stream dropped, page still alive)

- **[V]** If the server already saw the old stream end, there is no active client in between. The returning stream becomes active at once and gets a new snapshot (`bridge.go:95-97`, `118-131`).
- **[V]** If the server still thinks the old stream is open, the new stream replaces it at once with no 3 s wait (`bridge.go:98-102`; `TestSameClientReconnectReplacesStream`, PASS).
- **[V]** The page's id is one random UUID per page load (`web/src/api.ts:22`), and the page uses `EventSource`, which reconnects itself with the same URL (`web/src/conn.ts:16-20`). So a network drop is the same-id case; a reload or app restart is the different-id case.

### Different client id

- **[V]** With no active client, it becomes active at once.
- **[V]** If the server still holds the old stream, the new client waits: it gets `hello{active:false, waiting:true}`, the old one gets `release_request`, and after 3 s without a release the old one is cut off (`bridge.go:103-115`, `286-302`; `TestTakeoverWithoutReleasePromotes`, PASS). Scratch run: client B's stream showed `waiting:true`, then `active:true` plus the snapshot.
- **[V]** The cut-off client's POSTs get 409 `not_active` from then on (scratch run).

### Missing or duplicated thread items

- **No duplicates [V]**: updates are "set item at index" with the whole item, not appends (`transcript.go:42-45`, `509-519`). The full fetch returns the whole list.
- **No misses within one connection [V]**: each update carries the thread's version (`manager.go:185`). Events travel in order on one channel. If the buffer overflows, the stream is closed and the page gets a new snapshot on reconnect (`bridge.go:332-343`).
- **Version is in memory only [V]**: it starts at 0 when a thread is loaded (`transcript.go:25`, `55-65`). Temp test: version 9 before a restart, 0 after, same 5 items. A page that kept cached items across a server restart would compare against a version that went backwards. Today the page drops all cached items on every snapshot (`web/src/store.ts:114`).
- **A narrow reordering race [I]**: events are composed under the chat's lock but broadcast after unlocking (`manager.go:128-144`). Two goroutines changing the same chat (pump and `Decide`, or pump and a subagent runner) could broadcast version N+1 before N. The page ignores an update whose version is not newer (`web/src/conn.ts:82-90`), so N's changes would be skipped until the next full fetch. Not reproduced.

### A board RPC in flight when the stream drops

All four paths were run (temp tests and scratch server).

| Path | Result | Evidence |
|---|---|---|
| Server sees the drop | Call fails immediately | scratch: stream killed 1 s into a call → answer at 1.05 s; `bridge.go:118-131`, `353-366`; `TestActiveDisconnectFailsCalls` PASS |
| Same id reconnects while the old stream is still open server-side | Call is **not** failed and the `rpc` event is **not** resent; it waits out its full timeout | temp test: "call still waiting 303ms after the same-id reconnect", then "the board did not answer tool in 1.5s" (test timeout; 30 s in production); `bridge.go:98-102` has no `failCalls` |
| Page had the `rpc` before the drop and replies after reconnecting | Reply resolves the call (matched by rpc id, not by connection) | temp test: `out="late answer"`; `bridge.go:236-243` |
| Another client takes over (release or 3 s timer) | Old client's calls fail at promotion, although a client is active again | `bridge.go:294-298`; `TestSupersededClientCallsFail` PASS; temp test: err after 400 ms (shortened delay), `B active=true` |

- **[V]** Nothing retries in any of these paths.

### What the agent sees

- **[V]** A normal MCP tool result with `isError:true` and a text, never an HTTP error (`mcp.go:254-260`).
- **[V]** The text when the client leaves **during** the call is the short one: `the board isn't open: the AI Whiteboard window is closed`. It lacks the "don't retry" sentence. Cause: `Call` rebuilds the error with `errors.New(r.Error)` (`bridge.go:226-227`), so `errors.Is(err, ErrNoClient)` at `mcp.go:66` is false and `mcp.go:69-71` returns the raw text. Scratch output:
  `{"text":"the board isn't open: the AI Whiteboard window is closed","type":"text"}],"isError":true`

- **A reply after the 30 s is dropped silently [V]**: `POST /api/rpc-reply` for an id that already timed out returned `{"ok":true}` with HTTP 200 (scratch; `bridge.go:236-243`, `server.go:243-258`). The page cannot tell its answer was not used.
- **Consequence for edits [I]**: the page has no timeout of its own for a tool run; it loads the scene, applies the change, then replies (`web/src/board.ts:306-344`). On a slow link an `apply` can change the board while the agent was told the board did not answer. The server half is verified; the combined effect was not run end to end.
- **A reply from a non-active client is refused [V]**: 409 `not_active` (scratch; `server.go:252-255`).
- **A stalled client stays "active" [V]**: temp test `TestT06StalledClient` used a connection that stays open but stops reading.
  - After the 4096-message buffer filled, the stream was marked closed, but `IsActive` stayed true because the handler was stuck in a write.
  - Broadcasts were dropped. A call waited out its whole timeout ("the board did not answer tool in 700ms" with the test's short timeout; 30 s in production).
  - A different client id became active after the handover delay; the same id would replace it at once.
  - So over a dead link the agent gets the slow 30 s failure, not the instant "window is closed" one, until the server notices the dead connection.
- **Nothing retries [V]**: `Relay.Call` makes one `Bridge.Call`; neither has a loop (`mcp.go:63-71`, `bridge.go:204-233`). Whether the agent's MCP client retries is outside the server **[U]**.
- **The spawn family does not need a page [V]**: `spawn_subagent`, `stop_subagent` and `list_subagent_models` go to the chat manager, not the bridge (`mcp.go:289-294`, `306-332`). Scratch: `list_subagent_models` answered normally in 0.04 s with no client.
- **Scene files are never changed without a page [V]**: `drawing.excalidraw` has exactly two writers.

  - Both are non-GET `/api` routes needing the active client. An agent's `create_board` also goes through the page (`mcp.go:295-299`). Scratch: the scene file was untouched after the failed tool calls.
- **`Save` overwrites the whole file with no revision check [V]** (`boards.go:194-208`).
- **`board.json` can change without a scene change [V]**, but only through active-client routes (rename, move, seen, archive: `boards.go:211-269`).

## 6. Server stop and restart with running chats and no client

### The stop sequence on SIGINT/SIGTERM (`main.go:208-215`)

1. `StopAndFlush(2s)` returns at once when no client is connected (`bridge.go:249-253`; scratch: 0.02 s). [V]
2. `cm.Shutdown()` (`manager.go:1363-1391`), for every chat:
   - holds the chat;
   - writes all items including open ones (`Flush(true)`);
   - writes subagent threads and records, and `chat.json`;
   - stops app-spawned subagents and revokes their extra tokens;
   - closes the agent in the background. [V]
3. `agent.EndAll(2s)`, bridge socket closed, `server.json` removed, `os.Exit(0)`. Scratch: `server.json` gone after stop. [V]

### Kept

- **Thread on disk [V]**: every settled item, and through `Flush(true)` also the half-written text, the tool call without result and the open permission card. Temp test `TestT06ShutdownRunningNoClient` printed `items.jsonl` as `user, text(done), tool(no result), perm(no decision)`.
- **`chat.json` [V]**: `turnActive:true` is kept on purpose so the chat shows as stopped next time (`manager.go:1357-1358`; `TestInterruptedAtBoot`, PASS). Session id, usage, name and draft are there too.
- **Subagent records and threads [V]** (`TestShutdownWritesSubagents`, PASS).
- **Owed subagent results stay owed [V]** and travel with the next human message (`TestLoadClosesOpenPermissions` asserts `SubOwed` after the restart and delivery on the next Send; `TestShutdownDuringCarryingTurn`, PASS).
- **Boards, groups, defaults, catalogs [V]** (`state.json`, board folders).
- **Chat tokens [V]**: a chat's MCP token is in `chat.json` and resolved after the scratch restart.

### Lost

- **The running turn [V]**: its process is ended. Nothing resumes it; a chat with no process starts one only on a human Send (`delivery.go:101-119`; `TestNoProcessResultsWaitForHuman`, PASS).
- **Open permission requests [V]**: closed as denied at the next load (section 1).
- **Running subagents [V]**: app-spawned ones are stopped at shutdown and their result is not owed (`delivery.go:42-53`, `endParent`). Native ones still marked running are marked stopped at the next load (`subagents.go:62-66`; `TestLoadStopsRunningSubagents`, PASS).
- **In-memory state [V]**: thread versions (restart at 0), the hold flag, a start-error text, subagent extra tokens (`tokens.go:143`), the MCP contact log (`mcp.go:97-103`), pi bridge run handles.
- **After a crash or SIGKILL instead of SIGTERM [V for what is on disk mid-turn, I for the rest]**: unsettled items are not on disk; `turnActive:true` was written at Send (`manager.go:843`, `873`), so the chat still shows as stopped.

## What a user would notice

For a server that had no page for a while:

- A chat that needed nothing from the user finished its turn. The reply, tool cards, token counts and the automatic name are all there when the page comes back.
- Nothing marks that chat as "finished while you were away". It is simply idle with new content.
- A Claude or Cursor chat that asked for permission is still waiting at "approval", however long the gap was (as far as the server is concerned). It did no further work and accepted no new message. The card is in the thread and can still be answered. pi chats never wait this way.
- Board work an agent attempted in the gap did not happen. The agent was told the board is not open and, in the no-client case, told not to retry. The reply usually says so. The board file is unchanged.
- If the connection was stalled rather than closed, each board call the agent made took 30 s to fail, with the text "the board did not answer tool in 30s".
- A board call in flight when the connection dropped failed. It is not repeated when the page returns.
- On a slow link, a board edit can appear on the board although the agent reported that the board did not answer (inferred, see section 4).
- Subagent results that came in during the gap were handed to the parent agent by the server itself, unless the chat was waiting for permission, was held or had no process.
- While the page is not the active client it can read everything but change nothing: each send, stop, approve or save is refused with `not_active`.
- If the server was restarted during the gap:
  - a chat that was working shows "Stopped" with the note "Stopped: the app was closed while the agent was working." (possibly also "The agent stopped: …");
  - a pending permission card shows as denied;
  - a running tool card has no result;
  - the chat continues in the same agent session with the next message.
- Stopping a server that has no page takes no 2-second wait.

## Unknowns that remain

- **Agent-side permission timeout**: whether Claude Code's `can_use_tool` or Cursor's `session/request_permission` gives up after some time. Not shown in the repo; not testable without real CLIs.
- **When Claude's auto mode and Cursor ask at all**: how often a card appears in practice.
- **Whether an agent's MCP client retries** a failed or slow `tools/call`, and whether it has its own timeout shorter than the server's 30 s.
- **Time to detect a dead connection**: about 150 s for an idle one is inferred from Go's keep-alive defaults; with unsent data it depends on the OS. Not measured. Until then the client counts as active.
- **Page behaviour after a gap with unsaved board edits**: the server overwrites the scene with whatever the active client PUTs, with no revision check. Whether a returning page reloads the scene first or uploads its stale copy is page code I did not trace.
- **Double error note after a stop**: whether a real agent's exit is processed before the server exits (timing race; shown only with the fake).
- **The broadcast reordering race** in section 3 is read from the code, not reproduced.
- **What the agent CLIs keep of a cut turn** in their own session files, and so what the resumed session remembers.
