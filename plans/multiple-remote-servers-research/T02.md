## 2. Reconnect

**`checkServer({fetch,url,timeoutMs=1000})`** (`lib.js:137-149`): `GET <origin of url>/api/hello` with `cache: 'no-store'` and `AbortSignal.timeout(1000)`; true only if HTTP ok and JSON body has `app === 'ai-whiteboard'`; never rejects. It is called with the **main process's global `fetch`** (`main.js:125`), i.e. Node's fetch, not the window's session. [V]
- Consequence: this probe does not carry the renderer session's cookies, proxy settings, client certificates or any auth the page has. [I — Node's global fetch vs. Chromium's network stack; Electron offers `net.fetch`/`session.fetch` for the latter, https://www.electronjs.org/docs/latest/api/net]
- `/api/hello` returns `{app, version, pid, webVersion}` (`internal/server/server.go:195-198`); the desktop uses only `app`. [V]

**`createReconnector`** (`lib.js:160-264`), constants `lib.js:129-133` (pinned by `reconnect.test.js:94-99`):
- `start(url)` begins a loop: `check(url)` every **2 s**; a successful check resets the count; **3 failures in a row** → `relaunch()`. [V]
- `failLoad(code)` (wired to main-frame `did-fail-load`, `main.js:94-96`) → `relaunch()` at once for any code except `-3` (ERR_ABORTED). [V]
- `relaunch()`: `launch()` → on a URL, `load(url)`; then resume checks after 2 s. If `launch` or `load` rejects, retry `relaunch` every **5 s** forever. Never two launches at once (`launching` flag); `generation` counter drops stale checks/launches after `stop`/`start`. [V]
- `stop()` cancels all timers; called on window `closed` (`main.js:101`) and on `before-quit` (`main.js:207`). After a cancelled quit it is restarted by `onQuitCancelled` → `resumeAfterCancelledQuit` (`main.js:135-138`, `lib.js:396-400`). [V]
- Wiring in `main.js:124-130`: `check` = `checkServer`, `launch` = `findServer({env, bin, args, execFile})` (the same function start-up uses), `load` = `reloadURL` (`main.js:113-119`: sets `appOrigin`, `mainURL`, `win.loadURL(url)` without showing/focusing). [V]
- No dialog and no UI from the reconnector: "the page already shows that it is disconnected" (`main.js:121-123`). The page has its own reconnect: `EventSource` reconnects by itself (`web/src/conn.ts:21`). [V]
- It is one reconnector for one URL; `start(next)` while running only replaces the URL (`lib.js:243-250`). [V]

**What is specific to a local, launchable server**
- The recovery action is `launch`, which starts a process on *this* machine (`launch.go:60`). For a remote server there is nothing equivalent the app can run today. [V]
- With `AIWB_URL` set, `launch()` degenerates to "return the same URL" (`lib.js:125`), so recovery becomes: after 3 failed 1-s probes (≈6 s), `win.loadURL(sameURL)`; if that fails, again every 5 s. This is the only existing "remote-like" behaviour. [V from code; not run]
- The thresholds (1 s timeout, 3 misses) are loopback-sized. Over a WAN or tunnel, three slow answers within ~6 s trigger a **full page reload** of a server that is in fact alive. [I]
- A reload by the reconnector is itself an unload: if the page has pending saves, `beforeunload` cancels it and the close-flush path runs (10 s flush, then the "Board changes are not saved" dialog) — see §4. So "no dialog" is not strictly true when saves are pending and the server is down. [I — follows from `lib.js:362-390` and `web/src/main.tsx:14`; not run]
- After a relaunch the local server may come back on a **different URL** (the reconnector adopts whatever `launch` prints, `lib.js:221-224`; test `reconnect.test.js:124-134`). For a remote server the address is user-configured and should not silently change. [V for current behaviour]
- The rest is server-agnostic and reusable as is: the probe (`checkServer`), the timer/generation machinery, `failLoad`, `stop/start`. `launch` and `load` are injected, so a per-server reconnector with a different "bring it back" function fits the existing shape. [V that they are injected, `lib.js:160-169`]

## 4. Quit and close flush

**Contract with the page (both sides)**
- Page: `beforeunload` → if `hasPendingSaves()`, start `flushAll()` and `preventDefault()` (`web/src/main.tsx:14`); exposes `window.aiwbFlush = () => flushAll().then(() => !hasPendingSaves())` (`web/src/main.tsx:15-17`); also flushes on `visibilitychange: hidden` and `pagehide` (`main.tsx:12-13`). [V]
- Electron: a prevented `beforeunload` silently cancels the close / Cmd+Q / reload and emits `will-prevent-unload`; calling `event.preventDefault()` there forces the unload (`electron.d.ts:17859-17864`). [V doc]
- `attachCloseFlush({app, win, dialog, flushTimeoutMs = 10_000, onQuitCancelled})` (`lib.js:355-391`):
  - `win.on('close')` sets `closing = true` (fires before `beforeunload`, `lib.js:359-361`); `quitState(app)` sets `quitting = true` on `before-quit`, once per app via a `WeakMap` (`lib.js:314-326`). [V]
  - On `will-prevent-unload`: remember `wasClosing`/`wasQuitting`, clear both flags (the action is cancelled), then `flushed(win, 10 s)` = `win.webContents.executeJavaScript('window.aiwbFlush ? window.aiwbFlush() : false', true)` raced against the timeout; true only if it resolves exactly `true` (`lib.js:330-344`). [V]
  - Flushed → redo the same action: `app.quit()` if it was a quit, `win.close()` if a close, else `win.webContents.reload()` (`lib.js:387-389`). [V]
  - Not flushed → window-modal warning "Board changes are not saved. / The server did not answer. Close anyway and lose them?" with `Cancel` / `Close anyway` (`lib.js:373-380`). `Close anyway` sets `force` so the next `will-prevent-unload` is let through once (`lib.js:363-367,385`). `Cancel` on a quit, when no newer quit began meanwhile, calls `onQuitCancelled` (`lib.js:381-384`). [V]
- `main.js` side: `before-quit` sets `quitting = true` and stops the reconnector (`main.js:205-208`); `onQuitCancelled` sets `quitting = false` and `resumeAfterCancelledQuit({win: mainWindow, url: mainURL, reconnector})` (`main.js:135-138`), which restarts checking only if the window is still open and has a URL (`lib.js:396-400`). [V]
- With no pending saves none of this runs. "Nothing here touches the server" (`lib.js:354`). [V]
- Second flush user: the web client's own "Restart server" calls `window.aiwbFlush` before `POST /api/restart` (`web/src/version.ts:54`). [V]

**How it generalises to several loaded pages**
- Several **windows**: already designed for it. One `quitState` per app; each window has its own `closing`/`force`; test `closeflush.test.js:193-202` shows a quit resumed from the second of three windows. [V]
- Gaps with several windows (all [I], derived from `lib.js:362-390`, not run):
  - Each window that has pending saves cancels the quit independently and each handler calls `app.quit()` when its own flush is done. A second window whose page also prevents unload cancels that re-issued quit again and re-issues it later. It should converge (each round one more page has nothing pending), but the order is uncoordinated.
  - Each unreachable server produces its own dialog, each up to 10 s after the quit, each with its own "Close anyway". The dialog text names no server ("The server did not answer", `lib.js:376`).
  - `wasQuitting` is read from shared state that the first handler clears (`lib.js:369-371`); a second window's handler running after that may see `quitting === false` and treat a quit as a plain close (`win.close()` instead of `app.quit()`), leaving the app running with other windows open.
  - `onQuitCancelled` in `main.js` resumes one reconnector for one window (`main.js:137`); with N servers it must resume all that `before-quit` stopped.
- Several pages in **views**: the `beforeunload`-driven mechanism is documented as not respected for `BrowserView` (§3c), and `flushed(win, …)` addresses `win.webContents` only (`lib.js:333`). The flush would have to be driven from the main process over a list of webContents. `flushed` itself is easy to generalise (it only needs a `webContents`). [V for the code shape; I for the conclusion]
- **Switching** in one window: missing "continue to another URL" resume action (§3a). [I]
- Trust note: `executeJavaScript` runs `window.aiwbFlush` in the page's own world, so the page fully controls the answer and can delay a quit up to 10 s per attempt. With a remote server's page this is a (minor) lever for that server over the app's quit. [I]

## 5. Links and origin

- `linkAction(url, appOrigin)` (`lib.js:272-283`): `'stay'` = http(s) URL whose `origin` equals `appOrigin`; `'open'` = any other http/https/mailto URL; `'drop'` = everything else and unparsable URLs. Exact origin equality: scheme + host + port; `http://127.0.0.1:9999/` is "outside" when the app is on `:4747` (`links.test.js:8-12`). [V]
- `attachLinkHandlers(webContents, shell)` (`lib.js:289-308`): `setWindowOpenHandler` always returns `{action:'deny'}` — the app never opens a second Electron window from the page — and sends allowed URLs to `shell.openExternal` (default browser); `will-navigate` to anything but `'stay'` is prevented and, if allowed, opened externally. One `appOrigin` per attached webContents, initially `null` (so before `setAppURL` everything leaves or is dropped). [V]
- `setAppURL(url)` must be called "with every server URL before the window loads it" (`lib.js:288,304-306`); `main.js` does it in `loadURL` and `reloadURL` (`main.js:105,116`). [V]
- So "the app" = whatever origin was last passed to `setAppURL`, i.e. the last URL from `launch`/`AIWB_URL`. There is no allow-list of known server origins and no check that the origin is loopback. [V]

**What breaks or needs care with several origins**
- **A link from server A's page to server B's origin leaves the app**: it is `'open'`, so it goes to the system browser (same as `http://127.0.0.1:9999/` today, `links.test.js:10`). If cross-server links should switch servers inside the app, `linkAction` needs the set of registered origins and a new outcome. [V for current behaviour]
- **Order dependence when switching**: `setAppURL(new)` must precede `loadURL(new)`; in between, in-page navigations on the *old* origin are treated as external (test `links.test.js:78-85` shows the old origin is opened outside right after the move). [V]
- **`will-navigate` covers main-frame, user/page-initiated navigation only.** It is not emitted for programmatic `loadURL` or in-page (hash) navigation (`electron.d.ts:17745-17750`). There is no `will-redirect` or `will-frame-navigate` handler (grep of `desktop/`: only `will-navigate`, `did-fail-load`, `will-prevent-unload`, `close`, `closed`). So a **server-side HTTP redirect** during `loadURL(serverURL)` to another origin is not checked against `appOrigin`, and **sub-frame** navigations are unguarded. Low relevance for a loopback server the app launched; relevant when the URL is user-typed and the server is another machine. [V that the handlers are absent; I for the redirect consequence — Electron documents `will-redirect` as the event for that case, https://www.electronjs.org/docs/latest/api/web-contents#event-will-redirect]
- `shell.openExternal(url)` is called with a URL chosen by page content, filtered to http/https/mailto (`lib.js:291-293`). The filter is origin-independent, so it keeps working unchanged. [V]
- The reconnector can move `appOrigin` by itself (a relaunched local server on a new port, `main.js:116`). With a server list, the local server's origin is therefore **not a stable identifier**; identify servers by something other than origin. [V for the behaviour; the advice is opinion]

**Where a server list could live, given what exists** (facts, not a choice)
- Electron `userData`, next to `window-state.json`: the only place the desktop already writes; per desktop install; needs new read/write code (pattern for testability: inject `fs`/path like the other helpers). [V that it exists and is used; rest I]
- `~/.ai-whiteboard` on the desktop's machine: owned by the Go server; the desktop only *reads a path* there today (`lib.js:42-44`) and never writes. A list there would be visible to the local server and to a browser tab, but mixes "this machine's server data" with "this desktop's view of other machines". [I]
- The web client's storage: localStorage is per origin, so a list stored by one server's page is invisible to another server's page and to the main process before any page is loaded; it cannot drive start-up. [I]
- Secrets (tokens, passwords, if the transport needs any): Electron has `safeStorage` for OS-keychain-backed encryption of strings (`electron.d.ts:12035-12058`; https://www.electronjs.org/docs/latest/api/safe-storage). Nothing in the app uses it today. [V]

**Session / storage partition with several origins**
- All windows use the **default session**: no `partition` and no `session` usage anywhere in `desktop/` (`main.js:8` imports only `app, BrowserWindow, dialog, ipcMain, shell`; `webPreferences` at `main.js:50,85-89`). "Default is the default session" (`electron.d.ts:19565-19572`). [V]
- A `partition` starting with `persist:` gives a separate persistent session; pages with the same partition share it (`electron.d.ts:19565-19572`, `12510-12522`; https://www.electronjs.org/docs/latest/api/session). A session is the unit for "cookies, cache, proxy settings, etc." (same URL) and for permission handlers (`ses.setPermissionRequestHandler`, `electron.d.ts:13501-13509`). [V doc]
- In one shared session, between two server origins:
  - localStorage / sessionStorage / IndexedDB: separate per origin (scheme+host+port) — web platform rule. [I — standard same-origin policy, not Electron-specific, not run]
  - Cookies: scoped by host, **not by port**, so two servers reached as `127.0.0.1:<portA>` and `127.0.0.1:<portB>` (e.g. through tunnels) would share cookies. The app uses none today, so this only matters if the remote transport adds cookie auth. [I — RFC 6265 behaviour, not run]
  - HTTP cache, proxy configuration, certificate decisions, the permission handlers: one per session, shared. [V doc for "per session"; I for the consequences]
  - Granted permissions: Electron approves all permission requests by default when no handler is set (https://www.electronjs.org/docs/latest/tutorial/security#5-handle-session-permission-requests-from-remote-content), so there is nothing per-origin to share or isolate today. [V doc]
- **Origin = storage identity.** A server's drafts, selection and layout are keyed by its origin. If a remote server is reached through a local forwarded port that can differ between runs, its localStorage is lost, or picked up by whichever server gets that port next. Either the origin per server must be stable, or each server gets its own `persist:` partition so storage follows the server rather than the port. [I]
- The local server's origin can also change (port from `server.json`/`-port`, `main.go:266-285`), with the same effect today for the single server. [I]

**In use**
- Main window: `contextIsolation: true`, `nodeIntegration: false`, `preload: desktop/preload.js` (`main.js:85-89`). `sandbox` is not set → default `true` since Electron 20 (`electron.d.ts:19597-19604`); `webSecurity` not set (default on). [V; defaults V by doc]
- Starting window: `contextIsolation: true`, `nodeIntegration: false`, no preload, loads only an inline `data:` URL (`main.js:50,64`). [V]
- Navigation guard: `will-navigate` + `setWindowOpenHandler` deny/open-external (§5). [V]
- **None of the following exist**: Content-Security-Policy (no header in Go non-test code, no `<meta>` in `web/index.html`), `session.setPermissionRequestHandler` / `setPermissionCheckHandler`, `will-redirect` / `will-frame-navigate` guards, `certificate-error` / `login` handlers, IPC sender validation, `app.on('web-contents-created')` hardening, a custom protocol. [V — greps of `desktop/`, `internal/`, `cmd/`, `web/index.html`]
- The current safety argument is the server's, not Electron's: it binds `127.0.0.1` only (`cmd/ai-whiteboard/main.go:125`) and `guard` rejects any request whose `Host` is not `127.0.0.1:<port>` or `localhost:<port>` and requires the active client's `X-AIWB-Client` header on mutating `/api` calls (`internal/server/guard.go:14-38`). [V]
  - Side fact for the transport task: that Host check uses the **server's own port**, so a page reaching a remote server through a forward on a different local port (`Host: 127.0.0.1:<other>`) gets 403 "bad host" as the code stands (`guard.go:26-31`). [V for the code; the tunnel scenario is I]

**What changes when the page comes from another machine**
- Today the loaded page is code from the app's own bundle (`Contents/Resources/web`, served by the bundled binary — §10), over loopback. With a remote server, the page's JavaScript is **whatever that machine serves**, possibly a different version of the web client, and — if loaded over plain `http://` to a non-loopback address — modifiable on the network. Electron's guidance: load remote content only over secure transport (https://www.electronjs.org/docs/latest/tutorial/security#1-only-load-secure-content). [V doc; I for applying it here]
- **The preload API becomes reachable by that page.** `window.aiwbDesktop.openServerLog()` → `shell.openPath(~/.ai-whiteboard/server.log)` on the user's machine (`preload.js:6-8`, `main.js:191`). Today's damage is small: fixed path, no arguments, opens a local text file in the default app; the page gets no content back. But the handler does not check who calls it, and Electron's checklist asks for both: don't expose Electron APIs to untrusted content (https://www.electronjs.org/docs/latest/tutorial/security#20-do-not-expose-electron-apis-to-untrusted-web-content) and validate the sender of every IPC message (https://www.electronjs.org/docs/latest/tutorial/security#17-validate-the-sender-of-all-ipc-messages). **Any API added for this feature** (list servers, add/remove/switch, open tunnel) would by default be exposed to every server's page through the same preload — a remote page could then enumerate or change the user's server list unless handlers check the sender's origin or that API is exposed only to a local, app-owned page. [V for current surface and docs; I for the forward-looking risk]
- With `contextIsolation` and the default sandbox, the page cannot reach Node or `ipcRenderer` directly; it gets only what `contextBridge` exposes (`electron.d.ts:19439-19451,19597-19604`). That protection holds for remote pages as it does now. [V doc]
- **Permissions**: with no handler, a remote page's requests (notifications, media, clipboard-read, …) are auto-approved (security doc §5 above). [V doc]
- **`shell.openExternal`** is driven by page content but limited to http/https/mailto (`lib.js:279-282,291-293`); a remote page can open arbitrary web URLs in the user's browser, as the local one can. [V]
- **Quit/close**: a page controls `beforeunload` and the `aiwbFlush` answer and so can delay or (via the dialog) interrupt a quit (§4). [I]
- **Main-process probes**: `checkServer` fetches `<origin>/api/hello` from the main process every 2 s to whatever URL is registered (`lib.js:139`), with Node's fetch — no cert pinning, no auth, no proxy from the session. [V code / I consequences]
- A remote page is same-origin with its own server only; it cannot script the local server's page (different origin), but it can still *send* simple cross-origin GETs to `http://127.0.0.1:4747` from inside the app. The local server's guard (Host check, custom header, no CORS answers — `guard.go:14-18`) is what stands in the way, as for any web page in a browser. [I]

## (a) Unknowns that would change the plan

1. **Does a hidden or detached `WebContentsView` page keep working as a server's active client?** (EventSource alive, agent board edits applied by Excalidraw off-screen, `visibilitychange` behaviour, timer throttling.) Decides whether window model (c) is viable and whether (a) silently stops agents on the non-visible servers. Needs a prototype; not run.
2. **Is `will-prevent-unload` respected for `WebContentsView` in Electron 44?** The docs I read state it is *not* respected for `BrowserView` (`electron.d.ts:17866-17868`) and say nothing explicit about `WebContentsView`. Decides whether flush-before-close for model (c) can reuse the `beforeunload` mechanism or must be driven from the main process.
3. **Does a programmatic `win.loadURL(otherServer)` with pending saves go through `beforeunload` → `will-prevent-unload`, and what happens to the `loadURL` promise?** I inferred yes (and that the current handler then *reloads the old page*); not run. Decides how much of close-flush must change for model (a).
4. **What origin will a remote server have in the app?** (`http://127.0.0.1:<forwarded port>`, `https://host`, a custom scheme…) — from the transport task. It determines localStorage identity and stability (§7), whether cookies/cache are shared (§7), whether `guard`'s Host check passes (§8), and how risky the preload exposure is (§8).
5. **Can the GUI-launched app use the user's SSH setup** (ssh-agent socket, `~/.ssh/config`, PATH) if a tunnel is spawned from Electron? Not tested.
6. **Multi-window quit ordering** with several pages that have pending saves (§4): derived from reading the code; the actual sequence of `before-quit` / `close` / `will-prevent-unload` across windows in Electron was not run.
7. **Version skew**: how old a remote server's web client may be relative to the desktop app, and whether it may lack `window.aiwbFlush` (then `flushed` resolves `false` → the "not saved" dialog on every close with pending saves, `lib.js:333,342`). Policy question for the plan.
8. Whether `checkServer` should keep using Node's `fetch` (no session cookies/proxy/certs) for remote servers — depends on (4).

## (b) Implications — my opinion

- The smallest true statement about the current design is: **"server" = one URL string, copied into three closures, plus one global recovery action (`launch`)**. The feature needs a real server record (stable id, name, kind local/remote, URL or how to obtain it, how to recover it) and per-server instances of reconnector, link origin and flush state. The helpers in `lib.js` are already factories with injected dependencies, so this is mostly a `main.js` restructuring (singletons → a collection) plus new pure modules, not a rewrite of the helpers.
- **Do not key anything on origin.** Origins move (the local port can change after a relaunch; forwarded ports may differ per run), and localStorage follows origin. A per-server `persist:<id>` partition would decouple each server's page storage, cache and permissions from its address and from the other servers; that looks like the cleanest answer to §7, at the cost of the local server's existing localStorage (drafts, selection, layout in the default session) needing to stay where it is — keep the local server on the default session.
- **Recovery must be a per-kind strategy**: local = today's `launch`; remote = re-establish the transport (if any) and reload only when the page itself is dead, with more tolerant probe timings than 1 s × 3. Reloading a live remote page because three probes were slow would be a regression compared with letting the page's own `EventSource` reconnect.
- **The preload is the main security decision.** Today's single, argument-less call is harmless enough, but the feature's natural additions (list/add/remove/switch servers, open the log) must not be callable by a remote server's page. Two workable shapes: (1) server-management UI lives in Electron-owned UI (menu and/or a local page) and server pages keep only today's API, with `openServerLog` gated to the local server's origin; or (2) sender-origin checks on every handler. (1) also solves "the switcher must exist when no server is reachable" and "each server serves a different client version", which an in-page switcher cannot.
- **Close-flush needs one coordinator, not N independent handlers**, whichever window model is chosen: flush all loaded server pages, show one dialog that names the servers that did not answer, then perform the pending action (quit / close / reload / *switch*). The current per-window handlers work for one page and are racy-by-design for several (§4).
- The window models trade off against one hard product fact: **a server whose page is not loaded cannot have its boards edited by agents** (`README.md:41-42`). Model (a) (switch one window) is the smallest change but stops agent board edits on every server except the visible one; (b) and (c) keep them alive, (b) with code the helpers already support, (c) with the two unknowns above. I am not choosing; the plan should state this consequence explicitly next to whichever model it picks.
- The user-visible strings and affordances tied to the local machine need an inventory pass in the plan: start error dialog and its log button (`main.js:146-148`), `Open log` (`Sidebar.tsx:254-256`), the `missing` banner text (`Sidebar.tsx:260-263`), the unsaved dialog (`lib.js:375-376`), fixed window title (`main.js:84`).
- `AIWB_URL` is a ready-made manual test path for "the app showing a server it did not launch" and should be kept; it also shows the gaps cheaply (wrong error wording, reload-on-probe-failure) without building anything.
