**completed**: I built a user-space link simulator (delay, bandwidth cap, stall, cut; validated against known transfers) and ran M1–M6 with the real client in headless Chrome on the direct, good and poor profiles. Main findings: a first load is 37.5 s of blank page on the poor profile (4.0 s on good) because of the 8.9 MB uncompressed main.js; a board save that fails on a cut link is never retried after the reconnect; a save of a 1.35 MB scene takes 11 s on the poor profile, longer than the desktop's 10 s close-flush limit; T06's inference is confirmed (the agent is told "the board did not answer tool in 30s" while the edit is applied and later saved). Not run: a real ssh tunnel and Electron; the scratch server, simulator and scratch directory are gone and the real app was not touched.

# T10 — How the web client behaves over a slow or faulty link to its server

Marks: **[V]** verified by a run, **[I]** inferred (from code, arithmetic or timing), **[U]** unknown.

## Headline findings

- **First load is slow and blank.** 37.5 s of empty page on the poor profile, 4.0 s on good, because `main.js` is 8.9 MB uncompressed. A reload costs 3 round trips (all `304`).
- **A failed board save is never retried.** After a cut and a successful reconnect the edit stays only in the page until the next edit, a flush, or a close. A reload while the link is down loses it.
- **Saves are whole-scene uploads.** One rectangle on a board with a 1 MB image uploads 1.35 MB: 0.6 s on good, 11.0 s on poor. The page shows nothing while the server's file is 11–21 s behind.
- **The desktop's 10 s close-flush limit is too short for the poor profile.** One pending save of the image board takes 11.0 s; two take 20.3 s.
- **T06's inference is confirmed.** The agent is told `the board did not answer tool in 30s`, yet the edit is on the board in the page and reaches the file later. It happens with a stall, and also with no fault at all on an 8 MB board over the poor profile.
- **A stall shows nothing.** Requests and `aiwbFlush()` hang with no timeout and no "Reconnecting…".
- **Opening a long chat downloads the text twice.** `GET …/items` (2.09 MB) plus `GET …/tree` (1.16 MB) took 13.4 s on poor. The code repeats both after every reconnect.
- **Streaming re-sends the item on every delta.** 20 KB of text in 200 deltas produced 2.06 MB of `chat_items` events (103×).

## Set-up used

**Scratch server.** Built from this checkout and started exactly as the brief says: port 41000, MCP 41001, temp `-home`, temp `CURSOR_CONFIG_DIR`, the four agent paths nonexistent. It was restarted once to plant the long thread.

**Link simulator** (one Node process, loopback only, no system network settings):

`page → shaper :41010 (TCP level) → Host-rewriting HTTP proxy :41011 → server :41000`, control on :41012.

- The shaper works on the raw bytes of every connection, as a link or an `ssh -L` channel would.
- Each direction has one queue shared by all connections, served round robin in 1,400-byte segments at the configured rate (token bucket, burst of at most 10 ms).
- Each segment is delivered one one-way delay after it leaves the queue.
- A new connection passes nothing for one round trip (models connection or channel set-up).
- Back-pressure: a source socket is paused while more than 64 KB of it waits.
- **stall** (per direction or both): queue and delay line stop, connections stay open.
- **cut**: all connections destroyed and the listener closed (connection refused, like a dead forward). **uncut** listens again.
- The inner proxy rewrites `Host` only, streams both ways, and logs every request (bytes, status, times).
- Not modelled: packet loss, jitter, reordering.

**A simulator bug, found and fixed.** The inner proxy first used the same pattern as T04's `rproxy.js` (`r.on("close", () => res.destroy())`). Under back-pressure that can cut a response short; I saw one `ERR_CONTENT_LENGTH_MISMATCH` on `main.js`. I changed it to destroy only when the upstream response is incomplete, repeated the one affected run (good/small in M3), and ten further downloads were complete. The M1 runs came before the fix, but their byte counts show complete transfers. Anyone reusing `/tmp/aiwb-t04/rproxy.js` under load should know about this.

## M5. A link that breaks while the board has unsaved changes

All runs on the good profile and the small board unless said otherwise. The link was cut or stalled 0–1 ms after mouse-up, before the 500 ms save timer.

**Cut, then restored after 8 s, no further edit [V]**

- The sidebar shows "Reconnecting…".
- The save fails after 3 ms (`TypeError: Failed to fetch`). It is logged to the console only; nothing about the board appears on screen.
- After the link is back, the event stream reconnects within about 3 s (`EventSource` retries every 3 s), receives hello and snapshot, and "Reconnecting…" disappears.
- **The save is not retried.** For 32 s after the link came back there was no PUT. The server's file had 81 elements, the page 82.
- `hasPendingSaves()` is true throughout (probed through the `beforeunload` handler, which was prevented).
- That handler's `flushAll()` then wrote the scene (92 ms, 200) and the file had 82. Only a further edit, a flush or a close attempt writes it.

**`aiwbFlush()` across the cut [V]**

| When | Result |
|---|---|
| During the cut | `false` after 2 ms; pending stays true |
| After the link is back | `true` after 53 ms; the file is updated; pending is false |

**Reload [V]**

- **After the link is back, nothing retried:** Chrome shows its "leave site" dialog (`beforeunload` prevented). The handler's flush had already saved the scene before I accepted it. The reloaded page has the edit.
- **While the link is cut:** same dialog. After accepting, Chrome shows "This site can't be reached". **The edit is lost**: once the link is back the page loads the file's version (84 elements; the page had 85).
- **[I]** In the desktop app the same reload or close goes through `attachCloseFlush`: flush returns false at once, then the "Close anyway and lose them?" dialog. Read from `desktop/lib.js:356-389`; not run.

**Reload during a slow save** (poor, image board, reload 1.6 s into an 11 s save, no cut)

- **[V in the simulator]** The dialog appears. After accepting, the new page loads. The old page's upload still completed 10.6 s later, because the simulator had already taken the whole body, and the file got the edit. A second small PUT from the leaving page was refused with `409 not_active`.
- **[U]** Whether a real tunnel completes an upload whose sender is gone. It depends on where the bytes are buffered.
- **[I]** The reloaded page fetched the scene about 9 s before the file changed, so it shows the board without the edit. Its next save would overwrite the file, since there is no revision check (T06). From timing; the page's element count was not checked.

**Stall instead of cut** (both directions, 40 s) **[V]**

- No "Reconnecting…", no error, nothing on screen for the whole stall. The PUT stays pending; there is no timeout on any request.
- `aiwbFlush()` was still pending after 11 s.
- **[I]** The desktop's 10 s limit would pass and its dialog appear.
- On resume the PUT completed (39.6 s) and the file had the edit. The stream did not reconnect.

**A typed, unsent message and its draft across a cut [V]**

| Step | Composer | `aiwb.draft.<chat>` in `localStorage` | `draft` in the server's `chat.json` |
|---|---|---|---|
| Typed, 1.5 s later | text | empty | saved (47 ms) |
| Typed more, cut at once | full text | full text | old text (PUT failed) |
| Typed during the cut | full text | full text | old text (PUT failed again) |
| Link back for 23 s, nothing typed | full text | full text | **old text: no retry** |
| Then one more keystroke | full text | empty | full text (93 ms) |
| Or then a reload | full text | empty | full text (saved again on open) |

- The text is kept: the reconnect snapshot does not reset the composer, and the local copy survives a reload.
- The server's copy stays stale until the next keystroke or a reload.
- **[I]** The local copy is per origin, so it is found again only if the server keeps the same local port.

## M6. Streaming cost

Temporary test in `internal/chats` (`fakeAgent`, a real bridge, an SSE client counting raw bytes); deleted afterwards. **[V]**

| Text | Deltas | `chat_items` events | Bytes | × the text | Largest event |
|---|---|---|---|---|---|
| 20 KB | 200 | 203 | 2,062,816 | 103× | 20,208 |
| 20 KB | 400 | 403 | 4,095,216 | 205× | 20,208 |
| 40 KB | 400 | 403 | 8,125,216 | 203× | 40,208 |
| 80 KB | 800 | 803 | 32,250,016 | 403× | 80,208 |
| 20 KB | 20 | 23 | 233,732 | 11.7× | 20,207 |

- Scaling: bytes ≈ deltas × (text ÷ 2 + about 200 B). At a fixed delta size that is quadratic in the length of the item.
- **[I]** On poor (250 KB/s to the page) the 20 KB case is 8.2 s of link time and the 80 KB case 129 s. Whether the page falls behind depends on how fast a real agent streams.
- **[U]** Real agents' delta sizes and rates were not measured.
- **[I]** A compressing transport helps only for short items. Modelled as one zlib stream flushed per event (my stand-in for `ssh -C`, computed in Node, not run through ssh): 20 KB/200 deltas shrinks to 35 KB (1.8× the text), but 80 KB/800 deltas is still 11.0 MB (137×). Deflate's 32 KB window no longer sees the previous copy once the item is longer than that.

## What a user of a remote server would notice

- **First open of a server:** an empty window for about 4 s on a good link and about 37 s on a poor one. Later opens take well under a second.
- **Opening a board with a 1 MB image or 2,000 elements:** under a second on a good link, 5–7 s on a poor one.
- **Opening a long chat:** about 2 s on a good link, about 15 s on a poor one.
- **Drawing on a good link:** each stroke is on the server about a second later. Each stroke uploads the whole board, images included.
- **Drawing on a poor link, big or image board:** the server is 10–20 s behind and nothing on screen says so.
- **Closing the window right after drawing on such a board:** the close waits 9–20 s.
- **After a connection drop with a fresh edit:** "Reconnecting…" appears and goes away, and the edit stays on screen but is not on the server until the user changes the board again or closes the window. Reloading while the connection is down loses it.
- **A frozen connection:** the app looks normal; nothing saves and nothing warns.
- **Agent edits:** normally one round trip. On a poor link the first call on a big board takes about 6 s.
- **An agent can say the board did not answer while its change is visible on the board.** The change is saved later.
- **A message being typed** survives a drop and a reload.

## Candidates for work in the feature

Each is a measured problem, not a design.

1. **First load:** 37.5 s on poor, 4.0 s on good. 8.9 MB of uncompressed `main.js` and no loading state in `index.html`. gzip would send 2.7 MB.
2. **A failed board save is not retried after the reconnect.** The edit exists only in the page and is lost on a reload while cut.
3. **No visible save state.** A 10–20 s lag, a failed save and a stalled save all look the same as "saved".
4. **Whole-scene PUT for every change:** 1.35 MB and 11 s on poor for one rectangle on an image board; 10.8 MB uploaded for eight rectangles. The same PUT follows every agent `apply`.
5. **The desktop close-flush limit (10 s)** is shorter than one save on poor/image (11.0 s) and than two (20.3 s). Its dialog says "The server did not answer".
6. **Late tool reply:** the agent gets the 30 s timeout while the edit is applied and later saved. The page's late reply gets HTTP 200 and nobody is told. Reproduced with a stall, and with no fault on an 8 MB board.
7. **A stall is invisible and unbounded.** No request has a timeout and `aiwbFlush()` hangs.
8. **Opening a chat downloads its text twice** (`items` and `tree`): 3.25 MB and 13.4 s on poor for the long thread. The code repeats it on every reconnect.
9. **Streaming re-sends the whole item per delta:** 103× the text for 20 KB in 200 deltas, growing quadratically.
10. **`read_board` on a large board uploads a 193 KB reply:** 1.8 s on poor, 3.4 s while a save is uploading.
11. **A draft that failed to save is not retried on reconnect.** Minor: it is kept locally and saved on the next keystroke or reload.
12. **The snapshot is small** (72 KB for 50 boards and 200 chats, about 170 KB with real catalogs). It is not a problem at these sizes.

## Unknowns that remain

- **A real `ssh` tunnel was not run** (sshd is off, per T04). Its buffering, its behaviour with `-C`, and how it treats an upload whose sender closed are not measured. The zlib figures are a model.
- **Electron was not run** (forbidden). Its cache per origin, and the close-flush dialog over a slow link, are read from `desktop/lib.js`.
- **Real agents' streaming rate and delta size**, and so whether the page falls behind on a slow link, or the 4,096-message buffer overflows.
- **Whether an agent retries** after "did not answer", and duplicates the edit.
- **Packet loss and jitter** are not simulated; only delay, rate, stall and cut.
- **The refetch of `items` and `tree` on reconnect** is read from the code, not timed in a reconnect run.
- **The stale scene after a reload during a slow save** is inferred from timing.
- **Real snapshot size** is my measurement plus the catalog size read from the user's `state.json`.
