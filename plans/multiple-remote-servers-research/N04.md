# N04: what binds a chat to its server, and what a chat on another server would need

A chat is bound to its server in four ways: its record and history are files in that server's data folder, its
agent is a child process of that server working in a folder of that machine, it reaches its tools through that
server's loopback MCP listener, and everything else it names (group, board, run, the chat it was forked from,
defaults, catalogs) is an id or a path that only that server can resolve. The chat's slice of the API is 19
routes and 9 event types, all served on one event stream per server that goes to one "active client" only;
there is no per-chat stream and no observer role, so whoever follows a server live (the page in A, the local
server in B) takes that server away from any other client. The web client is single-server in three module
singletons (one `call`, one `EventSource`, one store keyed by bare ids) with 82 API call sites behind them. The
Go server has no client code for another server; its seam to an agent process is at the level of raw agent
events and local processes, which is lower than what a remote server's API gives (finished thread items), so
"a remote server as one more agent adapter" does not fit that seam without loss. Board chats cannot cross
servers as the code stands: a board chat must name a board that exists on the server that runs the agent, and
board tools are answered by that server's active page. Runs are tied to the machine more tightly than chats
(git worktrees, a set-up script, delivery into the folder's branch).

## S1. The chat's slice of the API

**Answer.** 19 HTTP routes are a chat's own, plus 4 that a chat's composer uses and that read other server
state (folder listing, plan usage, hello, state). All server events travel on one stream, `GET /api/events`,
to the active client only; a chat's live content is `chat_items` events applied on top of a thread fetched
with `GET /api/chats/{id}/items`. There is no per-chat stream and no subscription: every user chat's events
are sent, whichever chat is on screen.

All routes are in `internal/server/server.go` **[code]**. "Active" = refused with 409 `not_active` unless the
caller is the active client (`internal/server/guard.go:32-35, 41-53`).

## S3. Board chats and board tools across servers

**Answer.** All seven board tools are answered by the active client page of the server that runs the agent;
none reads the server's disk directly. The scene itself is read and written by the page over HTTP from that
same server. So today "agent on R, board on L" has no path: R refuses to create the board chat, and R's tool
calls go to R's active client with R's board id. A plain chat works without any of it and loses only the
board tools.

**Trace of `read_board`** **[code]**
1. The agent was started with `MCP{URL: http://localhost:6006/mcp, Token}` and `BoardID` (`manager.go:982-988`;
   `internal/boardapi/endpoint.go:5-11`). Claude gets it as an MCP config with a bearer header
   (`internal/claude/claude.go:206`), pi in its environment, Cursor in its ACP session **[report: T01 §7]**.
2. `POST /mcp` `tools/call` on the loopback listener → `Relay.dispatch` (`internal/boardapi/mcp.go:314-347`):
   the token resolves to the chat; a chat with no board is told "not available on this chat" (`mcp.go:341-344`).
3. `Relay.Call` (`mcp.go:58-87`) looks the chat's board up in the local board store and calls
   `Bridge.Call("tool", {chat, branch, board, name, args}, 30 s)`.
4. `Bridge.Call` (`bridge.go:204-233`) sends an `rpc` event to the active client, or fails at once with
   `ErrNoClient` when there is none.
5. The page: `conn.ts:91-100` → `runTool` (`web/src/board.ts:307`). `read_board` loads the scene with
   `GET /api/boards/{id}/scene` unless it is cached (`board.ts:28-47`), formats the elements and returns text
   (`board.ts:315-322`).
6. The page posts `POST /api/rpc-reply`; `Bridge.Reply` hands it to the waiting call (`bridge.go:236-243`).

**Trace of `apply`** **[code]**: steps 1–4 the same; the page loads the scene, runs `applyChanges` on the
live canvas or on the stored scene (`board.ts:336-344`, `207-216`; `web/src/apply.ts:78`), then saves with
`PUT /api/boards/{id}/scene` 50 ms later (`board.ts:244`). `boards.Save` overwrites the file
(`internal/boards/boards.go:194-208`) **[report: T06 §4]**.

| Tool | Needs the page | Uses the server's disk |
|---|---|---|
| `list_boards` | yes; answered from the page's store (`board.ts:311-313`) | no |
| `read_board`, `apply`, `delete_elements` | yes | through the page: `GET`/`PUT …/scene` |
| `get_view`, `show_board` | yes; they read and change the page's selection (`board.ts:324-334, 378-390`) | no |
| `create_board` | yes; the page calls `POST /api/boards` (`board.ts:370-376`) | through the page |
| `spawn_subagent`, `stop_subagent`, `list_subagent_models` | no (`mcp.go:329-334, 352-376`) | the manager's own state |
| run tools | no (`internal/boardapi/runs.go:84`) | the run service |

**What would have to be true for an agent on R to work on a board stored on L** (facts; each is false today)

- R must accept a chat that has board tools without the board being in R's store. Today `Create` returns
  `boards.ErrNotFound` (`manager.go:767-770`) and `Relay.Call` reads the board from R's store (`mcp.go:73`)
  **[code]**.
- R's tool call must reach a page that holds L's scene. R sends it to R's own active client only
  (`bridge.go:204-215`) **[code]**.
- The board id in the call must be L's id, and `list_boards`, `create_board` and `show_board` must mean L's
  boards, not R's **[inferred]**.
- Under **A** the local page is R's active client (S4), so R's `rpc` events already arrive at the page that
  has L's boards. The page would have to answer them from L's state: `runTool` reads one store and one scene
  cache keyed by bare board id (`board.ts:20, 307-313`) and saves through the one `api` (`board.ts:104`).
  Needed: the first bullet on R, and a per-server routing of `rpc` in the page **[inferred]**.
- Under **B** R's active client is L's server, which would have to forward each `rpc` to its own
  `Bridge.Call` and so to L's page: two 30 s waits in a row, two "no client" cases, and R still needs the
  first bullet **[inferred]**.
- In both, R's own page (a person at R) cannot be R's active client at the same time, and R's own board
  chats would send their tool calls to the local page or to L's server, which hold none of R's scenes unless
  they load them **[inferred from `bridge.go:190-215`]**.

**A plain chat on a server**: yes. A chat with no board gets the MCP endpoint and the spawn family only
(`manager.go:980-988`; `mcp.go:328-346`), no board context (`manager.go:1269`), no whiteboard prompt
(`agent.go:37`). It loses the seven board tools, `@board` mentions and element references. It needs no page
at all to run **[report: T01 §3]**.

## S4. The single-active-client rule under A

**Answer.** A page (or any program) that opens `GET /api/events` on a server becomes that server's active
client within 3 s and ends the session of whoever was using it. There is no read-only or per-chat way to
follow a server live. Without the role, only GETs work.

- The rule: one active client; a new client id becomes pending, the active one gets `release_request`, and
  after 3 s at most the newcomer is promoted and the old one gets `superseded` (`bridge.go:92-116`,
  `279-302`) **[code]**.
- For a second person or machine on that remote server: their page shows "Opened in another window" and
  unmounts its whole UI; "Use here" takes the role back, which cuts the first one off in turn **[report: T03
  §2]**. Their unsaved board changes depend on answering within 3 s **[report: T01 §3]**.
- While the local page holds R's role, R's board chats send their tool calls to it (S3) **[code:
  `bridge.go:204-215`]**.
- Routes that refuse a caller that is not the active client: every non-GET under `/api` except
  `/api/client/*` and `/api/rpc-reply` (`guard.go:41-53`). For a chat: create, send, draft, configure,
  rename, move, interrupt, permission, fork, open, label, delete, archive (the "Active" column of S1). The
  header `X-AIWB-Client` must equal the active id (`guard.go:32-35`) **[code]**.
- What works without the role: `GET /api/state`, `/hello`, `/chats/{id}`, `/items`, `/tree`, `/context`,
  `/subagents/…/items`, `/dirs`, `/usage/…`, `/boards/{id}/scene` **[code: `guard.go:45-47`]**. So a chat can
  be followed by polling `GET /api/chats/{id}/items` (the answer carries `version`), without live updates and
  without sending, stopping or answering permission asks **[inferred]**. The existing plan's attention
  component already relies on polling `GET /api/state` (plan section 4).
- The same rule applies to L's server under B if it reads R's stream **[inferred]**.
- A permission ask raised while nobody holds the role waits **[report: T01 §3, T06 §1]**.

## S6. The Go server as a client (for B)

**Answer.** There is no code in which the server calls another HTTP server, apart from probing its own
`/api/hello` on loopback at start-up (`cmd/ai-whiteboard/main.go:316-340`), and nothing abstracts where an
agent runs: all three adapters start a local child process in a local folder. The seam (`agent.Spawner` /
`agent.Agent`) could formally take a fourth implementation, but what a remote AI Whiteboard server exposes is
one level higher than what the seam expects, and much of what the chat manager does around the seam is local
by nature.

**The seam** **[code: `internal/agent/agent.go`]**
- `Spawner.Spawn(SpawnOptions) (Agent, error)` (`:73-76`); options: chat id, session id, resume, `Cwd`,
  model, effort, `MCP{URL, Token}`, `BoardID`, `Subagent`, `Dir` (the chat's folder), `MCPTools`,
  `Unattended`, `ReadOnly`, `NeedHistory` (`:31-66`).
- `Agent`: `Events() <-chan Event`, `Send([]ContentBlock)`, `Interrupt()`, `Decide(requestID, allow)`,
  `Close()` (`:141-152`).
- 16 event kinds: session, catalog, thinking, text start/delta/whole, tool start/input delta/input/result/
  denied, permission request, usage, turn end, exit, subagent patch (`:156-173`), with cost and token
  fields on turn end (`:190-210`).
- Optional interfaces found by type assertion: `Forker` (`SpawnFork` from another session's files,
  `DiscardFork`, `:103-121`), `SplitReader` (`:80-82`), `ContextSplitter` (`:124-126`).
- Adapters: `claude.Spawner` starts `claude` with `cmd.Dir = o.Cwd` (`internal/claude/claude.go:280-319`);
  `cursor.Spawner` an ACP process (`internal/cursor/cursor.go:112-124`, `acp.go:63-64`); `pi.Spawner` an RPC
  process plus a Unix-socket bridge in the data folder (`internal/pi/pi.go`, T01 §7). Each checks the folder
  with `os.Stat` first (`claude.go:290`, `cursor.go:123`).

**How `internal/chats` drives it** **[code]**
- `manager.go`: `Create` writes `chat.json` and starts nothing (`:763-815`); `sendOn` checks, starts or
  forks the process, composes the turn's blocks (run or board context, subagent results, quotes, text),
  appends the user item to the transcript, then `ag.Send` (`:1178-1325`); `pump` turns each `agent.Event`
  into transcript items and broadcasts (`:996`); `Decide`, `Interrupt`, `Stop` call the agent (`:1680-1778`).
- `spawn.go`: app-spawned subagents are further `Spawn` calls on the same map of spawners, any agent kind,
  in the parent's folder (`:152-157, 321-336`).
- `owned.go`: chats owned by a run (`CreateOwned`, `SendOwned`, `WaitOwned`, `StopOwned`, `:352-624`).
- `delivery.go`: handing finished subagents' results to the agent in a turn of its own (`:242-320`).
- `restart.go`: starting a fresh fork's process again after a model change, from the source session
  (`:25-135, 195-260`). It is not about server restarts.
- Server restart: a chat whose turn was running is loaded as `interrupted` and shown "stopped"
  (`manager.go:617, 441-442, 517-521`); nothing resumes it. `Shutdown` flushes history and closes every agent
  (`:1994-2030`); `agent.EndAll` ends what is left (`main.go:226`).

**Could a remote server sit behind the seam, with a mirror chat on it?** **[inferred from the code above]**
- `Spawn` → `POST /api/chats` + `PATCH` (folder, model, effort) on R; `Send` → `POST …/messages`;
  `Interrupt` → `…/interrupt`; `Decide` → `…/permission`. These map.
- `Events()` does not map cleanly. R's stream gives `chat_items` updates, i.e. finished or growing thread
  items (`transcript.go:41-45`), and `chat`/`branch_state` views, not text deltas, tool-input deltas or turn
  ends. A remote adapter would have to turn item updates back into agent events for `pump` to turn them into
  items again, or the manager would need a second kind of chat that takes items as they are and skips `pump`.
- `Send` gets the composed blocks; R's `sendOn` composes its own (context, quotes, notices) and records its
  own user item, so quotes and context would be applied twice or have to be passed through as R's own fields.
- Cost and tokens arrive on the seam (`agent.go:190-210`); R's API does not send a user chat's cost (S1).
- `Forker`, `SplitReader`, `ContextSplitter` work on local session files; over the API they would be
  `POST …/fork`, `GET …/context`, and branches (`target` on send), each a second mapping with R's ids.
- R's reading of its stream makes L's server R's active client (S4).

## S7. Runs

**Answer.** A run needs everything a chat needs from its server and more that exists only on the server's
machine. Under A a run is one more thing the page reads from R (15 more routes and 4 more event types).
Under B the local server would have to drive agents on R through an engine that calls its chat manager and
git directly, which the API does not expose.

- A run's orchestrator and task agents are chats owned by the run, created and driven through a Go
  interface, not HTTP: `CreateOwned`, `SendOwned`, `WaitOwned`, `StopOwned` (`internal/runs/host.go:20-36`;
  `internal/chats/owned.go:352-624`). They live in `runs/<run>/agents/<id>` (`paths.go` `RunChatDir`) and
  are not in the snapshot's chats (`app.go:37`) **[code]**.
- It works in git worktrees under `<parent of the data folder>/aiwb-run-work/<run>` (`paths.go` `RunWork`,
  `RunWorkDir`; `internal/runs/attempt.go:90`; `internal/rungit/worktree.go:91`), runs a set-up shell command
  (`internal/rungit/setup.go:60`), and delivers by merging into the folder's branch (`service.go:1193`;
  `internal/runs/deliver.go:84-117`) **[code]**.
- Its set-up is its own: agent kind, three model tiers, folder, settings (`RunView`, `run.go:227-243`;
  `PATCH /api/runs/{id}`), with defaults per group in `state.json` (`model.go:111`). It is blocked when the
  agent's program is missing on that machine (`host.go:110`) **[code]**.
- Its agents get run tools over the same loopback MCP (`internal/boardapi/runs.go:84`) **[code]**.
- After a server stop a run halts and continues at the next start (`main.go:223, 235`), unlike a chat
  **[code]**.
- Routes: `POST /api/runs`, `GET`/`PATCH`/`DELETE /api/runs/{id}`, `/draft`, `/start`, `/stop`, `/resume`,
  `/apply`, `/delivery`, `/detail`, `/goal`, `/tasks/{tid}/brief`, `/tasks/{tid}/attempts/{n}/report` and
  `/changes`, `/notes/{v}` (`server.go:849-996`); events `run`, `run_removed`, `run_detail`, `run_activity`
  (`conn.ts:49-52`). A chat on a run is `POST /api/chats {agent, run}` (`server.go:514-521`) **[code]**.

## Unknowns that remain

- Whether the owner wants a remote chat to sit in a local group or on a local board. S2 and S3 show the first
  needs a local placement record (A) or comes free (B), and the second needs server changes in both.
- Whether the remote server is used by one person from several machines or by several people. It decides how
  much the single-active-client rule (S4) hurts; the code has no user notion.
- How R should treat an API client that is not a page: no observer or per-chat stream exists (S4). What that
  would cost in `editorbridge` and `guard` was not designed here.
- Behaviour of a page against a server of another build was reasoned from code, not run (S5).
- Whether a `fetch`-read event stream with a secret header behaves like `EventSource` for reconnect and the
  20 s pings in Electron and browsers (S5); not run. N01/N02 own the secret.
- How large the events are on a slow link for a long thread, and whether polling `…/items` is a usable
  fallback (S4); not measured.
- I did not read the three adapters' session-file handling in full; "a fork needs the source session on the
  same machine" rests on the `Forker` contract in `agent.go:86-121`.

## Implications (opinion)

Kept apart from the facts; this is input for the design, not the design.

- **B as a full mirror is the one I would not choose.** Its appeal is real (the page stays single-server, a
  remote chat is a local record in a local group, the secret never reaches the page, browser-only use
  works), but the seam it would use carries raw agent events and local files, while R's API gives thread
  items; so it means a second kind of chat in the manager plus a mapping for every feature added since
  `8722065` (branches, forks, runs), and two histories of one chat to reconcile. It also still takes R's
  active-client role.
- **A is the architecture that matches "server is a property of the chat"**, and it keeps one record per
  chat. I would take it with three limits that the facts suggest:
  1. **Pass the remote calls through the local server** (`/api/servers/<id>/…` forwarded with the secret
     added, events included) rather than connecting the page cross-origin. The page's state work of S5 is
     the same, but CORS, the Host rule, the header on the event stream, the secret in page JavaScript and
     browser-only use all stop being problems, and the list of servers and secrets lives in the local
     server's data folder (S8) with the agents' reach to it as the one thing to guard. This is a pass-through,
     not B's mirror: the local server keeps no chat state.
  2. **Remote chats are plain chats** at first: no board on another server (S3). A board chat stays on the
     server that stores the board.
  3. **Runs stay on the local server** for now (S7); they can follow once chats work, since under A they are
     the same kind of work.
- **A needs one server change that the plan does not have yet:** a way for a second party to follow and act
  on chats without becoming the one active client (an API client that gets chat events and may call chat
  routes, but is never the target of board `rpc`). Without it A makes every added server unusable from its
  own machine while the app is open (S4). With plain chats only, such a client needs no board role at all.
- To keep the page change bounded I would make the three singletons (`api`, the connection, the server-owned
  part of the store) into one object per server, and let the sidebar show each server's tree as a section,
  not add a server key to every id: ids stay as they are inside their server's object (S5).
- A feature level in hello (already in the plan) becomes necessary, not optional, under A: the local page is
  the one page for every server's build (S5).
- **C stays the fallback** if the state split of S5 is judged too large: it is the cheapest, it is already
  planned and researched, and it keeps board chats and runs working on every server; what it cannot give is
  one sidebar.
