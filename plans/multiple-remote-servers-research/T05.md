One `BaseWindow` held eight views, each loading its own scratch server with the board on screen, for 7 min 20 s. Each view got its own renderer process, although all origins are the same site (`127.0.0.1`).

## E4. Storage per server

- **`localStorage` is separate for two loopback ports in the default session.** **verified** — key written on `127.0.0.1:39711`, read on `:39712` → `null`, read again on `:39711` → the value. Same result with the real servers A and B in E1 (`B sees t05.key = null`).
- **The same origin in two `persist:` partitions has separate `localStorage`.** **verified** — written in `persist:srv1`; `persist:srv2` reads `null`. Storage path: `<userData>/Partitions/srv1`.
- **Partition data survives an app restart.** **verified** — a second app run with the same userData read `partition-srv1-P1` in `persist:srv1`, `null` in `persist:srv2`, and the default session's own value in the default session.
- **Inside a partition, storage is still per origin.** **verified** — `persist:srv1` loading `127.0.0.1:39712` reads `null`, before and after the restart.
- **What this means for a server whose local address changes between runs:** a partition per server does not carry the page state over. If the origin changes (for example a tunnel that gets another local port, or a host renamed), drafts not yet on the server, selection, panel widths and theme start empty, and the old data stays orphaned under the old origin. Keeping state needs a stable origin per server, or the state has to live somewhere else. **inferred** from the verified per-origin result.
- **A cookie for `127.0.0.1` on one port is sent to the other port.** **verified**
  ```
  server :39711 got /c1 with Cookie: t05cookie=set-for-P1
  server :39712 got /c2 with Cookie: t05cookie=set-for-P1
  server :39712 got /c3 with Cookie: t05cookie=set-for-P1; fromserver=39711     (cookie set by the :39711 server with Set-Cookie)
  document.cookie on the P2 page: t05cookie=set-for-P1; fromserver=39711
  ```
  In `persist:srv1` the same origin got no cookie, so partitions do separate cookies. These were session cookies and were gone after the restart.

## What this means for each window model

### (a) One window that navigates between servers
- **Works as is:** switching with no pending saves (E1); state comes back from `localStorage` on return (E1); storage is separate per origin (E4).
- **Needs new code:**
  - A switch with pending saves: flush first, then load. Today it turns into a reload of the same server (E1).
  - `setAppURL` on every switch.
  - A `will-redirect` handler (E1).
  - A preload handler that checks the sender (E5).
- **Cannot work:** the server that is not shown has no page, so its agents get "The board isn't open" (E1). This model cannot keep several servers usable at once.

### (b) One `BrowserWindow` per server
- **Works as is:**
  - Each window stays the active client when minimised, hidden with `hide()` or covered, and applies edits in 0.1–0.9 s (E3).
  - `attachCloseFlush` per window handles close and reload.
  - Quit with all servers answering ends in a quit (E3).
- **Needs new code:**
  - Quit coordination across windows: other windows close before the user answers the dialog, "Cancel" leaves them closed, and one window can get two dialogs, one after it is gone (E3).
  - Everything in `desktop/main.js` that assumes one `mainWindow`, one `mainURL` and one reconnector (by reading).
  - Closing a server's window ends its client, so "keep usable" needs hide-instead-of-close or a clear rule (**inferred** from E1/E2: a destroyed page is no client).
  - Per-window link origin and a sender-aware preload handler (E1, E5).
- **Cannot work:** nothing found.
- Cost: about 200 MB resident per server window (the renderer cost measured in E2; a window was not measured separately, **inferred**).

### (c) One window with one `WebContentsView` per server
- **Works as is:**
  - A hidden view stays the active client for at least 7 minutes with any of the three hiding methods (E2).
  - Edits are answered in under 40 ms and saved in 0.1–0.9 s (E2).
  - `aiwbFlush()` can be called on hidden views (E2).
  - `will-prevent-unload` is emitted and respected for a view's own `reload`, `loadURL` and `close({waitForBeforeUnload:true})`, and `preventDefault()` forces the unload (E2).
- **Needs new code:**
  - Window close and quit must flush every view from the main process, because views are never asked; the `before-quit` version was run and works (E2).
  - `attachCloseFlush` is written against a `BrowserWindow` (`win.webContents`, `win.close()`, by reading), so it needs a view-aware form.
  - Views must be closed explicitly when their window closes, or kept on purpose; otherwise they live until garbage collection (E2).
  - Per-view link origin, `will-redirect`, and a sender-aware preload handler (E1, E5).
  - View bounds on resize, focus and keyboard routing: not tested.
- **Cannot work:** nothing found.
- Cost per kept-alive server: about 200 MB resident (83 MB in Activity Monitor); idle CPU 0.2 % of a core with default throttling, 4.3 % with `backgroundThrottling: false` (E2).

### Opinion
I would pick **(c)**, hiding with `setVisible(false)` and leaving throttling at its default.
- It is the only model where every registered server keeps its client without the user managing windows.
- The hidden pages did everything the product rule needs.
- The missing piece, flushing all views before close and quit, is small and was shown to work.
- Default throttling costs at most about a second on a save, keeps the page's own flush-on-hide, and uses about twenty times less idle CPU than `backgroundThrottling: false`.
- (b) is the fallback: it reuses more of today's close code, but its quit path needs rework anyway, and closing a window silently makes that server unusable for agents.
