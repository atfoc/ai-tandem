## 1. How the client talks to the server

**Requests**
- **V** There is exactly one `fetch` call site: `call()` at `web/src/api.ts:32-42`, `fetch(path, …)` at `:33`. Every path is a root-absolute literal such as `/api/state` (`api.ts:49-101`). No base URL, no `import.meta`, no env or config lookup.
- **V** Every request sends `Content-Type: application/json` and `X-AIWB-Client: <clientId>` (`api.ts:35`), including GETs.
- **V** `clientId = crypto.randomUUID()` at module load, "one per tab load" (`api.ts:23`). It lives in memory only, so a reload makes a new id.
- **V** Errors: a non-2xx answer throws `ApiError(status, body.error ?? statusText)` (`api.ts:26-29, 38`). A network failure is the raw `fetch` rejection. There is no retry, no timeout and no global error handler; each caller decides:
  - sidebar actions show a dialog through `reportError` (`web/src/Sidebar.tsx:87`, `web/src/Dialogs.tsx:16-18`);
  - the composer shows an inline error (`web/src/Composer.tsx:223`);
  - a failed board save is marked `failed` and written again on the next change or flush, with no retry timer (`web/src/board.ts:71-73, 104`);
  - several calls swallow errors with `.catch(() => {})` (for example `web/src/conn.ts:34, 36, 55`).

**Event stream**
- **V** One `EventSource` on `/api/events?client=<clientId>` (`conn.ts:19`). It is a module singleton (`let es`, `conn.ts:14`), and `connect()` closes the previous one (`conn.ts:17`).
- **V** Reconnect is left to the browser: `onerror` only sets `connected: false` (`conn.ts:21`, comment "EventSource reconnects by itself"). The page never calls `connect()` again by itself; only "Use here" does (`conn.ts:69`).
- **V** When the same client id reconnects, the server makes it active again and sends `hello` plus a full `snapshot` (`internal/editorbridge/bridge.go:95-102`). The client then replaces all server-owned state and refetches the open chat (`conn.ts:33, 52-56`; `web/src/store.ts:97-123`; "updates missed while away are not replayed", `store.ts:114`).
- **I** If `/api/events` answers non-200 (for example 403 "bad host", or a proxy error page), `EventSource` fails permanently per the HTML spec and the page shows "Reconnecting…" forever. Evidence: https://html.spec.whatwg.org/multipage/server-sent-events.html (a non-200 response fails the connection, and no reconnect follows). Not run.
- **V** In the desktop app the real recovery path is the shell's reconnector, not the page. It polls `GET /api/hello` every 2 s, and after 3 failures runs the local `launch` and loads the URL that prints (`desktop/lib.js:129-132, 137-149, 160-264`; `desktop/main.js:124-130`). For a remote server's page this would load the local server instead; that is the desktop task's area, noted here because it interacts with the page's own restart flow (§4).

**What the user sees when the server is unreachable**
- **V** On first load: the sidebar shell with "Reconnecting…" and "No chats yet.", and a spinner in the main area (`web/src/App.tsx:37, 67-68`; `Sidebar.tsx:189, 206`). Probe output on `http://127.0.0.1:<port>/` with `/api` answering 404: root text `"AI Whiteboard Reconnecting… + No chats yet. New group Show archived"`.
- **V** After having been connected: the full UI stays, with "Reconnecting…" in the sidebar head. Actions fail one by one. There is no blocking overlay and no "server unreachable" screen.
- **V** If the page itself cannot be loaded, the page has no say: there is no service worker and no offline shell (no `serviceWorker` in `web/src` or in `dist/main.js`).

**Can a server base URL be injected?** Same-origin is assumed in every one of these places (all **V**):

| Place | What is root-relative |
|---|---|
| `web/src/api.ts:33` | `fetch(path)` for every API call |
| `web/src/conn.ts:19` | `new EventSource("/api/events?…")` |
| `web/index.html:16-21` | `/favicon.ico`, `/favicon.png`, `/apple-touch-icon.png`, `/main.css`, `/main.js` |
| `web/src/main.tsx:1` | `EXCALIDRAW_ASSET_PATH = "/"` (fonts under `/fonts/…`, copied by `web/build.mjs:13`) |
| `web/src/version.ts:66`, `web/src/Sidebar.tsx:243` | `location.reload()` |
| `web/src/Markdown.tsx:135-139` | relative links in agent output resolve against the page origin |

- **V** The page must be served at the origin root. A path prefix such as `/servers/a/` would break assets and API calls without code changes.
- **V** All client state is in module-level singletons with no "server" dimension: `clientId`, `es`, the store (`store.ts:67-78`), `scenes` (`board.ts:20`), `lastUsage` (`Composer.tsx:616`), `lastSplit` (`Composer.tsx:673`). One page is one server.

**Could one page talk to a different origin's server?** No, three ways over:
- **V** The server's Host check allows only `127.0.0.1:<port>` and `localhost:<port>` and answers 403 "bad host" otherwise (`internal/server/guard.go:26-31`).
- **V** The server never answers CORS preflights (`guard.go:14-18`), and every client request carries a custom header.
- **I** So every cross-origin `fetch` would be preflighted and blocked, and a cross-origin `EventSource` would be blocked for lack of `Access-Control-Allow-Origin`. Standard CORS behaviour; not run.
- **V** Every non-GET `/api` call other than `/api/client/*` and `/api/rpc-reply` must come from the active client or gets 409 `not_active` (`guard.go:32-35, 41-52`).

## 2. Active / waiting / superseded

**Roles on the page**
- **V** `role` is `connecting | active | waiting | superseded` (`store.ts:24`). It is set from the `hello` event: `active` when `m.active`, else `waiting` (`conn.ts:32`).
- **V** `App` renders only `TakeoverScreen` when superseded and only `WaitingScreen` when waiting. The whole UI (sidebar, canvas, composer) is unmounted in both (`App.tsx:27-29`).

**Takeover sequence**
- **V** A new client id connecting while another is active becomes `pending` and gets `hello {active:false}`. The active one gets `release_request`, and a 3 s handover timer starts (`bridge.go:24, 103-115`).
- **V** The active page runs `flushAll()` then `POST /api/client/release` (`conn.ts:34`). The server promotes the pending client and sends the old one `superseded` (`bridge.go:167-173, 286-302`).
- **V** If the old page does not answer within 3 s it is cut off anyway (`bridge.go:114, 279-283`).
- **V** On `superseded` the page closes its stream, does not reconnect, and shows: "**Opened in another window** — AI Whiteboard is open in another tab or window. Only one can be in use at a time." with a **Use here** button (`conn.ts:35`; `Dialogs.tsx:55-64`).
- **V** "Use here" calls `connect()` with the same client id. The page becomes the pending client, shows "Taking over from the other window…" (`Dialogs.tsx:67-74`), then gets `hello {active:true}` and a snapshot (`conn.ts:69`).
- **V** `server_stopping` (stop or relaunch): the active page flushes boards and posts `/api/client/flushed`; the server waits for that or a timeout (`conn.ts:36`; `bridge.go:247-266`).

**Agents' board edits**
- **V** The page is the only place a scene changes (`board.ts:1-5`). The server relays each board tool call as an `rpc` event to the active client only and waits up to 30 s (`bridge.go:204-233`; `internal/boardapi/mcp.go:27, 63-65`).
- **V** The page runs `runTool` and posts `/api/rpc-reply` (`conn.ts:37, 58-67`; `board.ts:306-393`).
- **V** `runTool` works on boards that are not on screen through the stored scene, loading it on demand (`board.ts:207-216, 316, 338`). The page must be loaded and active; it need not be showing that board.
- **V** No active client: the agent's tool call returns "The board isn't open: the AI Whiteboard window is closed. Board work needs the window open. Tell the user, and don't retry until they ask again." (`mcp.go:30-31, 66-68`; `bridge.go:64, 212-215`).
- **V** A client that disconnects or is superseded mid-call: the call fails with the same error (`bridge.go:121-123, 296, 352-365`).
- **V** If another client is active (for example a browser tab on the server's own machine), the edits run there. The superseded page receives nothing, because server events go to the active client only (`bridge.go:189-200`).
- **V** Chats themselves do not need a page. README: "Quitting the app doesn't stop the server or its running chats" (`README.md:29-30`) and "boards can only be changed while the app (or a browser tab) is open" (`README.md:41-42`).
- **V** Nothing in the page signals attention outside itself: no `document.title` change, no Notification, no badge (grep of `web/src` finds none). A background server whose chat reaches "Needs your approval" (`web/src/ChatView.tsx:233-256`) is silent.

**What this means for a switched-away server**
- **I** If its page is unloaded (one window navigated to another server), plain chats and non-board agent steps continue, but every board tool call fails with the text above.
- **I** If its page stays loaded and active in a hidden view, board edits continue. `get_view` then reports that page's last selection as "what the user is looking at" (`board.ts:323-333`), and `show_board` changes the selection in the hidden page (`board.ts:377-390`).
- **U** Whether a hidden page answers within the 30 s timeout and saves promptly under Chromium/Electron background throttling. The reply path is event- and fetch-driven, but autosave uses `setTimeout` (`board.ts:82-86`, 50 ms after an agent edit at `board.ts:244`). Not tested.

**A stale-scene risk on "Use here"**
- **V** The scene cache is never cleared on a role change or snapshot. `loadScene` returns the cached scene if present (`board.ts:29-30`), and the only deletion is for removed boards (`board.ts:68`; grep for `scenes.(clear|delete|set)` shows only `board.ts:42, 68`).
- **I** A page that was superseded and then takes back with "Use here" (no reload) shows, and can later save, the board as it was before the other client edited it. This matters more for remote servers, where a second client at the server's machine is likely.

- **V** The URL is not used: no router, hash, query or `history` call in `web/src`; the only `location` use is `location.reload()`. A server's page always opens at `/` and restores its place from `aiwb.sel`.

- **V** Ids: boards and groups are a prefix plus 8 random base36 characters (`internal/model/model.go:29-41`); chat ids are UUIDs (`README.md:108`).
- **I** Cross-server id collisions are therefore improbable but not excluded for boards.

**If each server has its own origin**
- **I** All keys are separate per server and nothing leaks. Theme, pane widths and "Show archived" must then be set once per server, and the first paint of a new server's page uses the system theme. Storage is per origin: https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API.
- **I** A server's data stays tied to its origin. If its origin changes (for example a different forwarded port), its selection, unsent drafts and recent folders are orphaned under the old origin.

**If two servers are reached at the same origin at different times** (for example the same forwarded local port reused)
- **V/I** `aiwb.sel`: on the first snapshot, ids that do not exist are dropped and the key is overwritten (`store.ts:103-108`). Safe, but each switch loses the other server's place.
- **V/I** `aiwb.lastChat`: maps merge. Lookups are validated against the current chats (`Sidebar.tsx:44-45`), so it is safe; it only grows.
- **V/I** `aiwb.draft.<chat>`: server A's unsent drafts stay in storage while server B is shown. They are removed only on a successful save or when the chat is deleted (`drafts.ts:71-73`; `store.ts:151`). They are readable by server B's page script, since both pages are the same origin.
- **V/I** `aiwb.dirs`: server A's folders are offered as "Recent" on server B (`Composer.tsx:529, 537-540`). Picking one that does not exist shows the server's error.
- **I** Theme, widths and archived are shared, which is harmless and arguably wanted.
- **I** Two servers shown at the same time on one origin is not possible; an origin is one server at a time.

## 4. Version handling

- **V** Three versions are compared on every `hello` event, that is every connect and reconnect (`conn.ts:32`; `version.ts:27-32`):
  - the page's own `__APP_VERSION__`, stamped at build from `AIWB_VERSION`, default `"dev"` (`build.mjs:8, 19`);
  - the running server's `version`;
  - the on-disk web client's `webVersion`, read from `version.json` in the folder the server serves (`build.mjs:10`; `internal/server/server.go:49-55, 195-198`).
- **V** The rule (`web/src/logic/version.ts:17-22`): no banner if any of the three is `"dev"` or all are equal; "reload" if page ≠ disk; otherwise "restart". Versions are `git describe` strings and are never ordered (`logic/version.ts:1-4`).
- **V** What the user sees, in a banner above the sidebar footer (`Sidebar.tsx:227-272`):
  - "This page is out of date." with **Reload**, which calls `location.reload()`;
  - "New version installed. The server is still running the old one." with **Restart server**;
  - "Restarting…", "Restart failed" with **Retry** and **Open log** (or the log path), and the "program is gone" text.
- **V** Reload triggers: the Reload button (`Sidebar.tsx:243`), and automatically after a restart once `/api/hello` reports a different server version (`version.ts:62-67`).
- **V** Restart flow: confirm if agents are running, flush boards, `POST /api/restart`, poll `/api/hello` every 500 ms for up to 45 s (`version.ts:18-19, 35-70`).
- **V** Static files are served `Cache-Control: no-cache` with a content ETag (`internal/server/client.go:14-17, 38`), so a reload always fetches that server's current build.

**With each remote server serving its own build**
- **V/I** The check only compares a page with its own server and that server's disk. It is correct per server without change, and nothing compares a server with the desktop app or with another server.
- **I** The shell will host pages of different versions at once. A page built before any new shell API existed will not call it, and the only things an old page knows are `window.aiwbFlush` and `window.aiwbDesktop.openServerLog` (§6).
- **I** "Restart server" restarts the remote server on its machine. During the gap the page's own poll tolerates errors (`version.ts:67`), but the desktop reconnector would start the local server after about 6 s (§1).
- **V** The "missing" banner tells the user to "Quit the app and run `ai-whiteboard relaunch`" (`Sidebar.tsx:260-263`), which for a remote server means on the other machine.

**Probe** (headless Chromium from the Playwright cache, `chromium_headless_shell-1243`; `web/dist` built by me; `remote.test` mapped to `127.0.0.1` with `--host-resolver-rules`, so only the origin differs):

|---|---|---|
| `window.isSecureContext` | true | **false** |
| `crypto.randomUUID` | function | **undefined** |
| `crypto.subtle` | object | **undefined** |
| `crypto.getRandomValues` | function | function |
| `navigator.clipboard` | object | **undefined** |
| `navigator.serviceWorker` | object | undefined |
| `showOpenFilePicker` | function | undefined |
| `EventSource`, `localStorage` | work | work |
| **The built app** | renders: "AI Whiteboard Reconnecting… + No chats yet. New group Show archived" | **`#root` is empty; error: "Uncaught TypeError: crypto.randomUUID is not a function"** |

**App code**
- **V (ran)** `crypto.randomUUID()` at `web/src/api.ts:23` runs at module load, so on a non-localhost `http://` origin the whole page fails to start and the window is blank. This is the one hard blocker in the client. MDN marks it secure-context only: https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID.
- **V** `navigator.clipboard?.writeText` in the code-block Copy button (`Markdown.tsx:114`). The optional chaining makes it a silent no-op off a secure context: Copy does nothing and "Copied" never shows. MDN: https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API.
- **V** Not used by the app: `crypto.subtle`, `isSecureContext`, service workers, the File System Access API, Notifications, `window.open`. `document.execCommand("insertText" | "delete")` in the composer (`web/src/RefInput.tsx:157, 211, 238-240`) is not secure-context gated.

**Excalidraw** (`@excalidraw/excalidraw` pinned at `0.18.1`, `web/package.json:11`; installed version confirmed; references are to `web/node_modules/@excalidraw/excalidraw/dist/dev/`)
- **V** Clipboard: feature-detected (`"clipboard" in navigator`, `chunk-4FTI6OG3.js:21221-21223`), with fallbacks to the clipboard event and `document.execCommand("copy")` (`:21505-21545`).
- **I** Off a secure context, keyboard copy and paste still work, but menu "Paste" and "Copy to clipboard as PNG" (`navigator.clipboard.write` with `ClipboardItem`, `:21480-21500`) do not.
- **V** `crypto.subtle.digest("SHA-1")` for image file ids sits in a `try` with a `nanoid(40)` fallback (`chunk-4FTI6OG3.js:24775-24786`).
- **I** Images still work off a secure context, with random rather than content-hash ids.
- **V** Element ids use `nanoid` (`:15018-15022`), which needs only `crypto.getRandomValues`, available everywhere.
- **V** Fonts load from `EXCALIDRAW_ASSET_PATH` resolved against `window.location.origin` (`:4938-4975`; `main.tsx:1`), with a fallback to `https://esm.sh/…` (`:4978`). The app ships them under `dist/fonts` (`build.mjs:13`).
- **V** `EXPORT_SOURCE = window.location.origin` is written into exported files (`chunk-4FTI6OG3.js:285`). The library browser link passes `window.location.origin + pathname` as its return URL (`index.js:10014-10019`). The app does not read the URL hash, so a library return is ignored.
- **V** `EyeDropper` and the file pickers are feature-detected; the bundle references `showOpenFilePicker` and `showSaveFilePicker`.
- **I** Image export falls back to a download link off a secure context.

**Verdict**
- **V** A plain `http://<remote-host>:4747` origin is not viable as the code stands: the page does not boot, and separately the server answers 403 to any Host other than `127.0.0.1:<port>` or `localhost:<port>` (`guard.go:26-31`).
- **V/I** Reaching the page at `http://localhost:<port>` or `http://127.0.0.1:<port>` (a forwarded port or tunnel) is a secure context and passes the Host check when the forwarded port number equals the server's port, since the guard compares host and port. Whether a different local port can pass is a server question for the sibling task. MDN on potentially trustworthy origins: https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts.
- **I** `https://<host>` would also be a secure context for the page, but still fails the Host check today.
- **I** If plain remote http were wanted anyway, the client-side cost is small (replace `randomUUID`, accept degraded clipboard), but all traffic including chat content and permission answers would be unencrypted. That is the transport task's call.

## (a) Unknowns that would change the plan

1. **Does a hidden or background page keep working as the active client?** Not tested: whether rpc replies arrive within the 30 s timeout and whether autosave timers fire under Chromium background throttling in Electron. If it does not, "keep one live page per server" needs throttling turned off in the shell or a different approach. A small prototype settles it.
2. **Which origin each remote server will have.** A distinct stable origin per server makes storage clean (§3). A shared or changing origin (a reused forwarded port) mixes drafts, selection and recent folders, or orphans them. This depends on the transport task.
3. **Whether the server's Host check will accept the address the page is reached at** (a local forwarded port different from the server's own port, or an https name). Server task; the client only needs a secure context and a root-served page.
4. **How old a remote server's web client may be.** The shell can only rely on what that build exposes (`aiwbFlush`, `aiwbDesktop.openServerLog`, `/api/hello`). Whether the plan sets a minimum server version is a product decision.
5. **Is a second client on the remote machine expected** (someone using that machine's own app)? If so, the takeover ping-pong and the stale-scene-after-"Use here" behaviour (§2) become everyday rather than rare.
6. **Do remote servers run non-macOS?** "Reveal in Finder" calls `open -R` and the wording is macOS-specific.
7. **Electron session and partition per server** (whether storage is separated by partition as well as by origin) is the desktop task's area. It would change the §3 conclusions if a partition per server is used, since even a shared origin would then have separate storage.

## (b) Implications (my opinion)

- **Keep "one page = one server"**. Making one page talk to several servers would mean threading a base URL through `api.ts`, `conn.ts`, assets and every module-level singleton, adding CORS to a server whose protection rests on not answering it, and it still could not cope with servers on different builds. The switcher belongs in the shell, outside any server's page. It is also the only place that can show an unreachable server.
- **Prefer one live page per server, kept loaded while hidden, over navigating a single window**, because board tool calls fail the moment a server's page unloads. If the plan navigates one window instead, it should say plainly that board agents on the other servers stop drawing, and it must run the flush before every switch.
- **Reach every server through a `localhost` origin with its own stable port (a tunnel), or https.** Plain `http://host:4747` is dead on arrival for the client (§8), besides being unencrypted. A stable per-server local port also gives each server its own storage origin, which avoids the §3 mixing with no client change.
- **Small client changes worth planning for**, all optional and only effective on servers that have the new build:
  - show which server and machine the page belongs to (nothing does today);
  - hide or reword "Reveal in Finder" and "Open log" when the server is not on this machine, which needs the page to learn that, for example from the shell;
  - make the path-bearing texts say which machine they are on;
  - drop cached scenes on takeover-back;
  - replace `crypto.randomUUID` with a `getRandomValues`-based id so a misconfigured origin shows an error instead of a blank window.
- **Attention across servers needs a channel that does not exist yet.** A hidden server's "Needs your approval" or finished turn is invisible. The shell can poll `GET /api/state` per server (GETs are exempt from the active-client rule) without any page change, which also works for old builds.
- **The shell's reconnector and "Open log" are local-only by construction** and must become per-server before a remote page is loaded in the window. Otherwise a remote hiccup of about 6 s replaces the remote page with the local server.
- **Tests**: the connection, role and storage code has no unit tests. If the feature touches it, the plan should add tests there, since the only existing coverage is the paid, manual e2e run.
