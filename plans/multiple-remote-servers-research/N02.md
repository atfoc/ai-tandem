# N02 — The desktop app as client of an HTTPS server with a self-signed certificate and a header secret

I ran an Electron 44 harness against a TLS front with a self-signed certificate that demands `X-AIWB-Secret` on every request, placed before an unchanged scratch AI Whiteboard server; a second scratch server played "the local server". By default every kind of request fails with `ERR_CERT_AUTHORITY_INVALID` (Node: `DEPTH_ZERO_SELF_SIGNED_CERT`). `session.setCertificateVerifyProc` can accept exactly one certificate fingerprint for one host name in one session and covers page loads, `fetch`, `EventSource` and main-process `ses.fetch`; its verdict is cached per host name and certificate for 30 minutes, and nothing I tried clears it earlier. The secret can be sent in three working ways without the page holding it: `webRequest.onBeforeSendHeaders` (covers navigation, sub-resources, `fetch`, `EventSource` and preflights), a custom scheme handled in the main process, or `ses.fetch` in the main process; a page can also send it itself with a streamed `fetch`, which needs CORS answers from the server. One page held live streams and made API calls to two servers at once. `safeStorage` works in the unpackaged harness on this Mac without a prompt. A "test connection" in the main process can tell about ten outcomes apart.

Marks: **[run]** verified by run (excerpt given), **[code]** read from code, **[doc]** read from documentation, **[inferred]**, **[not run]**.

## S1. Self-signed certificate in Electron, per server

**Answer.** By default nothing connects. `session.setCertificateVerifyProc` covers pages and main-process requests of one session and can be limited to one host name and one fingerprint; it cannot see the port, and its verdict is cached for 30 minutes. `app.on('certificate-error')` sees host, port and window and is asked on every new connection, but does not cover main-process requests. The command-line switches are global. Node's `https` pins exactly with `ca` plus a no-op name check.

### Default behaviour **[run]**

| Request | Result |
|---|---|
| Page load `https://aiwb-remote.test:44211/` | `did-fail-load {"code":-202,"desc":"ERR_CERT_AUTHORITY_INVALID"}`; `loadURL` rejects with `code:"ERR_CERT_AUTHORITY_INVALID", errno:-202`; the window then holds `chrome-error://chromewebdata/` with an empty body |
| `fetch` from L's page | `TypeError: Failed to fetch` after 2 ms; no console message |
| `EventSource` from L's page | `error` event, `readyState=0` (it keeps retrying) |
| `net.fetch`, `ses.fetch` | rejects, `message: "net::ERR_CERT_AUTHORITY_INVALID"` |
| `net.request` | `error` event, same message |
| Node `https.get` | `code: "DEPTH_ZERO_SELF_SIGNED_CERT"`, "self signed certificate; if the root CA is installed locally, try running Node.js with --use-system-ca" |
| Node global `fetch` | `fetch failed`, `cause.code: "DEPTH_ZERO_SELF_SIGNED_CERT"` |

The certificate with the wrong names gives the **same** codes (`ERR_CERT_AUTHORITY_INVALID`, `DEPTH_ZERO_SELF_SIGNED_CERT`): the name mismatch is not reported separately when the certificate is also self-signed. **[run]**

### Ways to accept it

| Mechanism | Scope | Page load / `fetch` / `EventSource` | Main-process request | One host + one fingerprint? |
|---|---|---|---|---|
| `ses.setCertificateVerifyProc` | one session (partition) | yes / yes / yes | `ses.fetch` of that session yes; `net.fetch` (default session) and other partitions no | yes, by host **name** (no port) |
| `app.on('certificate-error')` | whole app; the handler gets the `webContents` | yes / yes / yes | **no** | yes, by URL (host and port) and by window |
| `--ignore-certificate-errors` | whole app, set at start | yes | yes (also `net.fetch`) | no: accepts any certificate. Unsuitable |
| `--ignore-certificate-errors-spki-list=<base64 SHA-256 of the public key>` | whole app, set at start | yes | yes | one key, any host; the list cannot change while the app runs **[inferred]**. Unsuitable for a list the user edits |
| Node `https`, `rejectUnauthorized:false` | that request | – | yes | no: accepts anything |
| Node `https`, `ca: <the certificate>` | that request | – | yes | that certificate, and the name must be in it |
| Node `https`, `ca` + `checkServerIdentity: () => undefined` | that request | – | yes | exactly that certificate, any name |

**What the verify proc receives [run]:** the host name (**no port, no URL**), Chromium's own result as text and number, `isIssuedByKnownRoot`, and the certificate (`data` = PEM, `subjectName`, `issuerName`, `serialNumber`, `validStart`, `validExpiry`, `fingerprint` as `sha256/<base64>`, which the harness converts to the colon-hex that `openssl` prints). Callback values: `0` accepts; `-2` makes the request fail with `net::ERR_FAILED`; `-3` keeps Chromium's result; another net error number is passed through (`-150` gave `net::ERR_SSL_PINNED_KEY_NOT_IN_CERT_CHAIN`).

**Every request or cached? [run]** Cached. The proc ran once per session, host name and certificate; neither further requests nor new connections called it again:
```
5 five more fetches, same connection: new proc calls 0
5 three fetches each on a new connection: new proc calls 0
```
The cached verdict, accept or reject, could not be changed from the app:
```
accepted first 200; proc calls 1
proc now says reject, nothing cleared 200; proc calls 0
after setCertificateVerifyProc(new function) 200; proc calls 0
after ses.clearCache() / clearAuthCache() / clearHostResolverCache() / clearStorageData() / clearData(): each 200; proc calls 0
after set(null) then set(new) 200; proc calls 0
wrong-names cert, proc rejects net::ERR_FAILED  →  proc would now accept: net::ERR_FAILED; proc calls 0
```
The cache is per session (each fresh in-memory session in S6 called its own proc) and is not kept across a restart with the same userData and partition (second start: `proc calls 1`). Electron's documentation says only "The result of this procedure is cached by the network service" **[doc]** (https://www.electronjs.org/docs/latest/api/session#sessetcertificateverifyprocproc). **How long the cache lives [run]:** 30 minutes from the moment the verdict was cached, whether or not requests are made meanwhile. A 35-minute run made one request per minute, each on a new connection:
```
[0.091]    proc(A) {"hostname":"aiwb-remote.test","fp":"61:6A:73:3F","accept":true}
[60.144]   TTL minute 1 200; proc calls 0        … minutes 2–29 the same …
[1800.264] proc(T) {"hostname":"aiwb-remote.test","fp":"61:6A:73:3F","accept":true}
[1800.267] TTL minute 30 200; proc calls 1
[1860.276] TTL minute 31 200; proc calls 0       … to minute 35 the same
```
So a changed rule reaches a certificate already decided on after at most 30 minutes, or at restart.

**`certificate-error` [run]:** the handler gets `webContents`, the full URL, the error, the certificate and `isMainFrame`. It fired for the page load, for `fetch` and for `EventSource`, and again for **every new connection** (three fetches on new connections: three events), so a changed decision applies at once. With a rule "host `aiwb-remote.test:44212` and fingerprint of `good`", port 44211 with the same certificate was refused: the port is visible here. It does **not** fire for main-process requests: with a handler that accepts everything, `ses.fetch` on a fresh session still failed with `net::ERR_CERT_AUTHORITY_INVALID`. (A `ses.fetch` succeeded only when it reused a connection a page had just opened.) The event is app-wide; `wc.session` tells sessions apart.

**Node `https` in the main process [run]:**
```

2 ca: the certificate itself {"status":200}
2 ca, name not in certificate {"code":"ERR_TLS_CERT_ALTNAME_INVALID"}      2 ca: good, server presents another certificate {"code":"DEPTH_ZERO_SELF_SIGNED_CERT"}
3 ca: wrong-names cert + checkServerIdentity: () => undefined {"status":200}

```
So: with `rejectUnauthorized:false`, `checkServerIdentity` is **not called**, and a pin written there lets the secret go to the wrong server. A fingerprint check in the socket's `secureConnect` handler stopped the request before the front saw it in this run; that it always wins the race is **not verified**. `ca` + no-op `checkServerIdentity` needs neither.

**Reading the certificate before trusting it [run]:** `tls.connect({rejectUnauthorized:false})` followed by `getPeerCertificate()` and `socket.destroy()` gives the fingerprint and names in 1 ms and sends no HTTP request (front log empty):
```
{"authorized":false,"authorizationError":"DEPTH_ZERO_SELF_SIGNED_CERT","fingerprint256":"61:6A:73:3F:…:11:B2","subject":{"CN":"aiwb-remote.test"},

```
`tls.checkServerIdentity(host, cert)` is the only place where "wrong names" became visible as its own error.

**Wrong names [run]:** Chromium hands the proc the same `net::ERR_CERT_AUTHORITY_INVALID`. A proc that compares only the fingerprint accepts it (`9c … {"status":200}`): a pin ignores names.

**Certificate changes after acceptance [run]** (front switched from `good` to `good2`):
```

8 new connection after change: proc {"hostname":"aiwb-remote.test","fp":"4E:90:5B:60…","verdict":-2} → {"error":"net::ERR_FAILED"}

```

With `certificate-error` the changed certificate was refused the same way. With `--ignore-certificate-errors` it was accepted silently; with the SPKI switch it was refused.

## S2. What "checkbox for self-signed certificates" can mean

| Meaning | Implemented by | What an attacker on the VPN can do |
|---|---|---|
| **(a) Skip verification for this server** | verify proc `callback(0)` for that host name whatever the certificate (**[run]** `9b … {"status":200}` with the wrong-names certificate); for Node requests `rejectUnauthorized:false` **[run]** | Anyone who can get between client and server (spoofed DNS or ARP, a rogue host with the address) presents any certificate at any time and receives the first request **with the secret header**, and from then on everything. **[inferred]** from: the secret travels in each request **[run]** |
| **(b) Accept exactly the certificate seen now** | fingerprint read with `tls.connect` or taken from the proc's request, stored with the entry; verify proc compares host name and fingerprint; Node requests use `ca` + no-op name check **[run]** | Only at the moment of adding, and only if the user does not compare the shown fingerprint with the server's. Later an interceptor fails the handshake, so no request and no secret are sent (**[run]** for the refusal; "no secret sent" follows from the failed handshake **[inferred]**). A regenerated or renewed certificate makes the entry fail until accepted again |
| **(c) Box off** | no proc, or `callback(-3)`: Chromium's verifier decides. Self-signed is refused with `ERR_CERT_AUTHORITY_INVALID` **[run]** | Needs a certificate that verifier trusts for that name. That such a certificate passes was **[not run]** (it needs a root in the owner's keychain). Node's `https` uses its own root list, not the OS store, unless `--use-system-ca` (the error text says so **[run]**); so "what the OS trusts" means Electron's `net`, not Node **[inferred]** |

Limits of (b) when built on the verify proc **[run]** (S1): no port, so two servers under one host name share one set of accepted fingerprints; and the cached verdict, so removing a server or its fingerprint reaches a certificate already decided on only after up to 30 minutes, or at restart.

## S3. Sending the secret header

**Answer.** All three ways work. From a cross-origin page the header forces a preflight, so the server must answer `OPTIONS` **without** the secret and send CORS headers; a streamed `fetch` then replaces `EventSource`. Injection by the shell covers every request kind including preflights and makes a plain cross-origin `EventSource` work; the page cannot read the value, but every page in that session gets it attached. In the main process `ses.fetch` reads the stream directly; a custom scheme lets the page keep `fetch` and `EventSource` while the main process adds the header.

### (i) The page sends the header (L's page → front) **[run]**

| Case | Result | Front saw |
|---|---|---|
| CORS off, `fetch` with header | `TypeError: Failed to fetch`; console: "blocked by CORS policy: Response to preflight request doesn't pass access control check: No 'Access-Control-Allow-Origin' header…" | `OPTIONS /api/hello secret=none acrh=x-aiwb-secret` only |
| CORS off, `mode:'no-cors'` with header | opaque response, status 0 | `GET secret=none`: the header is **dropped silently** |
| CORS on, `fetch` with header | `200`, `type:"cors"`, body readable | `OPTIONS … secret=none`, then `GET … secret=ok` |
| CORS on, streamed `fetch` of `/api/events` | `status 200, ct text/event-stream, headMs 1, firstMs 1`, events `hello{active:true}` and `snapshot` | |
| CORS on, `EventSource` | `error`, `readyState=2` (the 401 ends it; no retry) | `GET /api/events… secret=none` |
| CORS on, but `OPTIONS` also needs the secret | `Failed to fetch`; "preflight … does not have HTTP ok status" | `OPTIONS secret=none` |

The streamed `fetch` also delivered later events and the server's 20-second `: ping` comment without delay (S4) **[run]**. Unlike `EventSource` it does not reconnect by itself **[inferred]**.

### (ii) The shell injects the header **[run]**

```js
ses.webRequest.onBeforeSendHeaders({ urls: ['https://aiwb-remote.test:44211/*', …] },
  (d, cb) => cb({ requestHeaders: { ...d.requestHeaders, 'X-AIWB-Secret': SECRET } }));
```

| Request | Injected? |
|---|---|
| Navigation to the front (`/`) | yes: `GET / secret=ok`; listener: `type=mainFrame` |
| Sub-resources | yes: `GET /main.css secret=ok` (`stylesheet`), `GET /main.js secret=ok` (`script`) |
| Same-origin `fetch` and `EventSource` of the real web client | yes: `GET /api/events?client=4efd35fb-… secret=ok`, `GET /api/hello secret=ok`; the page showed "AI Whiteboard … No chats yet." |
| Cross-origin `fetch` from L's page, front with CORS | yes, `200` with no secret in the page's code |
| Cross-origin `EventSource` from L's page, front with CORS | **works**: `openMs 1`, `hello{active:true}`, `snapshot`, `finalState 1` |
| Preflight | yes: listener `OPTIONS 44212/api/groups type=xhr`, front `OPTIONS /api/groups secret=ok`; a front that demands the secret on `OPTIONS` was satisfied |
| Main-process `ses.fetch` in that session | yes: listener `type:"other", wc:null`, front `secret=ok` |

- **Front without CORS:** the page gets `Failed to fetch`, but the request **arrived with the secret and was executed**: `44211 GET /api/events?client=s3ii-y secret=ok origin=http://127.0.0.1:44201`. CORS hides the answer, not the effect.
- **Any page in the session gets the secret attached.** A page of a third origin (`http://localhost:44201`) made a `no-cors` GET: `44211 GET /api/hello secret=ok`. The filter is by target URL only. The listener does receive what is needed to narrow it: `frameOrigin=http://localhost:44201 wc=4 referrer=…` (`details.frame.origin`, `details.webContentsId`, `details.resourceType`).
- **Can the page read the value?** Nothing found: `{"requestHeaders":[],"responseHeadersVisible":["content-length","content-type"],"perfEntryKeys":["finalResponseHeadersStart"],"cookie":""}`. A server that echoed request headers would reveal it; the front does not. **[run]** for the checks, **[inferred]** that no other API exposes it.
- A session has one `onBeforeSendHeaders` listener: "Only the last attached `listener` will be used" **[doc]** (https://www.electronjs.org/docs/latest/api/web-request). Several servers in one session therefore need one listener that looks the secret up by URL.

### (iii) Main process only **[run]**

```
iii.1 ses.fetch stream read in main {"status":200,"ct":"text/event-stream","firstChunkMs":12,"firstEvent":"data: {\"active\":false,\"type\":\"hello\",\"waiting\":tru"}
iii.2 API call while the stream is open {"status":200,"body":"{\"groups\":[],\"boards\":[],…"}
```
`ses.fetch(url, {headers})` returns a web `Response`; `response.body.getReader()` delivers events as they come. It honours the session's verify proc (S1). (`waiting:true` here: the real client loaded in ii.1 was still the active one.)

### (iv) A custom scheme handled by the main process **[run]**

```js
protocol.registerSchemesAsPrivileged([{ scheme: 'aiwb-srv', privileges: { standard: true, secure: true, supportFetchAPI: true, corsEnabled: true, stream: true } }]);
ses.protocol.handle('aiwb-srv', async (req) => { /* h = req.headers + X-AIWB-Secret */
  const up = await ses.fetch(R + path, { method: req.method, headers: h, body: req.body, duplex: 'half', signal: req.signal });
  return new Response(up.body, { status: up.status, headers: /* up.headers + Access-Control-Allow-Origin */ }); });
```
From L's `http://127.0.0.1:44201` page, against the front **without** CORS:
```
iv.1 fetch aiwb-srv://r1/api/hello {"status":200,"body":"{\"app\":\"ai-whiteboard\",…"}
iv.2 EventSource aiwb-srv://r1/api/events {"events":["{\"active\":false,\"type\":\"hello\",\"waiting\":true}"],"openMs":2,"finalState":1}
iv.3 POST with custom header {"status":409,"body":"{\"error\":\"not_active\"}"}          front: GET /api/hello secret=ok, GET /api/events… secret=ok, POST /api/groups secret=ok
```
The page keeps `fetch` and `EventSource`, holds no secret, and the server needs no CORS answers. (409: the test's client id was not the active one.) Only these three calls were run: no large bodies, no long stream, no reconnect.

## S4. A page that talks to two servers at once

**Answer.** It works with both ways tried (page sends the header in a streamed `fetch`; shell injects and the page uses `EventSource`). No mixed-content block for `http://127.0.0.1` → `https://name`, nor for `https://` page → `http://127.0.0.1`. HTTP/1.1 allows 6 connections per host; HTTP/2 did not limit. The page's stream takes the second server over from whoever was active, after 3 s.

**Run [run]** — L's page holds `new EventSource('/api/events?client=pgL')` and a stream to `https://aiwb-remote.test:44212/api/events?client=pgR`; before that, "another user" (`client=other-user`) held R's stream. Times are seconds since the page opened its streams:
```
page: local stream          ["0.00s hello{active:true,waiting:false}","0.00s snapshot"]
page: second server stream  ["0.02s HTTP 200","0.02s hello{active:false,waiting:true}","3.02s hello{active:true,waiting:false}","3.02s snapshot"]
other user                  ["release_request" at +0.02 s, "superseded" and "stream ended" at +3.02 s]
API local  POST /api/groups {"status":200,"type":"basic","body":"{\"id\":\"g_lcutyfc0\",\"name\":\"n02-local\"}"}
API second POST /api/groups {"status":200,"type":"cors","body":"{\"id\":\"g_hoz9emfi\",\"name\":\"n02-second\"}"}
page: local stream after POST ["4.50s groups","4.50s defaults"]       page: second server stream after POST ["4.51s groups","4.51s defaults"]
after 22 s more: local stream state 1; second stream ["20.02s comment \": ping\""]
```
Each server sent its own events on its own stream; the two `X-AIWB-Client` ids did not interfere. The `MODE=inject` run gave the same timeline with `EventSource` on both.

- **Preflights [run]:** when the page sets the header, every call to the second server is preflighted, `GET` included (`OPTIONS /api/state … acrh=x-aiwb-secret`); the front sent `Access-Control-Max-Age: 0`, a larger value was not tried. With injection, `GET`s are not preflighted; calls with `X-AIWB-Client` or JSON still are.
- **Single-active-client rule [run]:** opening the stream is a takeover, as T01 §3 describes: the page first gets `hello{active:false,waiting:true}`, the previous client gets `release_request` and after 3 s `superseded`, then the page gets `hello{active:true}` and the snapshot. A page connected to N servers is "the active client" on each and displaces any other window on each.
- **Mixed content [run]:**
  ```
  https page -> http://127.0.0.1:44221 (CORS on) {"status":200,"type":"cors"}     -> http://localhost:44221 {"status":200}
  … with a custom header (preflight) {"status":200}     -> EventSource http://127.0.0.1:44221/__hang: open, 1 event
  https page -> http://aiwb-other.test:44221: "Mixed Content: … requested an insecure resource … This request has been blocked"
  https page -> http://127.0.0.1:44201/api/hello (the local server, no CORS): "blocked by CORS policy: No 'Access-Control-Allow-Origin' header"
  ```
  Loopback over plain HTTP is allowed from an HTTPS page; plain HTTP to any other name is blocked. The local server as it is refuses a remote page by CORS.
- **Private/local network access:** no block, no permission request and no `Access-Control-Request-Private-Network` header appeared in any run, also with `--ip-address-space-overrides=127.0.0.1:44218=public` and a permission handler that denies everything **[run]**. Both ends were loopback, and I could not confirm that the override took effect, so this does **not** show what happens with a page from a real non-loopback address: **[not run]**.
- **Connections per host [run]:**
  ```
  8 open streams to HTTP/1.1 front {"streams":[200,200,200,200,200,"pending after 1.5 s",200,"pending after 1.5 s"],"apiWhileStreamsOpen":"pending after 2 s","localServerMeanwhile":200,"apiAfterClosingStreams":{"status":200}}
  8 open streams to HTTP/2 front   {"streams":[200 ×8],"apiWhileStreamsOpen":{"status":200,"body":"{\"port\":44214,\"httpVersion\":\"2.0\"}"}}
  ```
  Six per host (name and port) on HTTP/1.1, counted separately for each server, so one stream per server plus API calls is far from the limit. Go's `net/http` serves HTTP/2 over TLS by default **[doc]** (https://pkg.go.dev/net/http#hdr-HTTP_2); the real server's TLS listener was not part of this task.

## Unknowns that remain

- **The verdict cache:** the 30 minutes were measured once, on this Electron version; the size limit of the cache and whether a rejected verdict expires the same way were not measured. No documented way to clear it was found.
- **A certificate the OS trusts** with the box off, and a privately trusted root: not run (it would change the owner's keychain).
- **A CA-signed certificate with the wrong name, an expired certificate:** codes not observed; only self-signed ones were made.
- **Local/private network access** from a page served from a real non-loopback address to `http://127.0.0.1`: not observable here (loopback only).
- **The real Go TLS server**: HTTP/2 with `EventSource` and with streamed `fetch`, its 401 body, and its CORS answers are N01's; the fronts for the main runs spoke HTTP/1.1.
- **The custom scheme** under real use: long streams, reconnects, uploads, aborts.
- **The web client itself** against two servers: only hand-written calls were run; the real client ran only same-origin through the front (S3 ii.1).
- **`safeStorage` in the packaged, signed app**, in a dev run sharing its name, and on Linux and Windows: not run.
- **Redirects:** whether an injected header follows a redirect to another host was not tested (the URL filter suggests not).
- **A cookie instead of a header** (T04 Q8) and **an OS-configured proxy**: not tested.

## Implications (opinion)

- **Make the checkbox mean (b), a pin, and show the fingerprint.** Meaning (a) gives the secret to whoever answers first, and the secret is a remote-shell credential (T04 §2). The pieces exist: `tls.connect` reads the certificate for "test connection" and for the dialog; the verify proc, or `ca` plus a no-op name check for Node requests, enforces it. The server should print the same SHA-256 so the user can compare.
- **Plan around the verdict cache.** With the verify proc, removing a server or un-accepting a certificate can take up to 30 minutes to apply while the app runs (a certificate never seen before is always asked about at once). Either write the proc so that only "accept this host name with this fingerprint" is ever answered `0` and treat removal as "takes effect within 30 minutes or at restart", or give each server entry its own session and a new one when its certificate changes, or do the remote traffic in the main process with Node `https` (`ca` pin), which has no cache. `certificate-error` has no cache but leaves main-process requests uncovered, so alone it is not enough for "test connection".
- **Keep the secret in the main process.** Three workable shapes came out, in my order of preference for a page that talks to several servers: (1) the custom scheme: no CORS on the server, no secret in the page, `EventSource` and `fetch` unchanged apart from the base URL; (2) `onBeforeSendHeaders` with the server answering CORS: the listener should also check `details.frame.origin` or the window, because otherwise any page in the session can send authenticated requests, and CORS does not stop their effect; (3) the page holds the secret and streams with `fetch`: the most server work (preflight without the secret, CORS on everything) and the weakest. If instead each server's page is loaded from its own origin (the T12 window model), injection alone is enough and no CORS is needed.
- **A local-server relay** (the Go server calling the remote one) avoids all browser rules but was not measured here; it needs its own pinning in Go. It, or a cookie, is also the only way a plain browser tab could use a remote server.
- **The single-active-client rule becomes visible to users:** a multi-server page takes over every server it connects to. The plan should say whether it connects to all servers at start or only to those with an open chat.
- **"Test connection"** should run in the main process on a throw-away session with a short limit (5 s was enough for everything except a black hole) and map the codes of S6; it should look at the certificate first so that "wrong names" and the fingerprint can be shown.
- **`safeStorage` is good enough on macOS;** on Linux check `getSelectedStorageBackend()` and tell the user when it is `basic_text`. The file with the entries should be written with mode `0600`, which today's code does not do for its one file.
