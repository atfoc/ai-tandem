**completed**: I confirmed by running it that a web page at any loopback origin in the app can today steal server A's active-client role with a bare EventSource (kicking the user to the takeover screen — verified in headless Chrome 154 and Electron 44) and, while it holds that role, POST a forged rpc-reply (text/plain, no custom header) that the server accepts 200 (verified server-side). ## Part A — what a foreign loopback page can do to an unpatched server

**Site classification matters and is the crux.** Chrome labels a request by *site* (scheme + registrable domain, **port ignored**):

- `http://127.0.0.1:4860` → `http://127.0.0.1:4851` is **`Sec-Fetch-Site: same-site`** (same host, different port). *This is exactly the multi-server case: server B's page at `127.0.0.1:<portB>` calling server A at `127.0.0.1:<portA>`.*
- `http://localhost:4861` → `http://127.0.0.1:4851` is **`Sec-Fetch-Site: cross-site`** (different host name).

Both are "not same-origin", and the rule below rejects both. Results were identical from both origins; the table shows the `127.0.0.1:4860` (same-site) run, which is the harder, realistic case.

| Attack (from attacker page) | Reached server? headers seen | Server answer | Effect on victim | Readable by attacker | Status |
|---|---|---|---|---|---|
| `new EventSource('/api/events?client=evil-es')` | **Yes.** GET; `Origin: http://127.0.0.1:4860`, `Sec-Fetch-Site: same-site`, `-Mode: cors`, `-Dest: empty` | 200 `text/event-stream`, **no** `Access-Control-Allow-Origin` | **Takes the active role.** Victim got `release_request`, then `superseded` after 3 s; its page showed the **"Opened in another window … Use here"** takeover screen | **No** — browser raises CORS error, `readyState` → CLOSED | **verified** |
| `fetch('/api/events?client=evil-nc',{mode:'no-cors'})` | **Yes.** GET; **`Origin` absent**, `Sec-Fetch-Site: same-site`, `-Mode: no-cors`, `-Dest: empty` | 200 stream | None observed (browser did not hold it long enough to be promoted) | No — `opaque`, status 0, body `""` | **verified** |
| `<img src='/api/events?client=evil-img'>` | **Yes.** GET; **`Origin` absent**, `Sec-Fetch-Site: same-site`, `-Dest: image` | blocked by ORB (`ERR_BLOCKED_BY_ORB`) | None observed | No | **verified** |
| `window.open('/')` / top nav | Not sent in headless (`window.open` returned `opened:false`). A real top-level nav carries `Sec-Fetch-Site: none` and would just load the victim's own page | — | — | — | **unknown** (headless); reasoned harmless |
| `fetch POST /api/rpc-reply` `text/plain`, `no-cors` | **Yes.** POST; `Origin: http://127.0.0.1:4860`, `Sec-Fetch-Site: same-site`, `-Mode: no-cors`, `Content-Type: text/plain`, **no** `X-AIWB-Client` | **`409 not_active`** when the sender id is not active/pending; **`200 ACCEPTED`** once it is (see below) | Forges the answer to an agent's board-tool call | No (opaque) | **verified** |
| `navigator.sendBeacon('/api/rpc-reply', …)` | **Yes.** POST reached server (`text/plain`) | as above | as above | n/a (fire-and-forget, `queued:true`) | **verified** |
| plain `<form method=post enctype=text/plain>` to `/api/rpc-reply` | **Yes.** POST; `Sec-Fetch-Site: same-site`, `-Mode: navigate`, `-Dest: iframe` | as above | as above | No | **verified** |
| `POST /api/client/release` / `/flushed` `text/plain` | **Yes.** POST; same header shape | `409 not_active` (sender not active); accepted if active/pending | could force a premature handover | No | **verified** |
| `POST /api/chats` with `X-AIWB-Client` (and `/api/boards`) | **Preflight only.** `OPTIONS` reached server; the POST **never did** | server answers OPTIONS with no CORS headers → preflight fails → `fetch` throws | none | No | **verified** |
| `fetch('/api/state')`, `/api/dirs` (cors) | **Yes.** GET; `Origin: http://127.0.0.1:4860`, `Sec-Fetch-Site: same-site` | 200 but no `Access-Control-Allow-Origin` → browser blocks the read | none | **No** — CORS error, body unreadable | **verified** |
| `fetch('/api/state',{mode:'no-cors'})` | **Yes.** | 200 | none | **No** — `opaque`, status 0, body `""` | **verified** |

**The forging is real from a browser.** In a focused run the attacker opened `EventSource(client=evil2)` (becoming active/pending) and then POSTed the `text/plain`, no-custom-header rpc-reply with `client=evil2`; the server logged **`rpc-reply 200 ACCEPTED id=evil2`** at both t=1.0 s and t=3.6 s. `activeOrPending` is the only gate on `/api/rpc-reply`, and the EventSource lets a page satisfy it. (Note the role is held only while the browser keeps the un-readable stream open — ~4–5 s before Chrome tears it down — so a late rpc-reply gets 409; a page can re-open the stream to persist. I verified acceptance, not an end-to-end forged *tool answer*, because driving a real pending board-tool RPC needs a board token and I did not start an agent; rpc ids are sequential per T04/`bridge.go`.)

**Nothing leaks by reading.** Every cross-origin read was blocked (CORS error or `opaque`/status 0). No body, and no status/timing signal of value, was observable by the attacker.

**Chrome Local Network Access.** The permission prompt for a **public** site reaching loopback ships in **Chrome 142** (this machine is 154), replacing Private Network Access (https://developer.chrome.com/blog/local-network-access). It gates requests "from the public network to a local network or loopback destination". My attacker pages were themselves at **loopback** origins, i.e. loopback→loopback (same address space), so LNA does **not** apply and **no prompt appeared** — the attacks landed freely. This is read-from-doc for the public-site case (I did not bind a non-loopback address) and verified-empirically for the loopback-page case that this feature actually creates.

### Two-line answer
**Yes.** Today a page at any loopback origin living in the app — server B's own page, or any other local web page, or even a tab the user opens in their normal browser — can, against server A or the local server: (1) **steal the active-client role** with one `EventSource`, throwing the user's window to the takeover screen; and (2) while it holds that role, **POST a forged `rpc-reply`** (`text/plain`, no custom header) that the server **accepts (200)**, answering an agent's board-tool call. It can neither read any response nor call the `X-AIWB-Client`-guarded write routes (`/api/chats`, `/api/boards`) — their preflight fails.

## Part B — prototype of the guard change

### The rule, in words
*Main listener* (`guardMain`, wired at `server.go:710`):
1. **Host:** accept when the Host is exactly `127.0.0.1` or `localhost` (lower-case), followed by `:` and a **non-empty, all-digits** port — any port. Everything else → `403 bad host`. (I split the host into name and port on the first `:`; a bracketed `[::1]` therefore fails, a bare name with no port fails, a trailing dot or non-numeric port fails, upper-case fails.)
2. **Same-origin, `/api` only:** reject `403` when the browser signals the request is not same-origin — **`Sec-Fetch-Site` present and not `same-origin`/`none`**, **or** `Origin` present and not equal to `http://` + the request's Host. A request with **neither** header passes (curl, `findRunning`, the desktop health check, agents).

*MCP listener* (`guard`, `server.go:186`): **unchanged** — exact `127.0.0.1:<mcpPort>` / `localhost:<mcpPort>`, no same-origin check (agents send no browser headers; the board token is the credential; the advertised URL `http://localhost:6006/mcp` must stay exact).

**Which clause is actually needed.** From Part A's recorded headers: **`Sec-Fetch-Site` alone closes every attack** — the role-steal and the no-cors POSTs carry `same-site`/`cross-site`, and the two no-`Origin` no-cors GETs (`<img>`, `fetch no-cors` to `/api/events`) are caught *only* by `Sec-Fetch-Site` (their `Origin` is absent). The `Origin` clause catches nothing extra in current Chromium; it is a **fallback** for any browser that sends `Origin` but not `Sec-Fetch-Site`. I kept both (belt-and-suspenders) as the brief proposed; all current browsers send at least one.

### Existing tests
`go build ./... && go test ./...` — **all packages pass, nothing failed.** The brief expected `TestBadHostIsForbidden` to break; it does **not**, because it only asserts that Host `evil.example` (no port) is 403 and that `localhost:<realport>` is 200 — both still hold under the new rule, and it never exercises a *different* loopback port. So no existing assertion had to change; but because it doesn't cover the new behaviour I added throwaway tests (`internal/server/zz_t09_guard_test.go`, 4 tests, all pass):
- `TestT09_MainAcceptsAnyLoopbackPort` — `127.0.0.1:59999`, `localhost:1`, … → 200.
- `TestT09_RebindingSpellingsStill403` — the spellings in the table below → 403.
- `TestT09_SameOriginCheckOnAPI` — the header matrix (same-origin/none/absent → 200; same-site/cross-site/foreign-Origin/no-Origin-same-site → 403).
- `TestT09_StaticFilesNotOriginChecked` — the same-origin check does not touch non-`/api` paths.

### Real client through a different-port forward — works
With `fwd.js 127.0.0.1:4852 → 4851` and the patched server, the real web client loaded and ran at **both** `http://127.0.0.1:4852/` and `http://localhost:4852/` (via CDP): `isSecureContext:true`, app rendered, `/api/hello` 200, `/api/mcp/status` 200. A same-origin `EventSource` became the **active** client (`hello active:true` + snapshot), a same-origin `POST /api/boards` returned **200** (`b_3038zr4d`), and the `board` event arrived on the stream. (On the *old* server this same forward is `403 bad host` — Q1 of T04.)

**Anything assuming "my port"?** **No.** The web client uses only relative URLs (`web/src/api.ts`, `conn.ts`); grep for `location.*`/`4747`/`6006`/`127.0.0.1` in `web/src` finds nothing but a CSS colour. `/api/mcp/status` reports the server's **own** fixed `http://localhost:6151/mcp` (correct — MCP is not forwarded; agents use the remote machine's own listener). The version check compares the server's own `version`/`webVersion`. The only "server is local" assumptions are the desktop-side ones T04 already flagged (reconnect runs local `launch`, "Open server log", reveal-in-Finder) — none is a port assumption.

### Part A attacks before / after the patch
| Attack | Unpatched (server C) | Patched (server A) — refused at |
|---|---|---|
| EventSource role-steal | **succeeds** (victim superseded) | **403 cross-origin** (GET `/api/events`, `sfs=same-site`) — victim **stays active** |
| no-cors fetch / `<img>` to `/api/events` | reaches server | **403 cross-origin** (no `Origin`, caught by `sfs=same-site`) |
| rpc-reply / client/release / client/flushed (text/plain) | reaches handler (200 if active/pending, else 409) | **403 cross-origin** (before the handler) |
| sendBeacon / form POST to rpc-reply | reaches server | **403 cross-origin** |
| read `/api/state`, `/api/dirs` | reaches server, body CORS-blocked | **403 cross-origin** |
| `POST /api/chats` / `/api/boards` (preflight) | preflight fails already | preflight still fails (OPTIONS → 403 cross-origin) |

Every attack is now stopped at the guard, before any handler, and the EventSource steal no longer supersedes the victim (verified: "no Use here" after the attack).

### Normal paths still work (verified, with the headers they carry)
- **The page's own same-origin requests** — a same-origin `EventSource` carries **`Origin` absent, `Sec-Fetch-Site: same-origin`, `-Mode: cors`, `-Dest: empty`** → passes; a same-origin `POST` carries **`Origin: http://127.0.0.1:<port>` (== Host), `Sec-Fetch-Site: same-origin`** → passes. Verified by the full client flow above (board created, events received).
- **Top-level load of `/`** — `Sec-Fetch-Site: none`, `-Mode: navigate` → passes (200).
- **`curl /api/hello`** with no extra headers → 200 (neither header present).
- **Desktop `checkServer`** — runs in the Electron main process (Node/undici `fetch`), which sends neither `Sec-Fetch-*` nor `Origin`, i.e. the curl case → passes. (Verified the equivalent header-free request; the Part C harness also loaded the client fine.)

### Old (unpatched) server through a different-port forward
`GET http://127.0.0.1:4856/api/hello` (forward → old server on 4855) → **`403 {"error":"bad host"}`**; `localhost:4856` same. The patched server returns **200** with the hello JSON. So the app can tell "this remote server is too old for tunnels" exactly as T04 said: a 403 `bad host` on `/api/hello` through the tunnel.

### Patch size and friction
`git diff --stat`: `guard.go +80/-1`, `server.go` one-line call-site change. Of the 80 lines in guard.go, roughly **40 are functional** (three helpers — `loopbackHost`, `isAPI`, `sameOrigin` — plus the `guardMain`/`guardMode` split and one two-line check); the rest are the doc comment and the throwaway logging. What made it slightly more than a one-liner: `guard()` is shared by the main and MCP listeners, so loosening only the main one needed a second entry point (`guardMain` → `guardMode(..., main:true)`); and the Host parse had to reject `[::1]`/trailing-dot/upper-case deliberately rather than fall out of a map lookup.

## Part C — inside Electron 44, and a shell-side block

Harness: two `BrowserWindow`s, `partition:'persist:victim'` (server C's real client) and `partition:'persist:attacker'` (the `127.0.0.1:4860` page), attacks fired with `webContents.executeJavaScript`.

- **The two working attacks behave exactly as in Chrome.** EventSource steal → victim superseded ("Opened in another window … Use here"). Forged `rpc-reply` from the Electron page → server logged **`rpc-reply 200 ACCEPTED id=evil2c`** (origin `http://127.0.0.1:4860`, `text/plain`, no `X-AIWB-Client`). **No permission prompt** of any kind (`select-client-certificate` and `setPermissionRequestHandler` never fired; `anyPrompt:false`).
- **Per-session partitions change nothing about network reach** (as expected). Victim and attacker already had separate `persist:` partitions and the attack still reached the server and superseded the victim. Partitions isolate storage/cookies, not loopback network access.
- **`session.webRequest.onBeforeRequest` filter on the attacker's session** (cancel every request whose URL is a loopback origin other than the page's own `http://127.0.0.1:4860`): **stops every vector.** The BLOCKED list contained the EventSource GET, both no-cors GETs (`evil-nc`, `evil-img`), and all three `POST /api/rpc-reply` (the `fetch`, the `sendBeacon`, and the form submission), plus the `/api/state` read — and **nothing from origin 4860 reached server C after the filter went in** (confirmed in `serverC.log`). `sendBeacon`/form returned `queued/submitted:true` client-side but were cancelled at the network layer. The victim **stayed active** throughout. The attacker page's **own** traffic still worked: `fetch(ownOrigin)` → 200, `new EventSource(ownOrigin + '/ownstream')` → opened, first message received. A main-frame top-level navigation is the same request type and is equally interceptable by `onBeforeRequest` with `<all_urls>` (I verified a subframe/form navigation was blocked; I did not separately drive a main-frame nav).
- **What the shell-side block does not cover:** a normal browser tab or any other local process **outside** the app. Chrome/Safari/Firefox the user opens to `http://127.0.0.1:<port>` (or any site, subject only to LNA which does not apply loopback→loopback) can still run the Part A attacks against any loopback server; so can another Electron/CLI process. The filter also relies on the app scoping every page into a filtered session and keeping the filter installed. Its value is that it needs **no server change**, so it protects even against **old-build** remote servers that lack the guard fix.

## What the plan should require (built only from verified findings)

1. **The server must add the same-origin check on `/api`** (reject when `Sec-Fetch-Site` is present and not `same-origin`/`none`, or `Origin` is present and ≠ `http://`+Host). This is the real fix: it stops the role-steal and the `rpc-reply`/`client/*`-forging from *any* foreign page in *any* browser, including a tab the user opens outside the app. Verified to close every Part A attack and to leave the real client, top-level loads, curl and the desktop health check working. Without it, every tunnel the feature adds is another loopback port with a shell behind it, reachable by any local web page.
2. **The server must accept `127.0.0.1`/`localhost` on any port on the main listener, keeping the MCP listener exact.** Verified: the real client loads and works through a different-port forward; DNS-rebinding stays fully closed; the MCP `http://localhost:6006/mcp` spelling is untouched. These two server changes together are ~40 lines.
3. **The app should also give each server's page its own session and install a `webRequest` filter** cancelling requests to loopback origins other than that page's own. Verified to block every vector in Electron 44. This is the **only** protection that works against remote servers running an **old build** without change 1/2 — so it is worth shipping alongside, as defence in depth.
4. **Known limit to state plainly:** the shell-side filter does not cover a normal browser tab or other local app outside the app; only the server-side same-origin check (change 1) protects against those, and only for servers new enough to have it.
5. **"Too old for tunnels" is detectable:** `GET /api/hello` through the tunnel returns `403 bad host` on an unpatched server, `200` on a patched one — the app can gate the feature on this.

## Unknowns that remain

- **End-to-end forged board-tool answer** (as opposed to rpc-reply acceptance) was not driven: it needs a board token / a real pending MCP `Call`, which needs an agent I was told not to start. Acceptance (the server's only gate) and sequential rpc ids are both established, so the composition is sound but not run as one piece.
- **A browser that sends neither `Sec-Fetch-Site` nor `Origin` on a cross-origin request** would slip the same-origin check. All current Chromium/Firefox/Safari (16.4+) send `Sec-Fetch-Site`; I did not test an exotic/old browser. Non-browser tools that send neither are not "web pages" and pass by design.
- **Electron main-frame top-level navigation under the filter** — reasoned from the blocked subframe navigation, not separately executed.
- **Real `ssh -L`** behaviour — unchanged from T04 (sshd off on this machine); not in scope here.
- The patch is a **prototype**: exact error strings, whether to also origin-check static files, and placement are for the implementer; the plan should carry the rule in words (above), not this code.
