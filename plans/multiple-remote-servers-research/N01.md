# N01: HTTPS and a header secret in the Go server

I read the server at commit `be7e469` and ran three prototypes outside the repository, all bound to `127.0.0.1` on ports 44100–44199: a 118-line Go program that makes a self-signed certificate and serves TLS; a 238-line patch of the real server that adds a second, HTTPS listener with a required `X-AIWB-Secret` header next to the unchanged loopback listener; and a 117-line Go client. The standard library is enough for everything: certificate, TLS, HTTP/2, constant-time compare, pinning. The event stream works over HTTP/2 through TLS with pings arriving. Keeping the loopback HTTP listener as it is and adding a second listener left all existing Go tests passing and `launch`, `stop`, the MCP listener and the Host guard untouched. Three things need a design decision: the page cannot send a header on navigation or on `EventSource`; a cross-origin call needs CORS answers the server does not give today (a preflight gets 409 or 401); and a stream opened with an old secret keeps receiving events after the secret is regenerated.

## S1. Listeners today and what a TLS listener needs

**Answer.** Both listeners are created in `serve` with a hard-wired `127.0.0.1`. There is no bind option, no TLS and nothing about addresses in `server.json`. A TLS listener for remote clients needs: a bind-address option, a certificate, a guard whose allowed Host values are not only `127.0.0.1`/`localhost`, and the secret check. Adding it as a second listener (shape b) touched 30 lines of existing code and broke no test; making the one listener HTTPS (shape a) changes every local caller.

Today (T01 §1 established the bind; line numbers below are at `be7e469`):

- Main listener: `net.Listen("tcp", fmt.Sprintf("127.0.0.1:%d", o.port))`, `cmd/ai-whiteboard/main.go:129`; served with plain `http.Serve(ln, srv.Handler())`, `main.go:238`. [code]
- MCP listener: `net.Listen("tcp", "127.0.0.1:<6006>")`, `main.go:138`; served at `main.go:214`; handler is `MCPHandler`, exactly `POST /mcp` behind `guard(s.Bridge, mcpPort, mux)`, `internal/server/server.go:234-238`. [code]

## S2. Self-signed certificate with the standard library only

**Answer.** About 35 lines make and write the certificate; `http.Server.ServeTLS(ln, certFile, keyFile)` serves it. No dependency is needed (`go.mod` stays empty). HTTP/2 is negotiated by default and a long-lived `text/event-stream` works over it.

[run] The prototype (`$TMP/cert/main.go`, 118 lines in all: `makeCert` 33, `fingerprint` 13, a `/hello` and an `/events` route) uses `ecdsa.GenerateKey(elliptic.P256(), rand.Reader)`, an `x509.Certificate` template with a random 127-bit serial, `KeyUsageDigitalSignature`, `ExtKeyUsageServerAuth`, `DNSNames`, `IPAddresses`, then `x509.CreateCertificate(rand.Reader, tmpl, tmpl, &key.PublicKey, key)` (self-signed: template is its own parent), `x509.MarshalPKCS8PrivateKey`, and `pem.EncodeToMemory`. Result:

```
-rw-r--r--  cert.pem (619 bytes)      -rw-------  key.pem (241 bytes)
Subject: CN=AI Whiteboard   Not Before: Oct 6 06:38:59 2026   Not After: Oct 6 07:38:59 2027
X509v3 Subject Alternative Name: DNS:localhost, DNS:aiwb-remote.example, IP Address:127.0.0.1, IP Address:10.11.12.13
```

- **Fingerprint** = SHA-256 of the certificate's DER bytes. In Go: `sha256.Sum256(block.Bytes)` after `pem.Decode`. [run] The program logged `696c340d…12be`; `openssl x509 -in cert.pem -noout -fingerprint -sha256` printed the same bytes as `69:6C:34:0D:…:12:BE`. A server can print it at start and a command can print it from the file.
- **curl:** [run] without `-k` → exit 60; `-k` → 200; `--cacert cert.pem` → 200 for `127.0.0.1`, `localhost` and `aiwb-remote.example` (via `--resolve`), exit 60 for `other.example`. A leaf certificate that is not a CA is accepted as its own trust root by this curl and by Go (S7).
- **Plain HTTP to the TLS port:** [run] `HTTP/1.0 400 Bad Request` "Client sent an HTTP request to an HTTPS server."
- **HTTP/2:** [run] `curl -w '%{http_version}'` → `2`, handler saw `r.Proto = HTTP/2.0`; with `--http1.1` → 1.1. Nothing has to be configured.
- **Event stream:** [run] `curl -sk -N -m 9 …/events` printed the first event and a ping every 2 s over HTTP/2 until curl's own time-out (exit 28); the same over HTTP/1.1. `w.(http.Flusher)` works on both. The real server's stream over TLS is in S5.
- **Validity.** The period is a free choice in the template (`NotAfter`). The prototype used 1 year; the server patch used 10 years. [code of the prototype]
- **Expiry.** [run] with a certificate that expired a minute earlier: the server starts and serves it without complaint (Go does not check its own certificate's dates); `curl --cacert` → exit 60 "certificate has expired"; `curl -k` → 200; the Go client with the certificate as root fails (text in S7); the Go client that pins the fingerprint connects, because pinning replaces the date check. The server log shows only `http: TLS handshake error … remote error: tls: expired certificate`.
- **A name or IP that is not in the certificate** cannot be added later: a new certificate is needed, and its fingerprint changes. [inferred] So the names have to be known when the certificate is made, or clients must pin the fingerprint and not check the name (S7b).

## S4. The secret's life

**Answer.** The data folder is the natural place: it is 0700 and every file in it is 0600, written atomically. There is no channel from a command to a running server except SIGTERM and HTTP on loopback, so a "regen" command needs one of: the server re-reads the file per request, a signal, or a restart. The prototype used a file plus SIGHUP and it worked; an already open event stream is not affected by the change.

- **Where.** `store.Open` makes the folder and sub-folders 0700 (`store.go:66,70`); `state.json` 0600 (`store.go:78,106`); `server.json` 0600 (`store.go:117`); `server.log` 0600 (`launch.go:100`); writes go through `WriteFileAtomic` (temp file + rename, `store.go:38-47`). [code] The prototype wrote `<home>/secret` (0600, 64 hex digits + newline), `tls-key.pem` (0600), `tls-cert.pem` (0644) with the same function. [run] `ls -la $TMP/home` showed these modes.
- **Creation on start.** 32 bytes from `crypto/rand`, hex-encoded; the prototype makes a new one on every start ("generated on server start", read literally). [run] After a restart the old secret gave 401. A consequence: every `relaunch`, `/api/restart` (the page's "Restart server", `launch.go:154-168`) and reboot invalidates what every remote client has stored. The alternative, create only when the file is missing, keeps clients working across restarts; both are a few lines. The certificate, in contrast, was created only when missing, so its fingerprint survived the restart [run: same fingerprint in both start lines of the log].
- **Subcommands today:** `serve` (default), `launch`, `relaunch`, `stop`; dispatched by a `switch` in `main` (`main.go:64-80`); `command` takes the first argument without a leading `-` (`main.go:83-88`); all share one flag set (`parseFlags`, `main.go:90-116`), so a new command gets `-home` for free. Adding `secret` was one `case`. [code, run]
- **How a command talks to a running server today:** `GET /api/hello` on loopback to find it and learn its pid; `SIGTERM` to stop it (`launch.go:140,187`); nothing else. The server handles only SIGINT and SIGTERM (`main.go:222-230`, the only `signal.Notify` in non-test code). The page can ask for a restart with `POST /api/restart`. [code]
- **Options for a running server to pick up a new secret:**

  | Option | Cost |
  |---|---|
  | Re-read the file on every request | No signalling; one small file read (or a `stat`) per request, including each stream open; a half-written file is not a risk with the atomic rename |
  | Signal (prototype: SIGHUP to the pid in `server.json`) | ~10 lines; [run] `ai-whiteboard secret -new -home …` printed the new secret, the log said "secret read again", old secret → 401, new → 200. Unix only (the server already is: T01 §5). A server started outside `launch` and without `server.json` is not told |
  | Authenticated loopback route (`POST /api/secret/regen`) | Fits how `/api/restart` works; the command needs the loopback listener to be trusted or to know the old secret |
  | Restart (`relaunch`) | No new mechanism; ends every running agent turn (`main.go:222-229`), which the code base avoids elsewhere (`scripts/install-app.sh:21`) |

- **How the user reads it.** The prototype's `ai-whiteboard secret` prints the file's content on stdout (one line, like `launch` prints one URL); `cat <home>/secret` is the same thing. On a remote machine both mean a shell there (SSH). The server's start line can print the certificate fingerprint; printing the secret into `server.log` would put it in a file that is never rotated (T01 §5), so the prototype does not. [run, inferred]
- **Constant-time comparison:** `subtle.ConstantTimeCompare([]byte(got), []byte(want)) == 1`; it returns 0 at once when lengths differ, which leaks only the length. An empty configured secret must be refused explicitly (the prototype does). [code of the prototype, run]
- **What clients experience on a change.** [run] A stream opened with the old secret at t=0, secret regenerated at t=1 s: the stream stayed open and still delivered a `board` event created afterwards; a `POST` with the old secret from that same client → 401; with the new secret → 200. So the secret is checked once, when a request starts. A page in that state would show a live, connected board whose every action fails with 401. To cut old holders off, the server has to close the open streams when the secret changes (the bridge has no such call today [code: `internal/editorbridge/bridge.go`, not prototyped]); a closed `EventSource` then retries with whatever the client has and gets 401 each time.

## S6. Cross-origin use of the API

**Answer.** Today a preflight is refused: 409 on the loopback listener, and 401 on a secret-protected listener, because a preflight carries no custom header. A wrapper of about 15 lines that answers preflights before the secret check and adds `Access-Control-Allow-Origin: *` is the smallest change that makes credential-less calls with the two headers, and the stream, pass.

[run] Preflights with `Origin: http://127.0.0.1:4747`, `Access-Control-Request-Method`, `Access-Control-Request-Headers: content-type,x-aiwb-client,x-aiwb-secret`:

```
Server as it is (loopback listener):  OPTIONS /api/boards → 409 {"error":"not_active"}   OPTIONS /api/state → 409    no Access-Control-* header
TLS listener, secret, no CORS code:   OPTIONS /api/state, /api/boards, /api/events → 401 {"error":"unauthorized"}
                                      GET /api/state with Origin + secret → 200, no Access-Control-Allow-Origin (a browser would hide the answer from the page [inferred])
TLS listener with -tls-cors:          OPTIONS (all three) → 204
                                         access-control-allow-origin: *
                                         access-control-allow-methods: GET, POST, PUT, PATCH, DELETE
                                         access-control-allow-headers: X-AIWB-Secret, X-AIWB-Client, Content-Type
                                         access-control-max-age: 600
                                      GET /api/state with Origin + secret → 200 + access-control-allow-origin: *
                                      GET /api/state wrong secret → 401 + access-control-allow-origin: *
                                      GET /api/events with Origin + secret → 200 text/event-stream + access-control-allow-origin: *, hello event arrives
```

- The 409 today comes from `needsActive`: `OPTIONS` is not GET/HEAD, so the guard asks for the active client (`guard.go:41-52`); T01 §2 observed the same.
- The wrapper must sit **outside** the secret check and the guard, or the preflight never gets its answer. [run]
- `*` is allowed because the calls carry no cookie or HTTP credentials; the secret header is the credential. A browser actually accepting these answers (including for a streamed `fetch`, and the private-network rules for a public page calling a private address) is **[not run]**: curl does not enforce CORS. That is N02's.
- A cross-origin `EventSource` needs no preflight but cannot send the secret; with a header secret the cross-origin stream has to be a `fetch` (S3).
- **Conflict with the plan's "same-origin check on `/api`"** (plan section 6, from T09): that check refuses, before any handler, every request the browser marks as coming from another origin, and lets through only the page's own requests, top-level loads and callers without browser headers. A local page calling a remote server's API is exactly a request marked as another origin, so the two cannot both hold on the same listener. Ways out [inferred]: keep the same-origin check on the loopback listener (where no secret is required) and allow cross-origin only on the secret-protected listener; or keep the page same-origin with the API (the remote server serves its own page), in which case no CORS is needed and the check can stay everywhere. The plan's Host rule is not in conflict: it is kept in the prototype.
- With `Access-Control-Allow-Origin: *` on the remote listener, any web page the user opens can call that API if it knows the secret; without the secret it gets 401. The cross-site problems T04 Q8 item 4 lists for cookies do not arise with a header secret, because a browser never attaches it by itself. [inferred]

## S7. Go as the client of such a server

## Unknowns that remain

- No listener on a real LAN or VPN address was run; firewall prompts on macOS for a non-loopback bind, and IPv6, are untested.
- Browser and Electron behaviour (accepting the self-signed certificate, CORS enforcement, private-network rules, a `fetch`-based stream, adding the header to navigations) is N02's; here only curl and Go were clients.
- Whether "generated on server start" means every start or the first start. The two differ in whether a restart logs every remote client out.
- Whether "only the API is exposed" means no static files on the remote listener. If yes, every page call is cross-origin and S6 applies; if the remote server may serve its page, no CORS is needed but navigation and `EventSource` need the secret by another route.
- Closing open event streams on regeneration was not prototyped.
- No rate limiting on wrong secrets was built or measured; a 256-bit secret makes guessing pointless, but 401s are not logged.
- A dial time-out to an unreachable host, and a certificate with a changed key on a pinned client in the app, were not run.
- HTTP/2 and the real page: the browser's per-origin limit of six HTTP/1.1 connections does not apply over HTTP/2, which may matter with several streams; not measured.

## Implications (opinion)

- Shape (b) is the cheap and safe one: the local app, `launch`, `stop`, the tests and the MCP listener stay exactly as they are, and the remote listener is opt-in with one flag. Shape (a) buys nothing behind a VPN and costs every local caller.
- Take the certificate's names and the guard's allowed Hosts from one list, and let clients pin the SHA-256 fingerprint. Pinning removes the dependence on names and dates, so a 10-year certificate created once is fine, and "the checkbox for self-signed certificates" could become "paste or confirm this fingerprint", which is stronger than "do not verify".
- I would create the secret when the file is missing and replace it only on the `secret -new` command. Regenerating on every start makes the page's own "Restart server" button lock all remote clients out.
- For the running server, re-reading the file per request or SIGHUP both work; whichever is chosen, regeneration should also close the open event streams, otherwise an old holder keeps reading everything until its connection drops.
- Hello on the remote listener should be behind the secret like everything else: "the secret on all endpoints" is then literally true and the client's "test connection" checks secret and certificate in one call. Local probes keep using the loopback hello.
- If the remote listener is API-only, the plan needs CORS on that listener and the same-origin check only on the loopback listener, and the page's event stream has to move from `EventSource` to `fetch`. If the remote server also serves its page, the app must put the header on navigation, static files and the stream (N02), and no CORS is needed. These are the two coherent designs; mixing them gives the costs of both.
