**completed**: I built an isolated scratch server and ran all five experiments plus a few extra ones with a TCP forwarder, a Host-rewriting proxy, a Go TLS+token front and headless Chrome; real `ssh -L` could not be run because sshd is off on this machine, so SSH-specific behaviour is from the man pages. Main facts: the Host guard rejects any forward whose local port differs from the server's port (403 `bad host`), SSE streams fine through a forward and recovers by itself after a drop, the web client does not load at all on a plain-http non-loopback origin (`crypto.randomUUID` is undefined), and an unauthenticated caller can take over the active client with one GET and then create chats and boards. My recommendation (opinion) is an app-managed SSH tunnel with one local port per server plus a small guard change to accept loopback Host names on any port; server-side token+TLS and bring-your-own-network are deferred.

## 1. Option A — SSH local port forward

### What it requires

**Server**
- Nothing, if the local port equals the remote server's port (verified, Q1).
- For several servers, or next to the local server on 4747, one of three things is needed (Q2):
  1. Each remote server runs on its own non-default port (`-port`), and that same number is free on the laptop.
  2. A small guard change: accept `127.0.0.1` / `localhost` with any port (`guard.go:26` builds exactly two allowed strings today).
  3. No server change, and the app rewrites `Host` itself.
- The bind address stays loopback. The MCP listener on 6006 is not forwarded: agents run on the remote machine and use its own `http://localhost:6006/mcp`.

**Desktop app**
- One `ssh` child per remote server, for example:
  `ssh -N -o BatchMode=yes -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -L 127.0.0.1:<Q>:127.0.0.1:<P> <host alias>`
- Per-server settings: SSH destination (an alias from `~/.ssh/config` works), remote port, local port (chosen by the app), optionally the remote command that starts the server.
- The reconnector must change. Today, after three failed `/api/hello` checks it runs the **local** `ai-whiteboard launch` (`desktop/lib.js:160-262`, wired at `desktop/main.js:122-128`). For a remote server it has to restart the tunnel instead.
- `checkServer` uses a 1 s timeout (`lib.js:131-137`).
- Each server gets its own origin `http://127.0.0.1:<Q>`, so `localStorage` (`aiwb.sel`, drafts, widths: `web/src/store.ts:37-54`) is separate per server without extra work.

**User**
- An SSH login on the remote machine that works without prompts: key in the agent, host key already in `known_hosts`.
- The server installed on the remote machine, with its web client folder. The client is not embedded in the binary: `-client` defaults to `web/dist` relative to the working folder, or the app bundle's `Resources/web` (`main.go:88-91`).
- Agent CLIs logged in on the remote machine.

### Failure modes

| Failure | What happens | Status |
|---|---|---|
| Tunnel process dies | Page shows "Reconnecting…", `EventSource` retries every 3 s, recovers about 3 s after the forward is back with a new `hello` + `snapshot`, no reload | **verified** (Q3) |
| Tunnel stalls with no reset (sleep/wake, Wi-Fi change) | Page shows nothing for the whole stall, `fetch` hangs, recovers silently when traffic resumes. The web client has no watchdog on the 20 s ping | **verified** (Q3) |
| ssh notices a dead peer | With `ServerAliveInterval 15` and `ServerAliveCountMax 3`, ssh disconnects after about 45 s | **inferred** (man text, Q7) |
| Local port already taken | With `ExitOnForwardFailure=yes` ssh terminates; without it ssh keeps running with no forward | **inferred** (man text) |
| Key needs a passphrase, or host key unknown | `BatchMode=yes` disables prompts, so ssh fails at once; the user must connect once in a terminal first | **inferred** |
| Laptop asleep or tunnel down | No active client on the remote server: agents keep running, but their board tools fail with "the board isn't open" (`internal/editorbridge/bridge.go:64,204-218`; 30 s call timeout `internal/boardapi/mcp.go:27`) | **verified by reading** |

### Security properties

- **Remote side**: unchanged. The port is loopback-only; who may connect is decided by sshd.
- **Network attacker**: sees SSH only.
- **Laptop side**: any process of any user on the laptop can connect to `127.0.0.1:<Q>` and gets the full unauthenticated API of the remote machine, which amounts to a shell there (Q5). This is the same exposure the local server has today, extended to the remote machine. `ssh -L` binds loopback by default (`gatewayports no` in `ssh -G` output); the app should pass `127.0.0.1:` explicitly.
- **Malicious web page in the laptop's browser**: same position as against the local server today.
  - DNS rebinding is blocked by the Host guard (**verified**: other host names get 403).
  - It cannot read responses (no CORS headers) and cannot call header-checked routes (**verified** `409`).
  - It **can** make itself the active client with one GET, kicking the user's window out, and can then post to `/api/rpc-reply` with its client id in the body, forging answers to agents' board tool calls (**verified** server-side with curl, section 7.1; that a browser page can actually send these requests is **inferred**).

## 2. Option B — server listens on a non-loopback address with its own access control

### What it requires

**Server**
- A bind-address option (`main.go:125` hard-codes `127.0.0.1`).
- A configurable allowed Host list. Today any other Host is 403 (**verified**: `192.168.1.4:4801`, `myhost.local:4801`, `LOCALHOST:4801` and `localhost:4801.` all return 403).
- Authentication on everything, static files included (Q8).
- **TLS is not optional.** On `http://<lan-ip>:port` or `http://name:port` the web client renders a blank page (**verified**, Q4).
- The MCP listener must stay loopback and strict. It reuses the same `guard()` with its own port (`internal/server/server.go:183-187`), so a guard change must not loosen it.
- `/api/hello` is used unauthenticated by `findRunning` (`main.go:269-285`) and by the desktop health check (`lib.js:137`); the plan must decide what it answers without a token.

**Desktop app**
- Per-server URL and token, with secure storage for the token.
- A way to get the token into the page session: a cookie bootstrap URL **verified** in Chrome; Electron's cookie and header APIs **not tested**.
- For a self-signed certificate, fingerprint pinning (Electron `setCertificateVerifyProc` / `certificate-error`: **not tested**).
- No process management.

**User**
- Opens a port or firewall rule, copies a token, and deals with a certificate.
- A real certificate needs a DNS name plus ACME. Go's ACME client is `golang.org/x/crypto/acme/autocert`, not the standard library; `go.mod` has zero dependencies today.

### Failure modes

- Certificate expiry, or a changed self-signed certificate.
- Token rotation.
- Firewall or NAT in the way.
- Without a tunnel process there is nothing to restart; the page's own `EventSource` retry handles network drops (**verified** for connection-refused, Q3).

### Security properties

- Anyone who can reach the port and has the token has a shell on that machine. The token is a remote-code-execution credential on an internet- or LAN-facing Go HTTP server with no rate limiting today.
- Without TLS the token and all content are readable on the network.
- With a self-signed certificate and no pinning, the first connection can be intercepted.
- With cookie authentication, the cross-site weaknesses in 7.1 become reachable from any web page unless the cookie is `SameSite=Strict` and/or the server checks `Origin`.

## 3. Option C — bring your own network (VPN, tailnet, reverse proxy)

### What it requires

**Server**
- **None, if a TLS reverse proxy in front rewrites `Host` to `127.0.0.1:<port>`.** **Verified**: with the unchanged scratch server behind `tlsproxy`, the full web client loaded and worked at `https://aiwb-remote.example:4805` (run B7 in Q8).
- If the user reaches the server directly on a VPN address (no proxy): a bind option and an allowed Host are needed, and plain http still gives a blank page (Q4). So this variant also needs HTTPS in front, or a web client that no longer needs a secure context.
- A token is advisable, because everyone on the VPN or tailnet can otherwise reach `/api`.

**Desktop app**
- Stores a URL and loads it. A rudimentary form exists: with `AIWB_URL` set, the app loads that URL and never runs `launch` (`desktop/lib.js:56,124-126`; read, not run).
- The reconnector's "run launch again" must be disabled for such servers.

**User**
- Everything else: reachability, TLS, access control.
- Proxy settings for SSE: no response buffering, and an idle timeout above the 20 s ping (`bridge.go:27`). The proxy-side requirements are **inferred**.

### Failure modes

| Failure | What happens | Status |
|---|---|---|
| Proxy answers with an error status (502) while the upstream is down | `EventSource` goes to `CLOSED` and never retries; the page stays on "Reconnecting…" forever, even after the upstream is back, until reload | **verified** (Q3) |
| Proxy keeps the client's stream open after losing the upstream | Page shows no sign at all while its stream is dead | **verified** (Q3, first proxy run) |

### Security properties

Entirely delegated. The server's only own defence is the Host guard, which a Host-rewriting proxy neutralises by design. An attacker who reaches the proxy and passes its authentication has a shell.

## Q1. Host guard vs. forwarded port — verified

**Answer.** Through a forward on a different local port, every route is refused with `403 {"error":"bad host"}`: `/`, `/api/hello`, `/api/events`, for both the `127.0.0.1` and `localhost` spellings. With the Host the server expects (what a same-port forward from another machine produces), everything works. A tunnel therefore needs one of: the same port number on both ends, a guard change, or Host rewriting.

**Evidence** (`node fwd.js 127.0.0.1 4802 127.0.0.1 4801` running):

```
$ curl -s -i http://127.0.0.1:4802/                         → HTTP/1.1 403 Forbidden  {"error":"bad host"}
$ curl -s -i http://127.0.0.1:4802/api/hello                → HTTP/1.1 403 Forbidden  {"error":"bad host"}
$ curl -s -i -m 3 "http://127.0.0.1:4802/api/events?client=x" → HTTP/1.1 403 Forbidden  {"error":"bad host"}
$ curl -s -i http://localhost:4802/api/hello                → HTTP/1.1 403 Forbidden  {"error":"bad host"}

$ curl -s -i -H 'Host: 127.0.0.1:4801' http://127.0.0.1:4802/          → HTTP/1.1 200 OK (index.html, 928 bytes)
$ curl -s -i -H 'Host: 127.0.0.1:4801' http://127.0.0.1:4802/api/hello → 200 {"app":"ai-whiteboard","pid":74676,"version":"dev","webVersion":"dev"}
$ curl -s -i -H 'Host: localhost:4801' http://127.0.0.1:4802/api/hello → 200 (same body)
$ curl -s -i -N -m 3 -H 'Host: 127.0.0.1:4801' "http://127.0.0.1:4802/api/events?client=probe1"
  → 200, Content-Type: text/event-stream, then  data: {"active":true,"type":"hello","waiting":false}  and the snapshot
```

Host spellings sent straight to P, all 403: `192.168.1.4:4801`, `myhost.local:4801`, `127.0.0.1` (no port), `[::1]:4801`, `LOCALHOST:4801`, `localhost:4801.`.

The MCP listener behaves the same: `curl -X POST -H 'Host: 127.0.0.1:9999' http://127.0.0.1:6101/mcp` → 403 `bad host`.

Code: `guard.go:25-31` — exact string match against `127.0.0.1:<port>` and `localhost:<port>`.

**Same result with the real web client in headless Chrome:**
- `node ctx.mjs http://127.0.0.1:4802/` → the page body is `{"error":"bad host"}`.
- `node ctx.mjs http://127.0.0.1:4801/ '--host-resolver-rules=MAP 127.0.0.1:4801 127.0.0.1:4802'` → the app renders fully and `/api/hello` returns 200. Chrome's URL keeps the server's port while every connection goes through the forwarder (its log showed the connections), which is exactly what a same-port `ssh -L` looks like.

## Q2. Several servers at once through forwards

**Answer.**
- A forward works unchanged only when local port = remote server port (**verified**, Q1).
- Local 4747 is the local server, and two remote servers on 4747 would need the same local port, so default-port servers cannot coexist.

The plan must pick one of:

1. **Non-default, mutually distinct remote ports**, each also free on the laptop. No code change; the user configures `-port` on every remote server. The number must be agreed across machines, which is fragile. (**inferred** from Q1)
2. **Per-server local ports plus a server-side guard change** so that `127.0.0.1:<any>` / `localhost:<any>` is accepted. The remote server must be a version that has the change; the app can detect an old one because `/api/hello` through the tunnel answers 403 `bad host`. That the server works when it sees an accepted Host is **verified** (Q1). That relaxing only the port keeps DNS-rebinding protection is **inferred**: a rebinding request always carries the attacker's host *name*, which is still rejected.
3. **Per-server local ports plus Host rewriting by the app**, no server change. Two ways were tried:
   - **Local HTTP reverse proxy** that sets `Host: 127.0.0.1:<remote port>` (`rproxy.js`, about 20 lines): the real client loads and works at `http://127.0.0.1:4803/` (**verified**). Cost: one more hop, and the 502 failure mode in Q3.
   - **Per-server browser session that uses the raw forward as its HTTP proxy**, so the URL stays `http://127.0.0.1:<remote port>/`: **verified in Chrome** with `--proxy-server=http://127.0.0.1:4802 --proxy-bypass-list=<-loopback>` (app rendered; Go's server accepts the absolute-form request line; `curl -x http://127.0.0.1:4802 http://127.0.0.1:4801/api/hello` → 200). The Electron equivalent (`session.setProxy` per partition) is **not tested**. All servers would then share the origin `http://127.0.0.1:4747`, so `localStorage` collides unless each server gets its own session partition.

## Q3. SSE through a forwarder

**Answer.** Events pass unbuffered. The server writes a `: ping` comment every 20 s. A 170 s idle stream stayed up. A killed forwarder is survived without a reload. A stalled forwarder is invisible to the page. A proxy that answers 502 kills the `EventSource` for good.

**Keep-alive in code**: `internal/editorbridge/bridge.go:27` (`pingEvery = 20 * time.Second`), ticker at `:138`, write at `:158-160`. It fires every 20 s regardless of traffic. The WHATWG spec recommends such comment lines "every 15 seconds or so" (https://html.spec.whatwg.org/multipage/server-sent-events.html).

**Unbuffered delivery — verified** (`node sse.js 4802 127.0.0.1:4801 sse1 170`, then a POST through the forwarder):

```
POST /api/groups sent at 20:02:19.972
   3030ms 20:02:19.993 CHUNK 79B "data: {\"groups\":[{\"id\":\"g_jgs76mmt\",\"name\":\"via-forwarder\"}],\"type\":\"groups\"}\n\n"
```
The event arrived 21 ms after the POST was sent.

**Idle survival — verified**: `: ping` chunks at 20008, 40006, 60005, 80005, 100005, 120006, 140005 and 160005 ms; the stream was closed by my own 170 s timer, not by a drop.

**Forwarder killed, then restarted after 12 s — verified** (`node drop.mjs kill`, real web client in headless Chrome):

```
loaded:            ES open, hello active=true, snapshot
forwarder killed at t=4030ms
  4009ms ES error (readyState 0 CONNECTING: will retry)     page shows "AI Whiteboard Reconnecting…"
  7014 / 10016 / 13018 / 16020ms ES error (CONNECTING)      fetch /api/hello: TypeError: Failed to fetch
forwarder restarted at t=16048ms
  19021ms ES open, hello active=true, snapshot               "Reconnecting…" gone, fetch 200
requests to /api/events at: 211, 7038, 10040, 13042, 16048, 19045 ms
```
Chrome errors: `ERR_INCOMPLETE_CHUNKED_ENCODING` on the stream, then `ERR_CONNECTION_REFUSED`. The page reconnects with the same client id, which is the "same tab reconnecting" path (`bridge.go:98-102`). The client side is `web/src/conn.ts:21` (`onerror` only sets `connected: false`) and `web/src/Sidebar.tsx:189`.

**Forwarder frozen for 56 s (`SIGSTOP`), then resumed — verified** (`node drop.mjs stall`):
- No `EventSource` error for the whole stall.
- The page text was unchanged (no "Reconnecting…").
- `fetch('/api/hello')` hit my 3 s timeout each time.
- After `SIGCONT`, fetch returned 200 and no reconnect happened.
- In the client code there is no timer watching the ping.

**Proxy that answers 502 when its upstream is gone — verified** (`node drop.mjs proxy`: Chrome → `rproxy` 4803 → forwarder 4802 → server; forwarder killed):

```
  4016ms ES error (readyState 0 CONNECTING: will retry)
  7023ms ES error (readyState 2 CLOSED: will not retry)      ← reconnect got 502
forwarder restarted at t=16076ms: fetch /api/hello 200, but the page still shows "Reconnecting…" 20 s later
requests to /api/events at: 217ms, 7055ms   (no further attempt)
```
This matches the spec: a response whose status is not 200 makes the user agent "fail the connection" (same WHATWG URL). `conn.ts` only calls `connect()` again from the "Use here" button (`conn.ts:69`).

A first run of this scenario used a proxy version that did not close the client's stream when the upstream died. The page then showed no error at all and its event stream was silently dead.

**Not verified**: the same sequences over a real `ssh -L`. An SSH forward is a byte channel like the forwarder, so the HTTP-level results should carry over, but ssh's own timing on sleep/wake is **inferred** from the manual (Q7).

## Q4. Page origin and secure context

| Option | Page origin | Secure context? | Status |
|---|---|---|---|
| A (forward) | `http://127.0.0.1:<local port>` or `http://localhost:<local port>` | yes | **verified** in Chrome |
| B/C over plain http | `http://<lan-ip>:4747`, `http://host.example:4747` | **no** | **verified** in Chrome |
| B/C over https | `https://host:port` | yes | **verified** in Chrome (certificate errors ignored) |

**Documentation.**
- Secure Contexts spec, "Is origin potentially trustworthy?" (https://w3c.github.io/webappsec-secure-contexts/#is-origin-trustworthy): scheme `https` or `wss`; host in `127.0.0.0/8` or `::1/128`; host `localhost` or ending in `.localhost`; otherwise "Not Trustworthy".
- MDN (https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts): `http://localhost` is secure, `http://example.com` is not.

**Runs** (`node ctx.mjs <url> [chrome flags]`):

## Q6. Single-active-client rule and a remote user — verified by reading; the takeover itself was observed in Q5

- One client is active per server. A new `/api/events` connection with a different id becomes pending. The active one gets `release_request` and is cut off with `superseded` after 3 s if it has not released (`bridge.go:24,103-114,286-301`). Observed timings: `release_request` at once, `superseded` 3.0 s later.
- A well-behaved active client flushes its board saves and posts `/api/client/release`, which promotes the newcomer immediately (`conn.ts:34`, `bridge.go:167-173`).
- The superseded page closes its `EventSource` and shows "Opened in another window … Use here" (`conn.ts:35`, `web/src/App.tsx:27`, `web/src/Dialogs.tsx:55-64`). It does not fight back by itself; clicking "Use here" reconnects and takes over again (`conn.ts:69`).
- Events go to the active client only (`bridge.go:190-200`). Non-GET `/api` calls from anyone else get `409 not_active` (`guard.go:32-35`).

**Browser left open on the remote machine + desktop app on the laptop:**
- When the laptop connects through the tunnel, the remote tab saves, releases and shows the takeover screen. Nothing is lost.
- If someone presses "Use here" on the remote machine, the laptop window gets the takeover screen.
- Two laptops against one server behave the same way: last one in wins.

**Consequences for a multi-server app:**
- Activeness is per server, and agents' board tools need an active client (`bridge.go:204-218`; README "boards can only be changed while the app (or a browser tab) is open").
- A server whose page is not loaded in the app has no active client, so its agents cannot touch boards.
- Keeping one live page per registered server keeps them all usable, but takes the active role away from any browser tab on those machines for as long as the app runs.

## Q7. What OpenSSH offers for a managed tunnel — read from `man ssh` / `man ssh_config` on this machine (OpenSSH_9.9p2); none of it run against a server

| Feature | Manual text (quoted) | Use for the app |
|---|---|---|
| `-N` | "Do not execute a remote command. This is useful for just forwarding ports." | Tunnel-only child process |
| `-L [bind_address:]port:host:hostport` | "connections to the given TCP port or Unix socket on the local (client) host are to be forwarded to the given host and port … on the remote side"; "The bind_address of "localhost" indicates that the listening port be bound for local use only" | The forward. Also accepts `local_socket:host:hostport` |
| `ExitOnForwardFailure` | "whether ssh(1) should terminate the connection if it cannot set up all requested … port forwardings, (e.g. if either end is unable to bind and listen on a specified port)"; it "does not apply to connections made over port forwardings" | Port clash becomes a process exit the app can see. A remote server that is not running does not |
| `ServerAliveInterval` / `ServerAliveCountMax` | "default is 0"; with interval 15 and count 3, "if the server becomes unresponsive, ssh will disconnect after approximately 45 seconds" | Turns a silent stall into an exit |
| `BatchMode` | "user interaction such as password prompts and host key confirmation requests will be disabled" | No hidden prompts from a GUI app; fails fast instead |
| `ControlMaster` / `ControlPath` / `ControlPersist`, `-O` | "Enables the sharing of multiple sessions over a single network connection"; `-O` commands: "check", "forward", "cancel", "exit", "stop" | One connection per host for both the tunnel and commands; `-O check` as a health probe |
| Config and aliases | ssh reads "1. command-line options 2. user's configuration file (~/.ssh/config) 3. system-wide configuration file" | The user's host aliases, `ProxyJump`, `IdentityAgent` and so on apply |
| Exit status | "ssh exits with the exit status of the remote command or with 255 if an error occurred" | Error detection |
| `StrictHostKeyChecking` | default `ask`: new keys are added "only after the user has confirmed" | With `BatchMode`, an unknown host fails; the user must connect once in a terminal |

**Run locally (connects nowhere):**
`ssh -G -o BatchMode=yes -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -N -L 127.0.0.1:47471:127.0.0.1:4747 some-alias` printed `batchmode yes`, `exitonforwardfailure yes`, `serveraliveinterval 15`, `serveralivecountmax 3`, `sessiontype none`, `gatewayports no`, `localforward [127.0.0.1]:47471 [127.0.0.1]:4747`. So the options are accepted, and `ssh -G` is a way for the app to validate a destination.

**Agent**: `launchctl getenv SSH_AUTH_SOCK` returns a socket path on this machine, so apps started from Finder have the agent (**verified for this machine only**).

**Starting the remote server over SSH** (`ssh host <path>/ai-whiteboard launch`) — **inferred** from `cmd/ai-whiteboard/launch.go`, not run:
- `launch` prints the URL as its only stdout line and exits (`launch.go:44-52,74-76`).
- The server is started in its own session, with output to `server.log` and no inherited terminal (`launch.go:95-117`), so it should outlive the SSH session.
- It takes PATH from the login shell (`launch.go:55,200-219`), so agent CLIs should be found.
- The printed `http://127.0.0.1:<port>/` gives the port to forward to.

Open points: see unknowns 2 and 3.

## Q8. Option B building blocks

**Go standard library for TLS** (`go doc`, and used in `tlsproxy/main.go`): `http.Server.ServeTLS`, `tls.Config{Certificates, MinVersion}`, a self-signed certificate made in memory with `crypto/ecdsa` + `x509.CreateCertificate`, `crypto/subtle.ConstantTimeCompare`, `httputil.ReverseProxy` (its `FlushInterval` doc says streaming responses are flushed immediately). Automatic Let's Encrypt certificates are not in the standard library.

**Scratch proof — verified** (TLS + one shared token in front of the unchanged server, loopback only):

```
$ curl -sk -i https://127.0.0.1:4805/api/state                                   → HTTP/2 401 {"error":"unauthorized"}
$ curl -sk -i -H 'Authorization: Bearer nope' …/api/hello                        → 401
$ curl -sk -i -H 'Authorization: Bearer s3cr3t-scratch-token' …/api/hello        → 200 {"app":"ai-whiteboard",…}
$ curl -sk -i 'https://127.0.0.1:4805/auth?token=s3cr3t-scratch-token'           → 303, set-cookie: aiwb_auth=…; Path=/; HttpOnly; Secure; SameSite=Strict
$ curl -sk -N -H 'Cookie: aiwb_auth=…' '…/api/events?client=tls1'                → 200 text/event-stream, hello + snapshot
$ curl -s https://127.0.0.1:4805/api/hello  (no -k)                               → curl exit 60 (certificate not trusted)

B7  Chrome  https://aiwb-remote.example:4805/auth?token=…  with --ignore-certificate-errors
    → lands on https://aiwb-remote.example:4805/, isSecureContext true, app renders, /api/hello 200, no errors
B8  Chrome, same, certificate not accepted  → net::ERR_CERT_AUTHORITY_INVALID
B9  Chrome, no token                        → page is {"error":"unauthorized"}
```

**What a minimal token scheme has to cover:**

1. **Page navigation and static files.** A navigation cannot carry an `Authorization` header, so either a cookie set by a bootstrap URL (verified above), or the desktop app sets the cookie or header itself (Electron `session.cookies.set` / `webRequest.onBeforeSendHeaders`: **not tested**).
2. **`fetch` calls.** Same-origin, so the cookie goes along with no client change. A bearer header would mean changing `api.ts:32-36`.
3. **`EventSource`.** The constructor's only option is `withCredentials`; no custom headers (https://developer.mozilla.org/en-US/docs/Web/API/EventSource/EventSource). The token must be a cookie (verified working) or a query parameter; a query token ends up in logs and history.
4. **Cross-site requests.** With a cookie, the browser attaches it to requests from other sites unless it is `SameSite`. `X-AIWB-Client` protects most non-GET routes, but not `GET /api/events` (which changes who is active), nor `/api/client/release`, `/api/client/flushed` and `/api/rpc-reply` (exempt at `guard.go:48`, client id read from the body at `server.go:140-145`). So: a `SameSite=Strict` cookie and/or an `Origin` check.
5. **`X-AIWB-Client` stays.** It identifies the tab for the single-active-client rule; it is not authentication (Q5).
6. **`/api/hello`.** Used without credentials by `findRunning`, `stop`/`relaunch` (`main.go:269-317`, `launch.go:132-149`) and by the desktop health check (`lib.js:137`); it reports the pid.
7. **Token lifecycle.** Where it is created and stored on the server, how the user reads it, rotation, and storage in the desktop app.
8. **Certificate trust.** A self-signed certificate is rejected by a browser (B8); the desktop app would need pinning (**not tested**).
9. **MCP listener.** It must remain loopback and Host-strict (`server.go:183-187`).

## 7. Other findings that affect the plan

### 7.1 Pre-existing cross-site weakness (matters more once tunnels add loopback ports)

**Verified** server-side with curl, sending what a foreign page's request looks like (foreign `Origin`, no custom header):

```
GET /api/events?client=evil  (Origin: http://evil.example)   → 200; the real client gets release_request, then superseded 3 s later
POST /api/groups, Content-Type: text/plain                   → 409 not_active   (header-checked routes hold)
POST /api/rpc-reply, text/plain, body {"id":"rpc_999","client":"evil","result":{"forged":true}} → 200 {"ok":true}
```

- A web page can therefore kick the user's window out, and can answer agents' board tool calls (rpc ids are sequential, `bridge.go:205`) while it holds the active role.
- It cannot read anything, because there are no CORS headers.
- That a browser really lets a page send these requests to loopback is **inferred**; newer Chrome versions may ask for a local-network permission, **not checked**.
- The server never looks at `Origin`.

### 7.2 Desktop behaviour that assumes "the server is local"

- The reconnector runs the local `launch` (`lib.js:124-128,160-262`).
- "Open server log" opens the laptop's `~/.ai-whiteboard/server.log` (`main.js:23,197`, `preload.js`).
- The start error dialog says "could not start its server" (`main.js:141-160`).

### 7.3 Server actions that happen on the server machine

- Reveal in Finder (`boards.go:291`): wrong machine for a remote user.
- The folder picker `/api/dirs` (`server.go:669-688`): correct for remote, it lists the remote disk.
- `/api/restart` (`launch.go:151-168`).

### 7.4 Version skew

The web client is served by each server, so the UI a user sees is that server's version; the desktop shell has to work with several versions at once.

### 7.5 Linux

`GOOS=linux GOARCH=amd64 go build ./cmd/ai-whiteboard` succeeds (**verified** compile only, not run). The README states macOS only.

## Unknowns that would change the plan

1. **Real SSH behaviour** (not run: sshd is off). Open: whether `ExitOnForwardFailure` exits as documented on a busy local port; how fast ssh notices a dead link after sleep/wake; whether a forward to a remote port nobody listens on fails cleanly per connection.
2. **Starting the server over SSH.** Whether `ssh host … launch` returns promptly, and whether agents started that way are logged in. On macOS, CLI logins kept in the Keychain may not be readable from an SSH session. If not, the user must start the remote server themselves, and "the app starts it" drops out.
3. **How the server gets onto the remote machine**, with its web client folder and a known path. Over a non-interactive SSH command the binary is not on PATH; on macOS it lives in the app bundle (`lib.js:11-15`).
4. **Electron specifics**, all untested: per-session proxy or Host rewriting, certificate pinning, cookie injection, running `ssh` from a Finder-launched app (only the agent socket was checked).
5. **Is more than one person or laptop per server in scope?** The single-active-client rule makes concurrent use a turn-taking affair.
6. **Should a non-visible server stay "active"?** One live page per server, or only the selected one (Q6).
7. **Bandwidth and latency over a WAN**: whole-scene `PUT`s and the board-tool round trip (30 s timeout). Not measured.
8. **Option C details**: whether Tailscale's HTTPS serve passes the original Host (it would be rejected today), and proxy buffering and timeouts for SSE. Not tested.
9. **Whether browsers block the cross-site requests in 7.1** by local-network permission. Not checked.

## Recommendation (opinion, not a finding)

**First version: Option A, an SSH tunnel managed by the desktop app, with one local port per server and a small server change so the Host guard accepts `127.0.0.1` / `localhost` on any port.**

Why:
- The remote server stays loopback-only and unauthenticated; SSH, which the user already trusts and has configured, is the access control and the encryption.
- The page origin stays loopback, so the web client works unchanged: secure context, clipboard, `randomUUID`.
- Each server gets its own origin, hence its own `localStorage`.
- Experiment 3 shows the existing client already survives tunnel restarts.

On the multi-server choices (Q2):
- I prefer the guard change over app-side Host rewriting because it is a few lines and adds no proxy with the 502 dead-end.
- The catch is that remote servers must run a version with the change; the app can detect an older one by the 403 `bad host` on `/api/hello` and say so.
- If touching the guard is unwanted, the fallback is the app-side reverse proxy (verified to work).

In the same version I would include:
- The suggested ssh flags (`-N`, `BatchMode`, `ExitOnForwardFailure`, `ServerAliveInterval`/`CountMax`, explicit `127.0.0.1` bind), using the user's `~/.ssh/config` aliases.
- A reconnector that restarts the tunnel instead of running local `launch`.
- Two web client hardenings found by experiment 3: re-create the `EventSource` when it is `CLOSED`, and reconnect when no ping arrived for about 45 s.

Deferred:
- **Starting the remote server from the app over SSH.** It depends on unknowns 2 and 3. First version: the user starts it, and the app shows a clear "server not running on that machine" state.
- **Option B** (bind address, token, TLS in the server). It is the largest and riskiest piece: a token that equals a shell, certificate handling, cross-site hardening. Nothing in option A needs it.
- **Option C** as a supported feature. A "URL-only" server entry is cheap (the app can already load a URL via `AIWB_URL`) and works with zero server change behind a Host-rewriting HTTPS proxy, but it hands the whole security question to the user. If offered at all, as an advanced, clearly labelled entry.

Independently of the option chosen, I would fix the cross-site weakness in 7.1 (check `Origin` on `/api/events` and on the routes that take the client id from the body), since every tunnel adds another loopback port with a shell behind it.
