# R1: agents survive temporary errors: what Cursor and pi cannot do

Deviations from `claude-retry-api-errors-goal.md` outcome 1.4 ("The same classification serves Cursor and pi where they report
enough to tell. Where an agent kind cannot be told apart or cannot reopen a session in a new process, it behaves as it does today
and the difference is written down as a deviation"), each with the reason. Design D3 has the decision; this file is the record.

- **Cursor: no turn is temporary.** A failed `session/prompt` reaches the adapter as a JSON-RPC error that `conn.Call` turns into
  text (`session/prompt: <message> <data>`, `rpcErrorText` in `acp.go`); its code is dropped, and no recording of a Cursor login,
  rate or overload error exists in the repository. The adapter therefore never sets `agent.Temporary`. A Cursor turn that ends with an
  error ends as before: a subagent is finished with the error and its result goes to its parent, the chat holds with the error
  note. Nothing retries it and it is never paused. Guessing from the text would break goal 1.1, which says the class comes from
  what the CLI reports.
- **Cursor: the session is still recorded, and a stopped Cursor subagent can be resumed.** Cursor reopens a session in a new
  process (`session/load`). A Cursor subagent has no session id when it is started: the process reports it with `EvSession`, and
  `handleSubEv` writes it into `Subagent.Session` (and `AgentID`, as before). A Cursor subagent stopped before that event has no
  session and cannot be resumed (`resume_subagent` says its session was not recorded). Since a Cursor subagent is never paused, it
  is resumed only when it was stopped.
- **pi: only an error pi retried itself and gave up on is temporary.** pi reports a failed turn as an assistant message with
  `stopReason: "error"` and a free-text `errorMessage`. The one statement that is not free text is its own retry: when the turn
  had an `auto_retry_end` with `success: false`, the turn end has `Temporary` `retried`, shown as "temporary error" (there is no
  class to name). Any other pi error is not temporary.
- **pi: a login failure is not temporary.** A 401 has `willRetry: false` and no retry lines
  (`internal/pi/testdata/failed_turn.jsonl`), so it ends as before. This differs from Claude, where a login failure is the case the
  goal began with (goal 1.2). Telling it from the text of `errorMessage` would be the guessing that goal 1.1 excludes.
- **pi: its retries are short.** pi retries within seconds (three attempts in the recording), the app's four take minutes; a pi
  turn that is retried by the app has already been retried by pi.
- **Claude: classes read from the CLI, two cases assumed.** The classes are those of the enum of the `error` field of Claude Code
  2.1.309 (read from its binary, nothing run) and of the recordings of 2.1.284 (`internal/claude/testdata/api_error_*.jsonl`).
  That "Not logged in" and a lost connection (`server_error` with `apiError: "no_response"`) arrive as an api-error assistant line
  plus an errored result, as a rejected key does, is **not verified**: it was seen only in the CLI's strings (design R2). If the
  CLI instead exits, the exit is no temporary error and the turn ends as before. One run of a real Claude subagent whose login has
  expired confirms it; it is paid and is run only when the person asks.
- **Claude: a rejected key and a usage limit are classed with the rest.** `authentication_failed` is temporary whether the login
  expired or the key is simply invalid, and `rate_limit` includes a limit that resets in hours. Their retries run out and the agent
  is paused, so a later "continue" resumes it; that was accepted in the design (D2).
