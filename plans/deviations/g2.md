# G2 deviations and notes for the integration

Nothing in C2 is met by less than it says. The following differ from it, add to it, or are left for the
integration.

## Additions and choices

1. **A launch lock.** `launch` and `relaunch` take an exclusive `flock` on `<data folder>/launch.lock` (made 0600,
   kept; waits up to a minute) for the whole of find, start and wait. Two launchers (the app's, a person's) take
   turns: the second finds the server the first started and starts none. This replaces the old way of keeping the
   race (keep polling while anything accepts on the port), which needs a port to look at and has none now. A
   `serve` started by hand does not take it: it is the loser of a race by its own MCP bind, as before.
2. **`launch` waits until the client listener serves.** The control socket answers hello as soon as it is bound,
   which is before the client listener serves; `launch` writes its answer only when `/status` says
   `client.listening` and has the fingerprint. A found server of this build that is not serving yet is waited for
   (30 s) too.
3. **The control socket is bound late**, just before `server.json` is written and after the servers and the stores are
   made, not directly after the client bind (C2.4 says "after the MCP and client listeners", which this is). A start
   that dies in between leaves no socket; one that dies after leaves a stale file that the next start replaces.
4. **`launch` hands the server it starts `-home <absolute folder>` first, then exactly the flags it was given**, as
   `-name=value`, and not `-json`. Without a flag the server's own default stays its own (its working folder is the
   home folder, where `launch` starts it). `pgrep -f "serve -home <folder>"` finds it, as the old tests did.
5. **`stop`, `status`, `secret` and `remote` take `-home` alone** (`status` also `-json`, `remote setup` its own
   flags); a flag of the server is a usage error (exit 2). `serve`, `launch`, `relaunch` take the server flags;
   `-json` only on the last two.
6. **`status` text.** `Port:`, `Names:` and `Fingerprint:` appear twice, as C2.3 lists them: the running server's after
   `Running:` and the files' after `Files:`. A reader tells them apart by the `Files:` line. A server of this build
   that does not serve yet has no `Address:` block. `status -json`'s `files` leaves out `port`, `names` and
   `fingerprint` when the files give none (never set up), and `running.instanceId` when the server has none.
7. **`serve` beside a running server** prints `AI Whiteboard is already running (pid N)` (no address) and exits 0, for
   this build and for the build before.
8. **Stopping.** `stop` and `relaunch` wait up to 10 s until `findRunning` no longer finds that pid, then up to 3 s
   (not an error) until the process is gone, so that the new server's MCP bind does not meet the old one's.
9. **`secret -new` of the build before** is signalled when its hello states feature level ≥ 1 and a pid and its
   `/api/remote/status` says it listens (as before); for this build when hello has a pid and `/status` says the client
   listener serves. The confirmation is the rise of `secretReloads`, in both. The sentence says "Its clients were
   disconnected" (it said "API clients").
10. **`legacyPort`** (4747) is a variable of package main so that the tests of the package look elsewhere; no test of
    this package looks at 4747. The built binary the process tests start does probe 4747 (read-only, `GET /api/hello` and
    `/api/state`) and ignores a server whose data folder is not its own.

## Removed

- `-port`, `-client` (and `-server-port` of `remote setup`), `bundleResources`/`resourcesFor` (the `-client` default),
  `startRelaunch` (nothing calls `POST /api/restart` now), `remote off`, the `remote status` command (both answer exit 2
  with C2.1's sentence).
- `server.ErrBinaryMissing` in `internal/server` is now used by nothing; `internal/` is not G2's, so it stays.

## Tests

- **Counts.** `cmd/ai-whiteboard` has 36 tests that are in the full set only and six smoke tests in the default set
  (listed in `harness_test.go`). `AGENTS.md` says 49 and six: the integration corrects the 49.
- **`AGENTS.md` lists eight names for `AIWB_TEST_WAITS`; the server reads three** (`ping`, `agents`, `images`, G1). The test that
  held the two lists equal (`TestSectionWaitNamesAreTheOnesOfAgentsMD`) is gone; the integration, which edits the docs,
  can put one back (`parseTestWaits("nosuchwait=1s")`'s error names the server's three).
- **`TestBundleCarriesSetupScript`** reads `desktop/electron-builder.yml` (D1's file) for the `extraResources` entry
  `../scripts/remote/setup-remote.sh` → `remote/setup-remote.sh`. It fails if D1 drops it.
- **`TestBuildServerFolders`** (needs `AIWB_TEST_BUILD=1`, no node) was run once and passes: four folders of the program and
  the two scripts and the README, no `web/`.
- **Stand-ins.** The older build is a Go HTTP server on a free loopback port (its `server.json` has no `control`), with a
  `sleep` process as its pid; the one of this build is a Go server on a Unix socket in the data folder. Both stop
  answering when their pid is gone. Tests of the command's choices (find, launch, stop, status, `secret -new` gate) run in
  the default set against them; the process-level ones are in the full set.
- **Removed with their subject**: the `/api/restart` test, `TestReloadSignalWithRemoteOff`, `TestAPIClientBesideAPage` (now
  `TestTwoClientsBesideEachOther`: two clients of the same kind), the app-bundle `-client` check, and the stand-in web client.

## Check of `desktop/conn` against the real program

`desktop/conn` (J1) was run against the real binary with a scratch script (not in the repository; `/tmp`), with a temporary
data folder, free ports and no agent programs on `PATH`; no `npm ci` was needed, the module uses Node built-ins alone:
never set up → `not_started` with the server's message naming `remote setup`; after the set-up and Retry → `connected`, the
snapshot, a call, `owner.status` (`status -json`), `owner.restart` (`relaunch -json`, `secret`; a new pid); `stop` while the
app is open → `unreachable` and started again by the app, `connected`; `secret -new` → `unreachable` then `connected`. All as
C2 says; no change of `desktop/` was needed.
